# 앵무새도 알아먹는 CP 강좌: CP0 ~ CP32, 그리고 다음 할 일

2026-11-08 작성, 2026-11-17 고침 (CP29~CP32 결과). CP31부터 이 파일은 `journal/`에 있음. 지금 결론만 보고 싶으면 `../README.md`랑 `../docs/`. 원본 기록은 [CHECKPOINT.md](CHECKPOINT.md)랑 `cp/CPn.md`. 여기는 그걸 배경지식 0인 사람용으로 풀어 쓴 거임.
숫자 옆에 **(측정)** = 실제로 재 봄, **(추정)** = 모델로 계산함, **(출처)** = 남의 논문·데이터시트.

---

## 0. 세 줄 요약

1. 운영자 없는 익명 커뮤니티를 만들려면, 운영자가 하던 일(검색, 스팸 거르기, 신원 확인)을 **각자 집에 둔 작은 상자(노드 박스)**가 대신 해야 함.
2. 그 상자가 하는 일 중 **기존 칩으로 비싼 부분**을 찾아서, 그걸 싸게 하는 **칩을 설계**하는 게 수업 프로젝트임.
3. CP(체크포인트)는 "큰 질문 하나 풀기" 단위임. CP0~CP29 동안 "어디가 비싼가 → 칩을 어떻게 짜나 → 그 칩 숫자가 진짜 맞나 → 진짜 컴퓨터 여러 대에서 굴려 보자 → 굴리기 전에 박스끼리 주고받는 규칙부터 제대로" 순서로 왔음.

## 1. 배경지식 0부터 (용어 사전)

| 용어 | 앵무새 설명 |
|---|---|
| 운영자 | 디시로 치면 디시 회사. 글을 다 볼 수 있고, 지운 글도 살릴 수 있음 |
| **server-blind** | 서버(저장해 주는 쪽)가 글 내용을 **못 읽게** 암호화해 두는 것. 그래서 서버가 검색·추천을 대신 못 해 줌 → 누가 해야 함 |
| **노드 박스** | 공유기·NAS처럼 집에 24시간 켜 두는 작은 상자. 이게 운영자 일을 대신함. 우리 칩이 들어갈 자리 |
| 수집 (ingest) | 새 글이 박스에 도착했을 때 하는 일 전부: 진짜인지 확인 → 암호 풀기 → 임베딩 → 색인에 넣기 |
| **임베딩** | 글을 숫자 384개짜리 벡터로 바꾸는 것. 뜻이 비슷한 글은 벡터도 비슷함. 이걸로 "뜻으로 검색"을 함. 바꿔 주는 AI 모델이 **인코더**(우리는 MiniLM, 사진은 CLIP) |
| 색인·검색 | 벡터들을 모아 두고(색인), 검색어 벡터와 가장 비슷한 10개를 찾음 (top-10) |
| **INT8 / FP16 / FP32** | 숫자를 몇 비트로 계산하냐. FP32가 제일 정확하고 비쌈, INT8이 제일 싸고 부정확. 칩 크기·전력이 이걸로 크게 갈림 |
| **Recall@10 계약** | "싼 방식으로 찾은 상위 10개가, FP32로 정확히 찾은 상위 10개와 평균 95% 이상 겹쳐야 한다"는 우리 품질 규칙. 싸게 만들려고 검색 품질을 깎는 꼼수를 막는 장치 |
| **익명 증명 (Groth16)** | "나 회원 맞음, 근데 누군지는 안 알려줌"을 수학적으로 증명하는 쪽지. 글마다 붙어 옴. 박스는 이걸 **검증**해야 함 (생성은 글쓴이 기기가 함) |
| RLN / 한도 | 같은 사람이 정해진 양 이상 쓰면 비밀이 드러나게 만든 장치. 익명이지만 도배는 못 하게 |
| **스팸 폭주** | 공격자가 가짜·진짜 글을 인터넷 회선 끝까지(100 Mbps) 쏟아붓는 상황. 박스는 쪽지를 다 검증해 봐야 버릴 수 있음 |
| 밀린 수집 | 박스가 8시간 꺼졌다 켜지면 그동안 쌓인 글을 한꺼번에 처리해야 함. 목표: 60분 안에 |
| 계약 (K1~K5 등) | 우리가 정한 목표치들. 새 글은 5초 안에 검색되게, 검색 응답은 50 ms 안에, 밀린 수집은 60분 안에 등 |
| **모델 / 시뮬레이션** | 칩을 실제로 안 만들고, "이 칩이면 몇 ms, 몇 mJ"를 계산하는 프로그램. 반도체는 못 찍으니 칩은 끝까지 모델로 감 |
| **에뮬레이션** | 진짜 코드로 진짜 일을 하는 것. 우리 프로젝트에서는 **"기능은 진짜, 시간은 모델"**로 정했음 (CP15). 아래 5절 참고 |
| RTL / 합성 | 칩 회로를 코드(Verilog)로 쓰고, 도구로 진짜 회로 면적·속도를 뽑는 것. 우리는 곱셈기 하나만 함 |
| gossip | 박스끼리 소문 퍼뜨리듯 새 글을 이웃에게 전하는 방식 |
| **동기화 (sync)** | 두 박스가 만났을 때 "너 있고 나 없는 거"를 찾아 맞추는 것. 꺼졌다 켜진 박스가 놓친 글을 따라잡는 것도 이거 |
| **집합 맞추기 (reconciliation)** | 글 목록 전체를 보내는 대신, 구간별 "지문"(ID를 더한 값)만 비교해서 다른 구간만 쪼개 들어가는 방식. 차이가 작으면 주고받는 양도 작음 |
| **바닥 (floor)** | 아무 일 없어도 10~30분마다 한 번 이웃과 지문을 맞춰 보는 것. "아무도 못 본 손실"을 고치는 최후의 안전망 |

## 2. 큰 그림: 일곱 막

| 막 | CP | 질문 | 답 |
|---|---|---|---|
| 1막 | CP0~CP5 | 박스가 뭐에 시간을 쓰나? 기존 칩(노트북 NPU)으로 충분하냐? | 시간의 98%는 인코더(임베딩). 근데 노트북 NPU를 잘 다루면 **시간 목표는 이미 지킴** → "빠르게"로는 칩이 필요 없음 |
| 2막 | CP6~CP14 | 그럼 칩이 필요한 데는 어디? | **스팸 폭주 때 익명 증명 검증.** 기존 엣지 칩은 이걸 아예 못 함 → 검증 유닛을 설계 (곱셈기 RTL까지) |
| 3막 | CP15~CP21 | 칩 숫자들이 "박스 하나가 하루 100만 건 받는다" 같은 대충 가정 위에 있음. 진짜 커뮤니티면? | 커뮤니티 시뮬레이터를 만들어 진짜 부하를 냄 → 인코더 크게 줄임, 칩 11 → 5.6 mm² (추정). 진짜 박스 프로세스로 데모하고 시뮬레이터와 숫자 맞춤 |
| 4막 | CP22~CP24 | 칩으로 못 막는 공격(진짜 회원이 한도 끝까지 비싼 글 쓰기)은? | 칩이 아니라 **규칙(프로토콜)**으로 막음. 그래도 남는 구멍은 "신원 만들기를 비싸게" 해야 함 |
| 5막 | CP25~CP28 | 진짜 여러 컴퓨터에서 굴리면? | 껐다 켜도 같은 회원 되게 만듦, 박스끼리 쓸데없이 묻던 것(폴링) 갈아엎음, 알고리즘으로 줄일 거 다 줄여 봄 → 그러다 품질 계약 구멍 발견, 칩 인코더 다시 키움 (16×16) |
| 6막 | CP29~CP30 | 팀원이랑 진짜로 굴리기 직전, 박스끼리 주고받는 규칙에 구멍은 없냐? | 구멍 10개 찾음 (H1~H10). 규칙을 "만날 때마다 집합 맞추기"로 갈아엎고 4가지 방법으로 검증 → 정확은 한데 비쌈 → CP30에서 중복 받기 없애고 구멍 하나(H11) 더 고침 → **데모 기본 규칙으로 채택** |
| 7막 | CP31~ | 남한테 보여줄 준비 | CP31: 저장소를 "지금 필요한 것 / 지난 기록"으로 정리. CP32: 한 화면에 사용자 다섯 띄워 보여주기 → 구멍 H12 (서브를 안 가리는 동기화) 찾음 |

지금은 **7막**: CP32 한 화면 데모 끝. 데모가 구멍 하나(H12)를 찾아서 다음은 CP33 서브별 동기화.

## 3. CP 하나씩

### 1막: 어디가 비싸냐

**CP0 · 영감 논문 찾기**
- 한 일: 비슷한 연구 18편 모으고 IKS(ASPLOS'25) 하나 리뷰.
- 결과: 엣지 검색 칩은 이미 있음. 아무도 안 한 건 **"새 글을 마감 안에 받아 넣기"**랑 **"검색하는 중에 넣기"**.
- 그래서: 우리 차별점을 거기로 좁힘.

**CP1 · 글 하나 받는 데 뭐가 비싸냐**
- 한 일: 새 글 받기(서명 확인 → 복호화 → 임베딩 → 색인)랑 검색을 단계별로 시간 잼.
- 결과 (측정): **임베딩이 98%**, 암호는 0.5%. 100만 개 검색은 25 ms라 쌈. 근데 INT8 임베딩은 품질이 0.875로 계약(0.95) 미달.
- 그래서: 메인 일감 = 인코더. 진짜 압박은 평소가 아니라 **밀린 수집**이랑 **약한 기기**.

**CP2 · 인코더 기준선**
- 한 일: INT8/FP16/FP32 품질·속도·에너지 비교.
- 결과 (측정): 계약 통과하는 INT8은 **없음** (최고 0.878). FP16은 0.999.
- 그래서: "어느 INT8이 빠르냐"가 아니라 "품질 기준을 뭘로 하냐"가 먼저라는 걸 깨달음.

**CP3 · 정밀도 계약**
- 한 일: 어느 층이 품질을 깎는지 하나씩 FP32로 돌려 봄.
- 결과 (측정): 오차가 골고루 퍼져 있어서 몇 층만 고쳐서는 안 됨. 대신 **INT8로 받고, 검색할 때 상위 20개만 FP32로 다시 매기면** 0.993.
- 그래서: 계약 = Recall@10 ≥ 0.95 확정. (이 "다시 매기기"를 나중에 칩 모델에서 빼먹음 → CP27에서 들킴)

**CP4 · 약한 기기용 가속기 첫 견적**
- 한 일: INT8 배열 크기별 시간·에너지 모델 + 노트북 NPU 실측.
- 결과: 모델 칩은 8시간치를 56분 (추정). NPU는 174분 (측정), 최대 성능의 1~2%만 씀.
- 그래서: NPU가 왜 노는지 알아봐야 함.

**CP5 · NPU는 왜 노냐**
- 한 일: NPU 시간 뜯어보기.
- 결과 (측정): 시간의 89%가 컴파일러가 마스크+softmax를 느린 길로 보낸 탓. 우회하니 **174분 → 45분**.
- 그래서: **"기존 칩이 시간 목표를 못 지킨다"는 주장은 안 섬.** 칩의 몫은 시간 말고 다른 데서 찾아야 함.

### 2막: 칩이 필요한 진짜 자리

**CP6 · 박스가 하는 일 전부**
- 한 일: 대상 기기를 "상시 켜진 홈 노드 박스"로 정하고 암호까지 다 잼. 시판 엣지 칩 조사.
- 결과: 평소엔 뭘 해도 1 W 아래. 근데 **스팸 폭주 때 익명 증명 검증**이 초당 1.2만 건 → CPU로는 24~181 W (추정). 그리고 **시판 엣지 AI 칩은 이 계산(큰 정수 곱셈)을 아예 못 함** (출처).
- 그래서: 칩의 존재 이유 = 폭주 때 검증.

**CP7 · 검증 유닛 첫 견적**
- 결과 (추정): 전용 유닛이면 CPU보다 400~800배 적은 에너지. 곱셈기 1개로도 충분해 보임.
- 그래서: 크기보다 "어디에 두냐"가 질문.

**CP8 · 검증 유닛 위치**
- 한 일: 전용 유닛 / 인코더 배열 빌려 쓰기 / CPU 명령 확장 / 소프트웨어, 넷 비교.
- 결과: 인코더 배열 빌려 쓰기는 40배 모자람. **전용 유닛** 채택.

**CP9 · 첫 RTL: 254비트 곱셈기**
- 한 일: 곱셈기를 Verilog로 쓰고 45 nm로 합성 (측정).
- 결과: 0.28 mm², 300 MHz급. 에너지는 추정의 4.2배였지만 그래도 통과.

**CP10 · 파이프라인 곱셈기**
- 결과 (측정): 클럭이 기대(2~4배)와 달리 1.2배만 오름 → 포기. 곱셈기 4개로 감.

**CP11 · 검증 유닛 전체 사이클 모델**
- 결과 (추정): 증명 하나에 곱셈 1.4만 번. 곱셈기 5 + 덧셈기 4. 곱셈기를 바쁘게 하려면 **계산 순서**가 핵심.

**CP12 · 칩 첫 견적**
- 결과 (추정): 칩 11 mm², 평소 0.09 W, 폭주 0.48 W. Pi 5 + Hailo 조합보다 살짝 나음.

**CP13 · 틀린 증명 섞기 공격**
- 결과 (추정): 틀린 증명 하나만 섞여도 묶음 검증이 통째로 실패 → 최악은 "전부 틀린 증명". 곱셈기 8 + 덧셈기 8로 키움.

**CP14 · 틀린 증명 버리는 비용 줄이기**
- 결과 (추정): 미리 계산 등으로 비용 0.65배 → **6 + 6으로 다시 줄임**, 칩 11.3 mm².

### 3막: 진짜 커뮤니티라면?

**CP15 · 시스템 설계**
- 결정: **기능은 에뮬레이션(진짜 코드, 진짜 암호·임베딩·검색), 시간·에너지는 시뮬레이션(칩은 모델).** 데모만 실시간. ← 지금 실험도 이 규칙 그대로임
- 깨달음: 칩 크기가 "박스가 모든 글을 받는다"는 숨은 가정에 묶여 있었음.

**CP16 · 사용자 행동 + 시뮬레이터**
- 결과 (모델): 사용자 100만 명이어도 상위 박스가 받는 양은 기존 가정의 **1/26**. 이미지는 계산보다 **전송**이 문제.

**CP17 · 박스 기능 전부 + 가상 가속기**
- 한 일: 박스가 하는 일 전부를 진짜 코드로 붙이고 시간은 칩 모델로 셈 (= **가상 가속기**).
- 결과: 1만 박스 하루 시뮬레이션에서 기능 거의 다 통과. 평소 칩은 거의 놂. 기기마다 같은 사진에서 **임베딩이 다르게 나옴**(INT8) → 결정성이 하드웨어 요구 후보.

**CP18 · 인코더 다시 판정**
- 결과 (추정): 진짜 부하 기준이면 인코더 **8×8, 1 MB면 충분** → 칩 11.3 → **5.61 mm²**. 같은 INT8 파일도 프로그램마다 결과가 다름 (측정).

**CP19 · 시나리오: 어디서 처음 깨지냐**
- 결과 (추정): 폭주 땐 칩보다 **CPU가 먼저** 무너짐 → "증명부터 확인" 순서로 해결. 진짜 회원이 한도 끝까지 비싼 글 쓰기(맞는 스팸)는 **칩으로 못 막음**.

**CP20 · 같은 조건 비교 + 하나씩 끄기**
- 결과: 검증 유닛 없는 기존 조합은 폭주를 못 버팀. **우리 기여의 중심 = 검증 유닛.** 사진 인코더는 INT8 안 되고 FP16 (측정).

**CP21 · 데모 + 실시간 vs 시뮬레이터**
- 한 일: 진짜 박스 프로세스 5개를 띄워서 시뮬레이터와 작업 수 비교.
- 결과 (측정): 55칸 전부 일치 → **시뮬레이터 숫자를 믿어도 됨.** 웹 화면 데모도 통과.

### 4막: 칩으로 못 막는 공격

**CP22 · 운영자 없이 맞는 스팸 막기**
- 결과 (추정): 무게 한도 + 사진은 뒤로 + 새/오래된 회원 구분, **셋 다** 있어야 버팀.

**CP23 · 무게 한도 구현 비용**
- 결과: 증명 회로 비용은 작음. 근데 CP22의 최악 공격 가정이 틀렸음 (사진 글이 아니라 긴 텍스트만이 최악) → 남는 구멍 541개 신원. 결론: **신원 만들기를 비싸게** 해야 함.

**CP24 · 정합성 빚 정리**
- 결과: 시뮬레이터 버그 고쳐도 고른 설계는 그대로. 데모 박스 = 설계 = 시뮬레이터. 컴퓨터 여러 대에서 돌게 만듦.

### 5막: 진짜 여러 컴퓨터에서

**CP25 · 껐다 켜도 같은 회원**
- 결과 (측정): 신원·글·지운 글을 디스크에 저장, 재시작해도 같은 회원. 근데 **박스끼리 20초마다 전부 물어보는 폴링**이었다는 걸 발견 → 원격 실측 취소.

**CP26 · 박스끼리 언제, 누구와, 뭘 주고받나**
- 결과: 폴링은 필요한 양의 **4.8만~430만 배**를 주고받음 (모델). **사건 기반(새 글 생겼을 때만, 켜진 이웃에게만, 빠진 것만)**으로 바꿈 → 0.5~7.6%만 추가. 데모가 모델과 일치 (측정).

**CP27 · 알고리즘 착취 감사**
- 규칙 추가: "하드웨어로 줄이기 전에 알고리즘으로 줄일 거 다 줄였냐?" (NORTHSTAR 7-6)
- 결과: 글 전체 대신 **ID 먼저** 보내기로 중복 6.8배 → 1.2배. 작성자가 보낸 임베딩을 믿으면 독살 공격 230배 → 임베딩은 박스가 직접 해야 함. 그리고 **CP12부터 칩 모델이 INT8만 셌다는 구멍** 발견 (계약 위반).

**CP28 · 계약 정밀도로 다시**
- 결과 (추정): 텍스트를 FP16으로 하면 8×8로는 못 지킴 → **16×16**, 칩 5.6 → 9.6 mm² 이상. 데모 박스에 ID 먼저 + FP32 텍스트 넣고 모델과 칸칸이 맞춤 (측정). 그러다 가짜 지우기로 진짜 글을 막는 보안 구멍 찾아 고침.
- 교훈: 알고리즘 감사가 오히려 하드웨어 몫을 늘린 첫 사례.

### 6막: 굴리기 전에 규칙부터

**CP29 · 박스끼리 맞추는 규칙 갈아엎기 + 4층 검증**
- 원래 계획은 팀원이랑 진짜로 굴리기였음. 근데 굴리기 전에 개념만 따져 봤는데 CP26 규칙에 구멍이 줄줄이 나옴. 예:
  - 고치는 계기가 "내가 켜졌다" 하나뿐. 박스가 2~3개면 전달 한 번 실패가 **영원히 빠짐** (H1).
  - "여기까지 다 가졌음"이라는 말을 그냥 믿음 → 거짓말하는 박스가 숨기면 끝 (H4).
  - **확인하기 전에 저장**함 → 가짜 봉투가 진짜 글의 ID를 먼저 차지하면 진짜가 "중복"으로 버려짐 (H8).
  - 그리고 숨은 편향: 정확성이 "늘 켜진 박스가 하나는 있다"에 기댐. 그런 박스는 사실상 **운영자**임.
- 한 일: 규칙을 **만날 때마다 집합 맞추기**로 바꿈 (확인 먼저, 내용 해시 ID, 사건마다 맞추기 + 느린 바닥). 검증은 네 겹:
  1. 무작위 시뮬레이션 520번 (거짓말 박스·가짜 글·시계 차이 섞음, 마지막에 다 켜 주는 꼼수 없음)
  2. 구멍마다 일부러 재현하는 대본 88번
  3. 작은 세계 전수 조사 (상태 2,496개 전부)
  4. 이 PC에서 진짜 박스 4개 띄우고 선 뽑기·시계 틀기·강제 종료
- 결과: 새 규칙(S2)은 **네 겹 다 위반 0** (모델 + 측정). 진짜 박스로 돌리다가 구멍 2개 더 찾음:
  - **H9**: 글 시각이 서명 밖이었음 → 중간 박스가 시각만 바꿀 수 있었음.
  - **H10**: 서명 확인 결과를 ID로만 기억함 → 서명만 깨진 사본을 먼저 보내면 진짜 글이 확인도 없이 버려짐. 모델에는 그 기억 장치가 없어서 진짜 코드에서만 보였음.
- 근데 **비용 관문에서 떨어짐**: 옛 규칙보다 +8~+583%p 더 씀 (모델). 그래서 규칙대로 데모 기본값은 안 바꿈.
- 교훈: 모델 검사는 **규칙**의 구멍을, 진짜 코드 검사는 **구현**의 구멍을 잡음. 둘 다 필요함.


**CP30 · 동기화 비용 짜내기**
- 새는 곳 셋을 고침:

| 새는 곳 | 디시로 치면 | 고침 | 결과 (모델) |
|---|---|---|---|
| 켜질 때 이웃 여럿한테 동시에 물어서 같은 글을 3~4번 받음 | 짤 하나를 갤러 셋이 동시에 퍼 줌 | **K**: "지금 받는 중" 표. 받다 실패하면 바로 다른 데서 | 중복 **2~4배 → 0**. 노트북 1,000대 장면에서 동기화 데이터가 박스당 하루 907 KB → 52 KB |
| 아무것도 안 바뀐 이웃이랑도 10~30분마다 확인 | 새 글 없는데 계속 새로고침 | **F**: 내 쪽이 바뀌었을 때만 확인 | 아무 일 없는 날 28~31 KB → 1~2 KB. 근데 사고 침 (아래) |
| 꺼진 박스를 계속 찔러봄 | 탈갤한 놈한테 계속 멘션 | **P**: 붙으면 그만 찾고 이웃한테 물어봄 | 찔러보기는 줄었는데 새 글이 **0.45초 → 1,059초** 늦게 옴 → 버림 |

- **F가 친 사고 (유령 이웃)**: 이웃들이 재시작하면서 나를 잊었는데, 나는 "깨끗함"이라 믿고 확인을 안 함 → 5시간 동안 고립. 알고 보니 "10~30분마다 확인"은 차이 확인이면서 **"너 아직 나 이웃으로 보냐" 확인**이기도 했음. 그걸 같이 빼 버린 거임.
  - 고친 F′: "30분 동안 그 이웃한테서 아무 소리도 못 들었으면 확인". 다 통과했지만 결과 보고 고친 거라 기본값 말고 옵션으로 둠.
- **원래 있던 구멍 하나 더 (H11)**: 1시간 넘게 반으로 갈라졌다 붙으면, 두 무리가 **영영 안 합쳐짐** (CP29 규칙에도 있던 거). 1시간에 한 번 아무 박스한테나 인사(탐색)하게 해서 고침.
- 세대 번호(맞추는 도중 내 목록이 바뀌었으면 "같음"을 안 믿기)는 진짜 박스로 일부러 그 장면을 만들어서 확인함. 끄면 진짜로 잘못 "깨끗함"이 찍힘.
- 결과: 기본 규칙 = **중복 막기 + 탐색**. 네 겹 검증 다시 다 통과 (무작위 220번 위반 0, 진짜 박스 대본 12개 통과). 글 하나는 박스마다 정확히 한 번만 확인됨 → 칩 일의 양은 그대로.
- **데모 박스 기본값을 새 규칙으로 바꿈.**
- 교훈: 뭘 빼서 아낄 땐 그게 몰래 하던 일까지 적고 빼야 함. 그리고 "만난 두 박스가 같아지냐"만 보면 무리가 쪼개지는 건 안 보임 → "켜진 남은 가졌는데 나만 없는 글"을 따로 셈.

## 5. 자주 헷갈리는 거

**Q. 그럼 칩은 어디 쓰임?**
A. 칩은 **설계도 + 계산 모델**임. 박스 프로그램이 진짜 일을 하면서, 그 일을 칩이 했으면 얼마 걸렸을지를 모델로 같이 셈. "기능은 진짜, 칩 시간은 모델"이 CP15부터의 규칙.

**Q. 왜 칩을 FPGA 같은 걸로 진짜 안 돌림?**
A. 없음 + 학기 안에 못 함. 대신 곱셈기 하나는 RTL로 써서 진짜 회로 숫자를 뽑았고(CP9~CP10), 나머지는 그 숫자로 맞춘 모델임.

**Q. 이 실험 망하면 뭐가 문제임?**
A. 칩이 아니라 **프로토콜**이 틀렸다는 뜻. 실제로 CP29에서 굴려 보기도 전에 그런 구멍이 10개 나와서 규칙부터 갈아엎었음. 칩 크기는 "박스가 받는 일의 양"에서 나오니까, 프로토콜이 바뀌면 칩 숫자도 다시 냄 (CP25~CP28이 실제로 그랬음).

**Q. 칩 프로젝트인데 왜 요즘 동기화 규칙만 만짐?**
A. 칩 크기는 "박스가 받아서 확인·임베딩하는 글의 양"에서 나옴. 같은 글을 3번 받으면 칩 일도 3배로 보임. 그래서 프로토콜이 틀리거나 낭비하면 칩 숫자도 틀림. 다행히 CP29·CP30에서 셌을 때 **글 하나는 박스마다 정확히 한 번만 확인·임베딩됨** (중복은 확인 전에 걸러짐).
