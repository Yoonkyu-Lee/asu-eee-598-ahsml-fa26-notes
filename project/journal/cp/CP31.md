  - 최신 칩(CP14 검증 유닛 + CP28 16×16 FP16 인코더)의 숫자가 한 곳에 없다. `box_server.py`에 박힌 상수(CP19·CP20), `sim_cp19.EncTable`, CP28의 FP16 배율로 흩어져 있다.

- 형식: **목적형**. [디자인] 구조 [구현] 옮기기, `chip.py`, README, 재현 스크립트 [측정] 옮긴 뒤 결론 숫자가 그대로 나오는지.

## 찾은 것 (옮기면서)
- 박스가 칩 시간 표 하나 때문에 `sim_cp19`를 import했고, 그게 `sim_cp16/17`과 `model_cp4/12/18`을 끌고 왔다. `chip.py`로 끊었다.
- **박스의 사진 칩 시간(0.552 s)은 CP20의 8×8 배열 값**이고, 텍스트만 CP28의 16×16 FP16으로 바뀌어 있었다. 숫자를 바꾸는 CP가 아니라서 그대로 두고 `docs/chip.md`의 열린 문제에 적었다. 전력(CP19)도 8×8 기준이다.
- 최신 칩 전체(검증 유닛 + 16×16 FP16 인코더 + SRAM)를 한 번에 계산하는 스크립트는 없었다. 면적 ≥ 9.6 mm²는 CP18 칩 + CP20 한 단계 + CP28 문장으로만 있었다. `chip.py`의 `SPEC`이 처음으로 한 곳에 모았다 (계산이 아니라 출처를 단 값).
- **경로 깊이 실수 (첫 진짜 박스 시험이 잡음)**: `src/demo/`(두 단계)에서 `tests/`·`box/`(한 단계)로 옮기면서 `HERE.parents[1]`이 `project/`가 아니라 저장소 루트를 가리켰다. 시험이 `<저장소>/box/lan.py`를 띄우려다 "box 0 did not start"로 넷 다 멈췄고, 저장소 루트에 `logs/`·`results/`를 만들었다 (지움). `tests/` 셋, `box/lan.py`, `box/run_demo.py`를 `HERE.parent`로 고침. import 검사는 이걸 못 잡는다 (경로는 실행할 때만 쓰임) → 옮긴 뒤에는 진입 스크립트를 실제로 돌려야 한다.
- 칩 모델 docstring의 옛 경로(`results/cp12/…`, `src/…`)를 새 경로로 고침 (코드 경로는 이미 맞았음, 출력 JSON 안의 `setup` 문자열은 결과를 바꾸지 않으려고 그대로).
