# CP32 — 한 화면 다중 클라 데모: 다섯 사용자가 한 화면에서 각자 행세

- 상태: 완료 (2026-11-17)
- 목적형. **[데모] [구현] [측정]**
- 질문: 최신 설계(CP30 S2+KE, ID 먼저 push, 망각, 방, RLN 벌칙, 한도)가 **사용자 눈으로 봤을 때** 약속대로 움직이는가? 한 화면에서 다섯 사용자가 각자 행동할 때, 각 화면에 보이는 것이 프로토콜이 말하는 것과 같은가?
- 왜 이것 (사용자 결정, 2026-11-17): 팀 운영은 프로젝트 끝으로 미룸. 그 목적은 "우리가 정답이라 여기는 프로토콜이 실사용에서 맞는지 체감"뿐이고, 그건 이 PC에서 박스 여럿을 에뮬해 한 화면에 보여주면 먼저 볼 수 있다.
- NORTHSTAR와의 연결: 4번 불변식(서버가 못 읽음, 운영자 없음, 사용성 유지, 스팸이 수집을 못 고갈)을 사람이 보는 화면으로 확인한다. 칩 숫자는 안 바꾼다 (7-2: 칩 시간은 `chip.py` 그대로 표시).

## 시작 전에 찾은 것
- `box/run_demo.py`(README의 "Try it")는 `exchange`를 안 정해서 **최신 동기화(recon)를 안 돈다** (CP21식 설정, push만). CP31까지 아무도 못 봄. → CP32의 데모가 대신하고, `run_demo.py`는 `legacy/`로.

## 사용자 다섯 (무대가 정함)

| 이름 | 박스 | 서브 | 방 R | 역할 |
|---|---|---|---|---|
| Ana | 0 | A, B | 열쇠 있음 | 평범한 작성자, 글을 지움 |
| Ben | 1 | A | 열쇠 있음 | 방에 씀, 투표 |
| Cho | 2 | A, B | 중계만 (열쇠 없음) | 검색, 사진 |
| Dev | 3 | A | 열쇠 있음 | 노트북: 꺼졌다 켜짐 |
| Eve | 4 | A, B | 중계만 | 한도를 어김 → 벌칙 |

서브 B 보유는 `common.community`의 고정값 (0, 2, 4). 방은 `lan.py`처럼 모두가 중계하고 암호를 들은 박스만 읽음.

## 이야기 (15단계, 각 단계에 판정)

| # | 누가 | 무엇 | 판정 (사전 등록) |
|---|---|---|---|
| 1 | Ana | 서브 A에 글 | 다섯 박스 모두 보유, ≤ 10 s |
| 2 | Cho | 그 글을 단어로 검색 | Cho 박스의 검색 결과 1위 안에 (자기 박스가 인코딩·색인) |
| 3 | Ana | 서브 B에 글 | 0, 2, 4 보유 ≤ 10 s, 1·3은 5 s 뒤에도 없음 |
| 4 | Ben | 방 R에 씀 | 0, 1, 3은 읽음. 2, 4는 봉투를 들고 있지만 못 읽음 |
| 5 | Dev | 노트북 닫음 (박스 3 끔) | 프로세스 종료 |
| 6 | Cho | 사진 글 (COCO) | 켜진 네 박스 보유 ≤ 10 s |
| 7 | Ben | 그 사진에 ▲ | 켜진 네 박스에서 점수 1 ≤ 10 s |
| 8 | Dev | 노트북 엶 (박스 3 켬) | 박스가 응답한 뒤 ≤ 30 s 안에 사진 글 + 점수 1 |
| 9 | Ana | 1번 글 지움 | 다섯 박스 모두에서 사라짐 (잊음 목록) ≤ 10 s |
| 10 | Eve | Cho의 사진을 지우려 함 | 거절 (403: 작성자 키 없음), 다섯 박스에 그대로 |
| 11 | 망 | {Ana, Ben} ⟂ {Cho, Dev, Eve}, 양쪽에서 글 | 3 s 뒤 반대쪽에 없음 (쪼개짐이 진짜) |
| 12 | 망 | 다시 붙임 | 두 글이 다섯 박스 모두 ≤ 3·(probe cap + floor 상한) = 180 s |
| 13 | 공격자 | Ben을 잠깐 떼고, Dev 글의 위조본(같은 id, 다른 내용)을 Ben에게 먼저 줌 | Ben이 위조본을 거절 (rej_id +1), 다시 붙인 뒤 진짜를 받음 ≤ 180 s |
| 14 | Eve | 같은 번호로 글 둘 (한도 위반) | 다섯 박스 모두 벌칙 알림 ≤ 10 s, Eve 화면에 "드러남" |
| 15 | Eve | 그 뒤 새 글 | 다른 네 박스에 5 s 뒤에도 없음 |

- **통과 규칙 (사전 등록)**: 15단계 판정이 모두 통과. 두 방식 모두에서: (H) 머리 없이(owner API 직접), (B) 브라우저에서 꼭두각시로 (클라 UI가 직접 입력·클릭). 시간 한도는 위 표. 시간은 이 PC 한 대의 루프백이라 **망 지연이 아님** (측정, 한 PC).
- **시계 설정 (표시)**: 바닥 20–40 s, probe cap 20 s (`sync_check`와 같은 시험 값, 기본값은 600–1800 s / 300 s). 기본값으로는 12·13단계가 최대 수 분. `stage.py --real-timers`로 기본값 실행 가능.
- 기록: `results/demo/story_headless.json`, `results/demo/story_browser.json` (단계별 판정·시간·각 박스 카운터).

## 대안

| | 방식 | 고르면 / 바꿀 조건 |
|---|---|---|
| S1 | 한 페이지에 진짜 박스 UI iframe 다섯 + 무대 서버 + 이야기 | 고름 |
| S2 | 다섯 박스를 한꺼번에 보는 새 클라를 따로 만듦 | UI를 두 벌 유지. iframe으로 못 보여 주는 게 생기면 |
| S3 | 브라우저 창 다섯을 손으로 배치 | 대본·판정 없음 |
| S4 | 머리 없는 시험만 (`sync_check`처럼) | "체감"이 없음 → 사용자 목적 실패. 단 (H)로 같이 돌림 |
| S5 | Playwright로 진짜 마우스 클릭 | 새 의존성. 꼭두각시로 부족하다고 하면 |

| | 행동 경로 | |
|---|---|---|
| A1 | 꼭두각시: 무대 → postMessage → 클라 UI가 입력창을 채우고 버튼을 누름 → 자기 박스 | 브라우저 (B) |
| A2 | 무대가 owner API 직접 | 머리 없이 (H), 끄기·망·공격자 단계 |

## 데모 지름길 (알고리즘 착취 검사, NORTHSTAR 7-6)

| 무엇 | 프로토콜 트래픽인가 | 비용 | 진짜 제품이면 |
|---|---|---|---|
| 클라 UI가 자기 박스를 1 s마다 새로 읽음 (기본 UI는 5 s) | 아님 (자기 박스, 루프백) | 클라당 O(1) | 박스가 클라에게 사건을 밀어 줌 (SSE) |
| 무대가 박스 다섯의 카운터를 2 s마다 읽음 | 아님 (관찰자) | 무대에만 | 없음 (데모 전용) |

## 실행
```
.venv/Scripts/python.exe -W ignore box/stage.py --headless    # (H)  -> results/demo/story_headless.json, 로그 logs/cp32_headless.log
.venv/Scripts/python.exe -W ignore box/stage.py               # (B)  http://127.0.0.1:8620/ 에서 ▶  -> results/demo/story_browser.json
```
(B)는 이 PC의 Chrome에서 두 번 돌림 (두 번째는 화면 스크롤 고친 뒤). `story_browser.json`은 두 번째 것.

- **사전 규칙 판정: 실패** (15단계 모두 통과가 조건, 3단계 실패). 이야기 전체: (H) 21 s, (B) 89 s (꼭두각시 입력 포함).
- 끝 상태 (`held_at_end`): 서브 B 글 `p3`가 **다섯 박스 모두**에. 3단계의 5초 창에서는 박스 1이 아직 안 받았을 뿐, 결국 다 받는다.
- 무대의 끄기·켜기 단추로 다시 켠 박스는 같은 신원(state 폴더)으로 돌아옴. 두 번째 (B)에서 바깥 페이지 스크롤 0.

## 찾은 것
- **H12: 집합 맞추기가 서브를 안 가린다 (CP29부터).**
  - recon 집합에 박스가 가진 모든 id가 들어가고, `_deliver_recon`은 내가 안 가진 서브의 메시지도 받는다. 그래서 세션 한 번이면 서브 B 글이 서브 B 밖 박스로 간다.
  - push는 서브를 지킨다 (`targets()`가 그 서브 보유자만). 새는 곳은 맞추기뿐.
  - 열쇠가 없어 화면엔 안 뜨지만, 받고 증명 검증하고 저장한다. 계수기: 다섯 박스 모두 증명 10개 검증 (서브 B 글과 방 글 포함).
  - 동기화 모델(`sim/sync.py`, `sim/recon.py`)에는 서브가 없어서 층 1–3이 볼 수 없었다. CP29·CP30의 층 4 대본은 서브 A만 썼다.
  - CP21 박스(push만)는 서브 B를 0, 2, 4에만 보냈다 (box/README의 2026-11-01 확인). CP29에서 생긴 회귀다.
  - 비용 (출처: CP16 행동 모델): P-all은 평균 박스 부하의 1/0.78 ≈ 1.28배, 상위 1 % 박스의 1/0.94 ≈ 1.06배. 칩 크기를 정한 상위 1 % 피크에는 작고, 평균 박스·저장·대역에는 크다. CP29·CP30의 동기화 비용(≤ 52.5 KB/박스·일)도 서브 없는 집합 기준이다.
  - 이것이 이 CP의 목적 ("실사용에서 맞는지 체감")이 찾으려던 것이다: 모델은 맞는데, 모델에 없는 축(서브)에서 구현이 설계를 벗어났다.
- `box/run_demo.py`는 최신 동기화를 안 돌았다 (시작 전에 찾음) → `legacy/box/`.
- 꼭두각시의 `scrollIntoView`가 바깥 무대 페이지까지 스크롤해 이야기 패널이 사라졌다 → 클라 자기 창만 스크롤.
