# CP34 — 칩 숫자 빈칸: 16×16 FP16 인코더 직접 매핑 (진행)

- 상태: 진행 (2026-11-17 시작). 목적형 **[측정] [디자인]**
- 질문: CP28의 "FP16 텍스트 = INT8 모델 × 4.0"(사진 탑의 비율을 빌려 옴)이 맞는가? 16×16 · 2 MB 인코더를 16비트 단어로 직접 매핑하면 사이클·에너지가 얼마이고, 그래서 칩 면적 ≥ 9.6 mm²(하한)와 전력을 계산값으로 바꿀 수 있는가?
- 방법: CP12 Timeloop/Accelergy 틀 그대로, 단어 폭만 `WB = 16` (`chip/model/timeloop/arch.yaml`, `timeloop_fp16.py`). 전역 버퍼 포트는 128비트 그대로 (같은 자원: 한 사이클 8단어). MAC은 Accelergy 16비트 정수 MAC = FP16 MAC의 **대리값(하한)**. INT8 기본값(`WB = 8`)은 결과가 바뀌지 않음 (포트 128/8 = 16, 전과 같음).
- 환경: WSL Ubuntu 24.04의 `/opt/tl` (CP12와 같은 설치). CP12처럼 root로 돌려야 Accelergy 설정을 찾음 (일반 사용자로는 Accelergy가 설정을 못 읽고 죽음).

## 첫 결과 (부분, 추정)
40분 시간 제한(중간 보고서 마감)에 16개 중 12개가 끝남. ffn_in·ffn_out의 P = 512·2048 넷이 빠짐. `results/chip/cp34_timeloop_w16_partial.json` (`timeloop_fp16_collect.py`).

| | 16비트 / INT8 (같은 16×16 배열) |
|---|---|
| 사이클 | 1.08–1.60배 |
| 에너지 | 2.07–3.95배 |

- 읽는 법: FP16 MAC이 한 사이클에 하나씩 낼 수 있다면 CP28의 시간 × 4.0은 비관적이고, 16×16보다 작은 배열이 K2·K3를 지킬 수도 있다. 단 MAC이 정수 대리값이라 에너지·면적은 하한이고, 큰 ffn 모양이 빠져서 **아직 설계를 바꾸지 않는다.**
- 다음: 남은 4개, FP16 MAC 모델(Accelergy FP 곱셈기·덧셈기 또는 출처 단가), 그다음 encoder_size로 다시 크기 정하기 → 칩 전체 면적·전력.

## 계획 (첫 결과 뒤, 재판정 전에 적음)
1. 16×16 w16 나머지 4개 (같은 작업 폴더에서 이어서).
2. **8×8 w16** 매핑 (같은 모양·행 4종): "더 작은 배열이 통과할 수 있다"를 확인하려면 필요.
3. FP16 MAC 단가: Aladdin(Accelergy 플러그인, 45 nm)의 3단 파이프라인 FP32 곱셈기·덧셈기 표(500 MHz = 2 ns 줄)에서 출발. 곱셈기는 가수 폭 비율의 제곱 (11/24)², 덧셈기(누산)는 FP32 그대로 (FP16 곱 + FP32 누산). 한 사이클에 하나씩 (파이프라인). 매핑 에너지에서 정수 MAC 몫을 빼고 이 값으로 바꿈. **추정 (공식 표시)**.
4. 크기 다시 정하기: CP28과 **같은 규칙** (검색어 P99 ≤ 50 ms = K2, 8시간 밀린 수집 ≤ 60 min = K3, B = 1)으로 `encoder_size`의 텍스트 시간을 "INT8 × 4.0" 대신 w16 매핑 사이클로. 통과하는 가장 작은 배열을 고름 (8×8 / 16×16).
5. 칩 전체: 인코더 면적(w16 ART + FP16 MAC) + 2 MB SRAM + 검증 유닛 2.12 mm² + 나머지는 rollup 그대로 → 면적, 평소 하루·폭주 전력. `chip/model/chip.py`의 SPEC을 출처 값에서 계산 값으로.
- 바꿀 조건 (미리): 8×8 w16이 K2·K3를 둘 다 지키면 8×8로 내림 (FP16 MAC 단가에 ±50 % 민감도를 같이 보고, 판정이 뒤집히면 "불확실"로 표시하고 16×16 유지).
