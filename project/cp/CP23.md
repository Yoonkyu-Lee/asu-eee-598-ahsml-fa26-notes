# CP23 — 무게 한도(T1)의 구현: 회로·검증 비용과 남는 구멍

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP22.md](CP22.md) (한계 첫 줄 "T1의 구현을 정하지 않았다"). 증명 검증 비용 모델은 [CP14.md](CP14.md) (O3 고정 기저 표), 공개 입력 셈법은 [CP17.md](CP17.md) W3. 그림은 아키텍처 보드(L1 "맞는 스팸")와 체크포인트 보드.

## 왜 이 CP인가
- CP22는 T1 + T2 + T3을 골랐다. 그런데 T1(무게 한도)은 모델에서 **무게를 실수로** 셌다. 실제 RLN은 메시지 하나가 메시지 번호 하나를 쓴다. "사진 글은 5.4단위"를 증명으로 강제하는 방법을 정하지 않았다.
- 방법에 따라 비용이 다른 곳에 생긴다: 공개 입력(박스의 검증 시간과 DRAM 표), 회로 크기(사용자 기기의 증명 생성), 반올림(정직한 거부와 공격자 몫), 그리고 벌칙(겹쳐 쓰면 비밀이 드러나는가).
- 같이 닫을 CP22의 구멍: 공격자가 1시간 창의 **시작에 몰아 보내는 버스트**는 돌리지 않았다.
- 형식: **목적형**. [디자인] (구현 대안, 벌칙 성립 여부) [구현] (arkworks RLN-n 회로, `sim_cp23.py`) [측정] (제약 수·증명 생성·검증 시간, CPU 예비 측정).
- 답할 질문:
  - T1을 어떤 증명 구조로 강제하면 규칙 S2를 지키면서 박스·사용자 비용이 가장 적은가?
  - 그 구조에서 남는 공격(K_crit_old)은 CP22의 2,823에서 얼마나 바뀌나? 버스트에도 버티나?

## 그림 (설계, 결과 전)
```
 글 (토큰 수, 사진) ── 무게 w (단위 = 256토큰 텍스트 인코딩, 사진 +4.43) ──┐
                                                                            ▼
 ┌ I1(q) 번호 n개: n = ⌈w·q⌉개의 연속 메시지 번호 k..k+n−1 < 한도를 회로에서 확인,
 │        번호마다 (몫 y_i, nullifier_i) 공개 → 공개 입력 3 + 2n, n마다 검증키 하나
 ├ I1p    I1(1)을 회로 하나로: 항상 n_max칸, 안 쓰는 칸은 꺼짐 표시 → 공개 입력 3 + 2·n_max 고정
 ├ I2     2의 거듭제곱 블록: 자기 블록 + 조상 태그 → 공개 입력 3 + 2·(레벨 수)
 ├ I3     크기 등급: 등급마다 따로 센 한도, 등급은 외부 nullifier H(epoch, 등급)에 → 공개 입력 그대로 (3 + 2)
 └ I4     글을 n개 메시지로 쪼갬: 증명 n개
                                                                            ▼
 박스: 증명 먼저 (O-b) → 공개 입력 MSM (O3 표, DRAM) + 페어링 → nullifier 표에 n개 → 복호화 → 토큰 수·사진으로 w 확인
       (w를 낮춰 신고한 글은 버림: 박스는 평문을 보므로 w는 회로 밖에서 확인 가능)
```
공개 입력의 뼈대는 CP6 bench와 같은 5개(뿌리, 외부 nullifier, 신호 x, 몫 y, nullifier)이고, 투표의 글별 nullifier(W3)는 무게와 상관없어 뺀다.

## 대안 (결과를 보기 전에 적음)
| | 구조 | 공개 입력 | 반올림 | 벌칙 | 바뀌는 곳 |
|---|---|---|---|---|---|
| I0 | CP22 모델 (연속 무게) | – | 없음 | – | 기준선, 구현 불가 |
| I1(q) | 번호 n = ⌈w·q⌉개, q ∈ {1, 2, 4} | 3 + 2n | 1/q단위로 올림 | 번호마다 성립 | 회로 n_max개, 검증키·O3 표 n_max개 |
| I1p | I1(1)을 회로 하나로 | 3 + 2·n_max (모든 메시지) | 1단위 | 성립 | 회로 하나, 모든 메시지 검증이 비싸짐 |
| I2 | 2의 거듭제곱 정렬 블록 | 3 + 2·(레벨) | 2의 거듭제곱 | **설계에서 확인** (아래) | 회로 레벨마다 |
| I3a | 등급 2개 (텍스트 / 사진 글), 등급별 개수 한도 | 그대로 | 등급 최댓값 | 성립 | 외부 nullifier에 등급 |
| I3b | 등급 3개 (짧은 ≤ 64토큰 / 긴 텍스트 / 사진 글) | 그대로 | 등급 최댓값 | 성립 | 같음 |
| I4 | 글을 n개 메시지로 (I1(1)과 같은 반올림) | 3 + 2, 증명 n개 | 1단위 | 성립 | 메시지·증명 n배 |

- **I2는 설계에서 먼저 따진다.** 블록 둘이 겹치는 것은 하나가 다른 것을 품을 때뿐이다. 겹침을 잡으려면 작은 블록이 조상 레벨의 태그를 내야 한다. 그런데 태그에 RLN 몫을 붙이면 **겹치지 않는 형제 블록 둘도 같은 조상 선에 점 두 개**를 찍어 정직한 사용자의 비밀이 드러난다. 몫을 떼면 겹친 사용은 거부만 되고 벌칙이 없다 (박스마다 먼저 본 것이 달라 일부가 퍼짐). → I2는 계산 없이 **탈락** (벌칙이 성립하지 않음). 표에는 공개 입력 수만 참고로 적는다.
- I3은 회로를 바꾸지 않는다. 대신 공격자는 등급마다 한도를 다 쓴다 (텍스트 등급은 256토큰, 사진 등급은 256토큰 + 사진).

## 측정·계산
- **M-a 회로 (측정, 세컨컴 CPU 단일 스레드, 예비 측정)**: arkworks 0.5로 RLN-n 회로를 짠다. Poseidon (t = 3, α = 5, 전체 라운드 8, 부분 라운드 57, BN254) 가젯을 손으로 쓰고, 상수는 시드로 뽑은 값이다 (보안용 상수가 아니지만 제약 수는 같은 구조). 회로: 신원 약속 H(a0, 한도) → 깊이 20 Merkle 경로 → 번호 i마다 a1 = H(H(a0, 외부 nullifier), k+i), y_i = a0 + a1·x, nullifier_i = H(a1, 0) → k + n ≤ 한도 범위 검사 (16비트). n ∈ {1, 2, 3, 4, 6, 8, 12, 16, 24}마다 제약 수, 증명 생성 시간, 검증 시간 (준비된 검증키), 증명 + 공개 입력 바이트.
- **M-b 칩 (추정)**: 검증 비용 = CP14 단건 × (1 + 352·Δ/26,785) (Δ = 공개 입력 증가, CP17 셈). O3 표 = 공개 입력 기저 하나당 (2⁸ − 1)·32·64 B = 522 KB (CP14 w = 8). 폭주 요구: 100 Mbps에서 메시지가 공개 입력 하나당 32 B씩 커진다 → 초당 개수 요구가 줄어든다 (CP13의 12,207/s는 1 KB 메시지).
- **M-c 박스 모델 (추정)**: `sim_cp22`를 그대로 쓰고 구현마다 바뀌는 것만 바꾼다: 정직한 메시지 무게(반올림·등급), 한도(정직한 거부 ≤ 10⁻³로 다시 고름), 공격자의 메시지 묶음(등급마다 한도를 다 씀). T2 + T3은 켠 채로.
- **버스트 (추정)**: 고른 구현에서 공격자가 창마다 한도를 창의 시작 1초 안에 다 보냄 (새 그룹 1시간 창, 오래된 그룹 10분 창).

## 공격 전략 (계획 추가, 박스 모델을 돌리기 전에 적음)
- **CP22의 공격 가정에 구멍이 있을 수 있다** (셈, 추정). CP22의 공격자는 언제나 "256토큰 + 사진" 글만 보냈다. 그런데 T2에서는 사진 인코딩이 실시간 텍스트 뒤로 가므로, 실시간 줄에 들어가는 것은 그 글의 텍스트 몫(1단위)뿐이다. 같은 무게 한도 W로 **256토큰 텍스트만** 보내면 실시간 줄의 일이 W단위로, 사진 글보다 약 5.4배다.
  - 오래된 그룹: W = 6단위/10분이면 신원 하나가 실시간 줄에 6 × 0.124 s / 600 s = 1.24 ms/s → K_crit_old가 2,823이 아니라 수백일 수 있다.
  - 새 그룹: 5단위/1시간 × 10⁴ 신원 = 1.72 s/s로 인코더(1 s/s)를 넘는다 → CP22의 S2 통과가 뒤집힐 수 있다.
- 그래서 모든 구현에서 공격자는 **K_crit가 가장 낮아지는 전략**을 쓴다고 본다:
  - S-p: 256토큰 + 사진 (CP22).
  - S-t: 256토큰 텍스트만.
  - S-c (I3만): 등급마다 한도를 다 씀 (짧은 등급은 64토큰, 긴 등급은 256토큰, 사진 등급은 256토큰 + 사진).
  - 정수 번호(I1, I3)에서는 창마다 보낼 수 있는 글 수가 정수다 (남은 단위는 256토큰 텍스트로 채움).
- **S-t가 모든 구현에서 S2를 깨면 고칠 손잡이** (바꾸는 곳이 적은 순):
  - F1 **실시간 텍스트는 앞 128토큰만** 인코딩 (박스만). 근거: CP20에서 MiniLM 128토큰 자르기의 Hit@10이 256토큰보다 낮지 않았다 (0.968 vs 0.943). 무게도 인코딩하는 만큼만 센다.
  - F2 **번호 순 우선**: 회로가 "이 메시지가 이번 창의 앞 m단위 안인가" 1비트를 공개하고 (공개 입력 +1), 박스는 그룹마다 앞 번호를 먼저 처리한다. m은 정직한 메시지 중 m단위 밖으로 밀리는 몫이 5×10⁻³ 이하인 가장 작은 값 (K1이 P99라 1% 꼬리의 절반까지). 드러나는 것: 메시지 하나가 그 창의 "많이 쓰는 사람"의 뒤쪽 메시지인지 1비트.
  - F1 + F2.
- 판정은 아래 S3 그대로, 손잡이를 고를 때는 바꾸는 곳이 적은 순 (없음 < F1 < F2 < F1 + F2)을 구현 순서보다 먼저 본다.
- 뒤집을 조건: 손잡이를 다 써도 S-t에서 S2가 깨지면 **CP22 판정을 정정**한다 ("새 신원 1% 공격은 텍스트 스팸으로 깨진다"). 그때 필요한 신원 비용(새 그룹 한도를 얼마로 묶어야 하는지)을 숫자로 적는다.
- 정정에 쓸 숫자도 같이 잰다 (스모크 실행에서 CP22 기준선이 그대로 재현되고 S-t에서 새 그룹이 끝나지 않는 것을 본 뒤, 전체 실행 전에 추가): 모든 실행에서 새 그룹이 버티는 신원 수 **K_crit_new**, 그리고 고른 것(없으면 I1(1), 마지막 손잡이 단계)의 s_new 1%·20% 민감도.

## 결과를 보고 추가한 대안 I5 (첫 전체 실행 뒤, 그 결과는 아래 결과 절)
- 첫 전체 실행에서 I0–I4 × 손잡이 4단계가 모두 S-t에 졌다. 원인을 보니 **사진 글이 5.4단위라서 새 그룹 한도 W가 사진 하나보다 커야 하고, 그 W를 텍스트 스팸이 실시간 줄에 다 쓴다.** T2에서 사진은 실시간 줄 밖인데 같은 예산을 나눠 쓰는 것이 문제다.
- **I5 텍스트 단위 + 사진 개수**: 번호 공간 둘. 텍스트 몫은 1/4단위 번호 (q = 4, 모든 메시지), 사진은 따로 센 개수 한도 (사진 글만 번호 하나 더). 공개 입력 3 + 2·(텍스트 번호 + 사진 0/1), 검증키는 (텍스트 번호 수 × 사진 유무)마다. 한도는 텍스트 W를 먼저 가장 작게, 그다음 사진 L을 가장 작게 (정직한 거부는 둘을 더한 위쪽 경계).
- 같은 규칙 S3으로 손잡이 없음·F1 두 단계에서 돌리고, S3 순서에서는 I1q4 다음·I4 앞에 둔다 (회로 여러 개). 결과를 보고 만든 대안이라 판정에 쓸 때 그렇게 표시한다.

## 판정 규칙 S3 (결과를 보기 전에 적음)
1. **벌칙**: 한도를 넘겨 쓰면 언제나 비밀이 드러나야 한다. 아니면 탈락 (I2).
2. **S2 그대로**: 정직한 거부 ≤ 10⁻³, 새 그룹 신원 10⁴개 공격 중 두 그룹 새 글 P99 ≤ 4.64 s, 검색어 P99 ≤ 50 ms. 한도는 구현마다 다시 고른다 (CP22의 `pick_limits`와 같은 방식).
3. **폭주**: 공격자가 가장 비싼 회로(바이트당 검증 비용이 가장 큰 것)로 틀린 증명을 100 Mbps로 보낼 때, 6×6 검증 유닛의 최저 용량(13,429/s × 1/검증 비용 배수)이 요구 개수 이상. 아니면 검증 유닛을 다시 정해야 하는 것으로 적는다.
4. 1–3을 지키는 것 중 **바꾸는 곳이 가장 적은 것**: I3 (회로 그대로) < I1p (회로 하나) < I1(q) (회로 여러 개, 작은 q 먼저) < I4. 단 고른 것의 K_crit_old가 같은 규칙을 지키는 다른 구현의 가장 큰 값의 절반 미만이면 그다음 것을 고른다 (남는 공격을 반 넘게 키우면서까지 단순함을 사지 않음).
5. 고른 것에 버스트를 돌린다. S2-2가 깨지면 새 그룹 창을 10분으로 줄인 한도로 다시 보고, 그래도 깨지면 한계로 적는다.
- 뒤집을 조건: 고른 구현의 사용자 쪽 증명 생성이 CPU에서 n = 1 대비 3배를 넘으면 (폰에서 수 초가 됨, 추정) 그다음 것과 비교해 적는다. O3 표 합이 64 MB를 넘으면 (박스 DRAM의 큰 몫, 추정) 창 w = 4 표(61 KB/기저)로 바꾼 검증 비용을 다시 셈.

## 실행
```
cargo run --release --manifest-path src/crypto_bench/Cargo.toml --bin cp23 -- results/cp23/rln_n.json   # 약 2분
.venv/Scripts/python.exe src/sim_cp23.py          # 세컨컴 약 2시간 13분: 구현 6 × 손잡이 4 × 전략 2 (K_ref + K_crit 둘), 규칙 S3, s_new 민감도
.venv/Scripts/python.exe src/sim_cp23.py --i5     # 약 9분: I5 (없음, F1) 뒤 규칙 S3 다시
.venv/Scripts/python.exe src/sim_cp23.py --need   # 약 3분: 새 그룹 한도를 얼마로 묶으면 S-t 10⁴을 버티나
```

## 해석
1. **CP22를 정정한다.** T2(사진 뒤로)가 공격자의 최선을 바꿨다: 사진 대신 텍스트. CP22는 가장 비싼 글을 최악으로 가정했지만, 우선순위가 생긴 뒤에는 "가장 비싼"이 아니라 "실시간 줄에 가장 많이 들어가는" 글이 최악이다. 남는 공격 2,823 → 541, 1% 새 신원 → 0.5%.
2. **무게 한도의 구현은 비용 문제가 아니었다.** 어느 구조든 검증 유닛을 바꾸지 않고 (폭주 바이트당 ≤ 1.00), 사용자 증명은 최대 1.2–2.8배. 문제는 **예산을 무엇으로 세느냐**였다. 실시간 줄에 들어가는 텍스트와 뒤로 가는 사진을 한 예산에 넣으면 사진 때문에 커진 예산을 텍스트 스팸이 쓴다 → I5(예산 둘)가 남는 공격을 541 → 2,842로.
3. **F1(실시간 128토큰)은 거의 공짜 이득이다.** 박스만 바꾸고, CP20에서 품질이 떨어지지 않았고, 정직한 부하도 줄어 검색어 P99가 31 → 20 ms. 공격 쪽에서는 S-p 공격의 K_crit_old를 2,823 → 7,540으로. 다만 텍스트 스팸에는 조금만 (541 → 664).
4. **익명 한도만으로는 정직한 새 사용자와 새 신원 스패머를 가를 수 없다.** 한도를 정직한 사람의 필요(거부 ≤ 10⁻³)에 맞추면, K개의 스패머가 받는 몫은 K × 정직한 사람의 필요다. 10⁴ × (새 사용자 한 시간의 텍스트 필요) > 인코더 용량이면 어떤 한도도 못 지킨다. 남는 길은 s_new가 작다는 근거(출처)나, 신원 하나의 비용(NORTHSTAR 5)이다.

## 한계
- s_new(새 사용자 몫)와 새 사용자의 쓰기 분포의 출처가 없다 (CP22와 같음). 이번 결론이 이 값에 달려 있다.
- I5는 첫 전체 실행 결과를 보고 만든 대안이다 (S3 순서에서 I1(4) 다음). F2와 함께는 돌리지 않았다 (F2가 아무 구현에서도 듣지 않아서).
- I5의 정직한 거부는 텍스트 거부 + 사진 거부를 더한 위쪽 경계.
- F2의 등급 구현(I3)은 등급마다 같은 m을 쓴다. 정직한 늦은 몫은 등급별 Poisson으로 셈.
- 공격 전략은 S-p·S-t·S-c 셋. 짧은 텍스트를 많이 보내는 전략은 I0에서는 무게가 같아 같은 일이고, 정수 번호에서는 올림 때문에 공격자에게 손해라 돌리지 않았다.
- 회로의 Poseidon 상수는 시드로 뽑은 대역 (제약 수만 맞음). 검증 시간은 CPU 가변 기저 MSM (칩 O3와 다름). F2의 공개 입력 +1은 CPU에서 재지 않음.
- 증명 측정은 예비 측정 (세컨컴, 조건 확인 안 됨).
- 버스트(창 시작에 몰아 보내기)는 고른 구현이 없어 돌리지 않았다.
- 박스 한 대 모델, P-all 물량 (CP19–CP22와 같음).

## 계획에서 달라진 점
- 박스 모델을 돌리기 전에 공격 전략(S-t, S-c)과 손잡이 F1·F2를 계획에 추가 (CP22 공격 가정의 구멍을 셈으로 찾음).
- 스모크 실행 뒤 K_crit_new와 s_new 민감도를 추가.
- 첫 전체 실행 뒤 I5를 추가 (결과를 보고 만든 대안, 그렇게 표시). 새 그룹 한도별 필요 계산(`--need`)을 추가 (계획의 "필요한 신원 비용을 숫자로").
- 버스트는 돌리지 않음 (고른 것이 없음).
