# CP7 — 증명 검증 가속기의 첫 비용 모델

2026-10-31 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 그림은 체크포인트 보드 아티팩트.

## 왜 이 CP인가
CP6에서 박스의 크기를 정하는 일은 **스팸 폭주 때의 익명 증명 검증**이었다.
- 100 Mbps 폭주(초당 1.2만 건)를 2 W 박스로 견디려면 검증당 **0.16 mJ 이하**가 필요하다 (추정).
- CPU로는 24–181 W가 든다.

이번 CP는 이 질문에 답한다. 전용 하드웨어라면 검증당 몇 mJ인가? 곱셈기는 몇 개, 몇 W가 필요한가? 그 차이가 CP4의 인코더 모델처럼 숫자로 서는가?

## 환경·의존성 (CP6 표에 추가)

| 무엇을 | 왜 | 기대 | 이후 CP 의존성 |
|---|---|---|---|
| `crypto_bench prims` 모드 | 페어링을 이루는 연산(Fq·Fq2·Fq12 곱, Miller loop, 최종 지수승, G1 스칼라 곱)을 따로 잼 → 연산 수 모델을 CPU와 대조 | | CP8 RTL 검증 |
| `crypto_bench` 기능 `fast` (`ark-ff/asm`) + `RUSTFLAGS="-C target-cpu=native"`, 빌드 폴더 `target-fast/` (git 제외) | CPU 기준선을 최선의 소프트웨어에 가깝게 (CP5 교훈: 소프트웨어부터 짜낸다) | Groth16 검증 P코어 1.38 → 1.22 ms (12%) | |

측정 조건은 CP6과 같다.

## 방법
1. **[측정] CPU** (`src/bench_cp7.py` → `results/cp7/cp7_cpu.json`):
   - 기본 빌드와 asm 빌드 각각, P코어 0과 저전력 E코어 20에서 연산별 시간을 잰다.
   - 배치 검증 10초 루프의 패키지 에너지를 잰다.
2. **[조사] 연산 수**:
   - 254비트 BN 곡선의 optimal ate 페어링 (출처: [herumi/ate-pairing](https://github.com/herumi/ate-pairing/) README, Aranha 외 EUROCRYPT 2011을 손본 값):
     - Miller loop 6785 mu + 3022 r
     - 최종 지수승 3526 mu + 1932 r
     - mu = 256×256비트 곱(축약 없음), r = 512→256비트 몽고메리 축약
   - G1 공식 (Explicit-Formulas Database): Jacobian 2배(a = 0) 2M + 5S, 혼합 덧셈 7M + 4S.
   - 이 표는 Fp254BNb 곡선 기준이다. Semaphore·RLN의 BN254는 루프 길이가 비슷해 ±20%로 본다 (추정).
3. **[디자인] 검증 유닛 비용 모델** (`src/model_cp7.py` → `results/cp7/cp7_model.json`):
   - 단가: 수업 L7 Horowitz 표 (45 nm, CP4와 같은 표). 32비트 곱 3.1 pJ, 32비트 덧셈 0.1 pJ, 8 KB SRAM 32비트 읽기 5 pJ.
   - 254비트 = 32비트 워드 8개:
     - mu = 64번 곱 + 128번 덧셈 = 211 pJ
     - r = 72번 곱 + 144번 덧셈 = 238 pJ
     - Fp 곱 1번 ≈ 0.45 nJ (추정)
   - Fp 덧셈은 곱 1번당 2번 (가정).
   - 피연산자 이동: 연산마다 3 × 8워드를 8 KB SRAM에서 읽고 씀. 상한으로 넣고, 계산만 한 경우와 범위로 낸다.
   - Groth16 검증 1건 = Miller loop 3 + 최종 지수승 1 + 공개 입력 5개의 MSM.
   - 배치 64개의 증명당 = Miller loop 1 + 128비트 가중치 스칼라 곱 + MSM 몫 + (Miller loop 2 + 최종 지수승) / 64.
   - 유닛 = 완전 파이프라인 Fp 곱셈기 (500 MHz, 사이클당 1번, 가정).
   - 동적 에너지만 (CP4와 같음).

## 결과

### 1. CPU (측정, 단일 코어, µs)
| | P코어 기본 | P코어 asm | E코어 기본 | E코어 asm |
|---|---|---|---|---|
| Fq 곱 (ns) | 15.7 | 14.8 | 39.1 | 38.4 |
| Miller loop 1개 | 261 | 227 | 648 | 480 |
| 최종 지수승 | 374 | 322 | 997 | 640 |
| Groth16 검증 | 1,376 | **1,218** | 3,483 | **2,645** |
| 배치 64 증명당 | 349 | **316** | 888 | **709** |

배치 검증의 패키지 에너지 (측정, 기본 빌드):

| | 칩 전체 | 활성 |
|---|---|---|
| P코어 | 6.1 mJ/증명 | 4.0 mJ/증명 |
| E코어 | 8.5 mJ/증명 | 2.1 mJ/증명 |

CP6이 시간 비율로 추정한 활성 값(3.8 / 2.0 mJ)과 맞는다.

**CPU와 연산 수 모델 대조** (P코어 asm, CPU 시간 ÷ Fq 곱 시간):
- Miller loop 1개 = Fq 곱 1.54만 번어치. 모델은 0.49만–0.98만 번이므로 CPU가 1.6–3.1배를 더 쓴다 (덧셈·함수 호출·축약 방식).
- 최종 지수승 = 2.18만 번어치. 모델은 0.27만–0.55만 번이므로 4–8배다.
- 출처의 최적화 라이브러리(herumi, Haswell)는 Miller loop 0.71M, 최종 지수승 0.46M 사이클이다. arkworks의 최종 지수승이 특히 덜 최적화되어 있다.
- CPU 기준선은 최선의 소프트웨어로 약 2배 더 빨라질 여지가 있다 (추정). 아래 비교는 이 여지를 감안해도 결론이 같다.

### 2. 검증 유닛 (추정, 45 nm, 동적만)
| | Fp 곱 환산 | µJ (계산만) | µJ (8 KB SRAM 이동 포함) |
|---|---|---|---|
| Groth16 검증 1건 | 2.2만 | 9.8 | **17.7** |
| 배치 64의 증명당 | 0.66만 | 3.0 | **5.3** |

증명당 에너지 비교:

| | mJ/증명 | 2 W 예산(100 Mbps, 0.16 mJ) 대비 |
|---|---|---|
| P코어 단건 (측정, 활성) | 14.9 | 91배 초과 |
| E코어 배치 (측정, 활성 / 칩 전체) | 2.1 / 8.5 | 13 / 52배 초과 |
| **유닛 단건 (추정)** | **0.018** | **9배 여유** |
| **유닛 배치 (추정)** | **0.0053** | **31배 여유** |

**폭주 크기 맞추기** (500 MHz 파이프라인 Fp 곱셈기 1개 기준):

| 링크 | 초당 Fp 곱 (단건 / 배치) | 필요한 곱셈기 | W (단건 / 배치) |
|---|---|---|---|
| 10 Mbps | 2,700만 / 810만 | 0.05 / 0.02개 | 0.02 / 0.007 W |
| 100 Mbps | 2.7억 / 0.81억 | **0.54 / 0.16개** | **0.22 / 0.07 W** |

출처와 대조: 제작된 페어링 ASIC 하나가 페어링 1번에 0.185 ms다 (Awano 외, [IEICE](https://ken.ieice.org/ken/paper/202104127C35/eng/)). 배치에서 증명당 필요한 계산(Miller loop 약 1번, 페어링의 약 0.6배)으로 환산하면 100 Mbps 폭주에 그런 칩 1–2개다. 우리 모델의 "곱셈기 1개 이하"와 같은 자릿수다.

## 해석
1. **검증은 하드웨어가 압도적으로 이기는 자리다 (추정).**
   - 검증 유닛은 증명당 0.005–0.018 mJ다. 같은 방식의 CPU 측정값(배치 2.1 mJ, 단건 14.9 mJ 활성)보다 **약 400–800배** 작다.
   - CPU는 254비트 곱 하나에 수십 개 명령과 그 오버헤드를 쓴다. 유닛은 곱셈기 하나에서 끝난다 (L7 Horowitz 표의 "명령 오버헤드" 논리와 같음).
   - CPU 소프트웨어가 2배 빨라져도, 공정 차이(45 nm 모델 vs Intel 7/4 실측)를 감안해도 자릿수는 그대로다.
2. **필요한 하드웨어가 아주 작다.** 100 Mbps 폭주도 500 MHz Fp 곱셈기 1개 이하, 0.07–0.22 W면 된다 (2 W 예산의 4–11%). 전 CP의 인코더(16×16 배열 + 2 MB SRAM)에 비하면 작은 부속이다.
3. 그래서 **P와 M이 선다**:
   - W: 익명 스팸 방지 증명 검증, 폭주 때 메시지 전부.
   - P: 범용 CPU는 큰 정수 곱에 명령 오버헤드를 내고, 엣지 NPU는 아예 못 한다 (CP6).
   - M: 박스 칩 안의 작은 Fp 곱셈 유닛 + 배치 검증.
   - 남은 설계 질문은 두 가지다. (a) 전용 곱셈기를 둘 것인가, 인코더의 INT8 배열로 큰 정수 곱을 할 것인가 (254비트 = 8비트 조각 32개, 조각 곱 1,024개 = 16×16 배열 4번). (b) 곱셈기의 실제 면적·에너지.
4. 폭주가 싸게 막히면 다음 병목은 네트워크 수신과 메시지 해시·중복 확인(nullifier 조회)일 수 있다. 아직 재지 않았다.

## 한계
- 모든 유닛 숫자는 45 nm Horowitz 단가와 schoolbook 32비트 조각 곱으로 쌓은 추정이다.
- 실제 곱셈기(Karatsuba, 64비트 조각, 파이프라인 레지스터)의 면적·에너지는 RTL 합성으로 확인해야 한다.
- Fp 덧셈 비율(곱 1번당 2번)과 SRAM 이동은 가정이다. SRAM 이동은 상한으로 넣었다 (레지스터 파일이면 더 작음).
- 연산 수는 Fp254BNb 곡선 기준 출처 값이다. BN254(SNARK 곡선)는 ±20%로 봤다.
- 제어, 누설, 온칩 연결은 뺐다. 증명 형식 확인(점이 곡선 위에 있는지, 부분군 검사)도 뺐다. G2 부분군 검사는 페어링에 견줄 만큼 비쌀 수 있다. 다음 CP에서 연산 수에 넣어야 한다.
- 폭주 크기(링크, 메시지 크기)는 CP6과 같은 가정이다.
