# CP27 — 알고리즘 착취 감사: 박스가 하는 일마다 알고리즘으로 더 줄일 수 있는가

2026-11-07 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP26.md](CP26.md) (다음 CP 줄).

## 왜 이 CP인가
- NORTHSTAR 7의 6번 (2026-11-07 추가): 하드웨어로 줄이려는 일을 알고리즘·프로토콜로 착취할 수 있는 만큼 착취했는가? CP26에서 데모의 폴링을 걷어 내며 이 원칙을 세웠다. 지금까지의 칩 결론(CP12–CP23)이 이 시험을 통과하는지 아직 보지 않았다.
- 칩의 몫은 CP17 결론대로 평소가 아니라 (a) 폭주 (b) 검색 지연 (c) 오프라인 뒤 밀린 수집 (d) 유휴 전력이다. 평소 가장 바쁜 박스의 인코더는 하루 0.7초 일한다. 그래서 (a)–(c)에서 박스가 하는 일이 알고리즘상 꼭 필요한지가 칩 주장의 바탕이다.
- 사용자 계획 (2026-11-07): 준비될 때까지 CP를 진행한 뒤, 팀원 컴퓨터로 박스를 에뮬레이트해 커뮤니티를 운영해 본다. 전제는 둘이다. 팀원은 언제든 참여를 중단할 수 있다. 사용자의 미니 PC(이 세컨컴, 원래는 노드 박스)가 상시 켜져 있다. 이 CP에서 박스 설계가 바뀌면 그 운영 전에 데모에 넣는다.
- 형식: **목적형**. [조사·디자인] 박스가 하는 일 감사표 [구현·측정] A: push 중복 (교류 모델) [측정·모델] B: 모두가 모든 글을 인코딩하는 것.
- 답할 질문:
  - 박스가 하는 일 중 알고리즘으로 더 줄일 수 있는데 아직 안 줄인 것은?
  - A: 같은 봉투가 이웃마다 한 부씩 오는 것(꼭 받을 바이트의 약 5.7배)을 완전성·신선도를 지키며 줄일 수 있는가? 폭주 때는 얼마나 중요한가?
  - B: 박스마다 모든 글을 인코딩하지 않고, 작성자가 붙인 임베딩을 쓰면서 검색 결과에 오른 것만 검증해도 되는가? 그러면 인코더 칩의 (a)·(c) 몫은 얼마나 남는가?

## 그림 (설계, 결과 전)
박스 한 대가 메시지 하나에 하는 일 (CP24 O-b 순서), 그리고 감사 질문:
```
 받기 ─ 봉투가 이웃마다 한 부 (D = 6) ──────────────── A: 한 부만 받을 수 있나? (먼저 ID만, 없는 것만 요청)
 ① 표 찾기 (중복 버림)                                  이미 O(1) (CP19 O-b)
 ② 증명 검증 (검증 유닛)                                 이미 묶음 64 + 무작위 가중치 + 실패 시 이분 (CP14). 버릴 것을 먼저 버림 (O-b)
 ③ Ed25519, ④ nullifier, ⑤ 복호화                        싸다 (CP1: 0.5%)
 ⑥ 인코딩 (MiniLM 텍스트, CLIP 사진) ─ 모든 박스가 모든 글 ── B: 작성자가 한 번 만든 임베딩을 쓰고, 검색에 오른 것만 다시 계산해 검증?
 ⑦ 색인에 넣기                                           싸다
 검색: 검색어 인코딩 + 정확 검색 (평탄)                    CP1: 싸다. ANN은 색인이 커질 때 (보관과 메모리 CP)
```
B의 흐름 (대안 E3):
```
 작성자: 글 → 자기 기기에서 임베딩 e_a (INT8 384바이트, 사진은 CLIP 512) → 암호화된 본문 안에 함께
 박스:   복호화 → e_a로 곧바로 색인 (검증 안 됨 표시) ── 쉴 때 뒤에서 차례로 검증 (다시 계산 e_b, cos(e_a, e_b) ≥ τ)
 검색:   검색어 인코딩 → e_a로 순위 → 위 k개 중 검증 안 된 것만 지금 검증 → 틀린 것은 버리고 다음 후보로 → 검증된 k개만 보임
 폭주:   스팸은 검색에 오르지 않으면 인코딩되지 않는다. 오르면 그때 한 번 (그리고 버려짐)
```

## 대안 (결과를 보기 전에 적음)
**A: push 중복** (CP26 교류 모델 `sim.exchange`에 넣음)

| | 무엇 | 예상 |
|---|---|---|
| P0 | 이웃 D = 6에게 봉투를 바로 (지금) | 중복 ≈ 5.7배 |
| P1 | D = 3 | 중복 ≈ 2배, 손실·꺼짐에 덜 튼튼 |
| P2 | 이웃 6에게 ID만 먼저 (IHAVE), 없는 이웃만 요청 (IWANT) | 중복 ≈ 0, 홉마다 왕복 하나 더 |
| P3 | 이웃 2에게 봉투 + 나머지 4에게 ID (Plumtree 꼴), ID만 왔는데 0.5 s 안에 봉투가 없으면 요청 | 중복 ≈ 1배, 지연 거의 그대로 |
| P4 | 봉투를 받자마자 이웃에게 "보내지 마" (IDONTWANT) | 봉투 1 KB는 전송이 0.4 ms라 알림이 늦음 → 효과 작음 |

**B: 인코딩**

| | 무엇 | 검증 |
|---|---|---|
| E0 | 박스가 모든 글을 받자마자 인코딩 (지금, CP22 우선순위 줄) | 할 필요 없음 |
| E2 | 작성자 임베딩으로 색인, 검색 위 k개 중 검증 안 된 것만 그때 검증 | 검색 때만 |
| E3 | E2 + 쉴 때 뒤에서 차례로 검증 (최근 글 먼저) | 쉴 때 + 검색 때 |
- 검증 = 박스가 다시 계산해 cos(e_a, e_b) ≥ τ. 기기마다 계산이 조금 다르므로 τ < 1. τ는 정직한 작성자를 거의 다 통과시키는 값으로 정한다 (아래 B1).
- 틀린 임베딩은 그 글을 버린다. 익명 신원이라 작성자를 묶어 벌할 수는 없다 (RLN 위반이 아님). 그래서 한 번 속이는 데 박스 쪽 비용은 검증 한 번이다.
- 쓰지 않는 것: 먼저 검증한 박스의 서명을 믿기. 운영자 비슷한 신뢰가 생긴다 (NORTHSTAR 4).

## 판정 규칙 (결과를 보기 전에 적음)
- **감사표**: 박스가 하는 일마다 (i) 이미 착취함 (근거 CP) (ii) 더 줄일 후보 (iii) 본래 필요 중 하나로 적는다.
- **A**: CP26 장면 셋, n = 100·1000, 손실 10⁻³·10⁻². 완전성(빠짐 ≤ 10⁻⁴)과 켜져 있을 때 도착 P99 ≤ 2 s를 지키는 것 중, 박스당 받는 총 바이트(꼭 받을 것 + 중복 + 교류 오버헤드)가 가장 적은 것. 차이가 10% 안이면 단순한 것 (P0 < P1 < P4 < P2 < P3). 함께 적는다: 평소 하루 바이트(박스당), 폭주 때 공격자 바이트당 박스가 받는 바이트(증폭).
- **B1 (측정, `data/cp3_cache`)**: 같은 글 2만 개를 FP32·FP16·INT8 동적·INT8 채널별로 인코딩한 임베딩을, 작성자 기기와 박스의 계산 차이 대신으로 쓴다. 쌍마다 cos(e_a, e_b)의 분포를 보고, 정직한 쌍의 99.99%가 통과하는 τ를 정한다. τ 안에서 공격자가 임베딩을 움직여 얻는 순위 이득(검색어 1천 개, 위 10개에 끼어드는 비율)을 잰다.
- **B2 (측정)**: 작성자 임베딩(INT8)으로 순위를 매기고 박스가 FP32로 검증할 때 Recall@10 ≥ 0.95 (NORTHSTAR 6 공정 비교 규칙).
- **B3 (모델, 칩 시간 CP19·CP20)**: E0 / E2 / E3의 인코더 일. 장면은 셋이다. ① 평소 하루 ② 24시간 밀린 수집 (CP19 S3) ③ 맞는 스팸 폭주 (CP19 S4·S5, 신원 K개). 셋 각각에서 새 글이 검색되기까지(K1 ≤ 4.64 s), 검색어 P99(K2 ≤ 50 ms, 검증 포함), 인코더 바쁜 시간을 낸다. 독살 공격(스팸 임베딩을 인기 검색어 근처로 놓기)도 넣는다.
  - 고르기: K1·K2를 지키는 것 중 인코더 일이 가장 적은 것. 차이가 10% 안이면 단순한 것 (E0 < E2 < E3).
  - E2나 E3을 고르면, CP19–CP23의 인코더 크기 결론(8×8, K_crit)을 새 일의 양으로 다시 적는다. 칩 주장이 줄어들면 줄어든 대로 적는다.
- 고른 것이 박스 설계를 바꾸면, 팀 운영 전에 데모에 넣는다 (다음 CP).

### B1: 허용 문턱과 독살 이득 (측정, `results/cp27/embed.json`)
같은 글 2만 개의 정밀도 쌍 (작성자 → 박스), 정직한 글이 통과하는 몫과, 공격자가 임베딩을 검색어 쪽으로 최대 arccos τ만큼 돌렸을 때 관련 없는 글이 위 10개에 끼어드는 비율 (무작위 20만 쌍, 정직하게는 0.048%):

| τ (각도) | 끼어들기 | 이득 | 통과: FP32 → FP16 | FP32 → INT8 채널별 | FP32 → INT8 동적 | INT8 → INT8 |
|---|---|---|---|---|---|---|
| 0.965 (15.2°) | 11.0% | 230배 | 100% | 100% | 100% | 99.99% |
| 0.99 (8.1°) | 1.1% | 23배 | 100% | 97.5% | 81.7% | 63.7% |
| 0.999 (2.6°) | 0.13% | 2.8배 | 100% | 0% | 0% | 0% |
| 0.9995 (1.8°) | 0.099% | 2.1배 | 100% | 0% | 0% | 0% |
- **INT8 두 방식끼리의 차이가 크다** (하위 0.01%에서 cos 0.965). 박스가 INT8로 검증하면 τ를 0.965까지 내려야 하고, 그러면 공격자가 230배 이득을 얻는다. FP16으로 검증하면 τ = 0.9995에서 정직한 글이 모두 통과하고 이득은 2배다.
- 결론: **안전한 검증은 박스가 FP16으로 다시 계산하는 것**이고, 그건 FP16으로 인코딩하는 것과 같은 비용이다. 작성자 임베딩은 인코딩 일을 줄여 주지 못한다.

### B2: Recall@10 (측정, FP32 정확 검색이 정답, 검색어 1천 개)
| 글 벡터 \ 검색어 | FP32 | FP16 | INT8 동적 | INT8 채널별 |
|---|---|---|---|---|
| FP32 (작성자) | 1.000 | 0.999 | 0.904 | 0.910 |
| FP16 | 0.999 | 0.999 | 0.904 | 0.910 |
| INT8 동적 | 0.894 | 0.894 | 0.862 | 0.860 |
| INT8 채널별 | 0.915 | 0.915 | 0.874 | 0.878 |
- 박스가 직접 INT8로 인코딩하는 지금 방식(INT8 / INT8)이 0.86–0.88. 0.95를 넘으려면 글 벡터와 검색어 모두 FP16 이상이어야 한다.

### B3: 인코더 일 (모델, 추정, `results/cp27/enc.json`)
CP19 칩 표 (8×8 INT8 500 MHz: 164토큰 글 70.9 ms, 검색어 10.9 ms), 하루 물량 P-all (텍스트 25,889, 검색 1,440), FP16 = INT8의 4.0배 (CP20 이미지 탑 GEMM 0.545 s / 0.136 s, 텍스트에 그대로 씀).

| 방식 | 하루 칩 시간 | 검색 (K2 50 ms) | Recall | 독살 이득 | 새 글 검색 가능 | 스팸 포화 (텍스트/s) |
|---|---|---|---|---|---|---|
| E0a INT8 수집 (CP12 이후 모델) | 1,852 s | 14 ms | **0.878 ✗** | 없음 | INT8 인코딩 뒤 | 14.1 |
| E0a + CP3 재순위 20개 (FP16) | 10,038 s | **5.70 s ✗** | 0.993 | 없음 | INT8 인코딩 뒤 | 14.1 |
| **E0b FP16 수집** | 7,422 s | 46 ms | 0.999 | 없음 | FP16 인코딩 뒤 | **3.5** |
| E2 작성자 벡터, 검색 때 위 10개 FP16 검증 | 4,156 s | **2.89 s ✗** | 0.999 | 2배 | 곧바로 | (검색 때) |
| E3-int8 작성자 벡터, 쉴 때 INT8 검증 | 1,899 s | 46 ms | 0.999 | **230배** | 곧바로, 검증은 나중 | 14.1 |
| E3-fp16 작성자 벡터, 쉴 때 FP16 검증 | 7,422 s | 46 ms | 0.999 | 2배 | 곧바로, 검증은 나중 | 3.5 |
- 대안에 정밀도(INT8 / FP16 검증)를 넣은 것은 B1·B2 결과를 본 뒤다 (표시).
- **사전 규칙대로면 E3-int8** (K2·Recall을 지키며 일이 가장 적음). 그러나 독살 이득이 230배다. 규칙에 보안 기준이 없었던 계획의 구멍이다.
- **고른 것 (결과를 보고, 표시): E0b FP16 수집.** 독살 면이 없고 가장 단순하다. E3-fp16은 일이 같고, 새 글이 검증 전에 검색된다는 것만 더한다. 그 대신 검증이 밀리면(폭주) 검증 안 된 글이 결과에 오른다.
- E2는 이 칩에서 성립하지 않는다. 후보 하나를 FP16으로 검증하는 데 284 ms (추정)라서 검색 한 번이 K2를 넘는다. CP3의 "검색 때 재순위"도 같은 이유로 이 칩에서는 5.7 s.
- **정정 (CP19–CP23, 추정)**: CP12 이후 칩 모델은 텍스트를 INT8로만 인코딩했다. 계약 정밀도(Recall ≥ 0.95)를 지키려면 FP16 수집이 필요하고, 텍스트 일은 약 4배다. 그러면 스팸 포화점이 14.1 → 3.5 텍스트/s, 24시간 밀린 수집이 1,836 → 7,359 칩 s로 바뀐다. CP19–CP23의 K_crit와 밀린 수집 결론은 약 4배 낙관적이었다. 다시 내는 것은 다음 CP.
- 뒤집을 조건: 사람 판정으로 INT8 검색 품질이 FP16과 같다는 근거가 나오면 E0a로 돌아간다 (CP3가 보류한 것: 10등과 11등의 점수 차 중앙값이 0.0033뿐이고, 자기 글 찾기 Hit@10은 INT8과 FP32가 같음).

### A: push 중복 (모델, 추정, `results/cp27/push.json`)
박스가 받는 총 바이트 ÷ 꼭 받을 바이트 (꼭 받을 것 + 중복 + 교류 오버헤드), 손실 10⁻³. 괄호 안은 켜져 있을 때 도착 P99:

| 장면 | n | P0 바로 D = 6 (지금) | P1 D = 3 | **P2 ID 먼저** | P3 Plumtree 꼴 | P4 "보내지 마" |
|---|---|---|---|---|---|---|
| C-a 모두 상시 | 100 | 6.76 (0.21 s) | 3.11 (0.30 s) | **1.19** (0.61 s) | 2.59 (1.11 s) | 5.94 (0.21 s) |
| | 1000 | 6.75 (0.42 s) | 3.07 (0.41 s) | **1.19** (1.21 s) | 2.57 (1.66 s) | 5.99 (0.41 s) |
| C-b 상시 1 + 노트북 | 1000 | 1.12 (0.15 s) | 1.04 (0.20 s) | **1.01** (0.45 s) | 1.04 (0.85 s) | 1.10 (0.15 s) |
| C-c 절반씩 | 1000 | 3.90 (0.31 s) | 2.09 (0.36 s) | **1.10** (0.91 s) | 1.81 (1.45 s) | 3.52 (0.31 s) |
- **판정 (사전 규칙): P2.** 모든 장면·n·손실(10⁻³, 10⁻²)에서 빠짐 0, 도착 P99 ≤ 1.21 s (기준 2 s), 총 바이트가 가장 적고 (평균 1.10배) 다음(P3 1.81배)과 10% 넘게 차이 난다.
  - P1(D = 3)은 손실 10⁻²·n = 1000에서 처음으로 빠짐이 생긴다 (C-a 9.7 × 10⁻⁶, C-c 1.9 × 10⁻⁵, 기준 안). P4는 봉투 1 KB가 0.4 ms에 나가서 "보내지 마"가 늦게 닿아 중복을 15%만 줄인다 (예상대로).
  - P3이 P2보다 중복이 많은 것: 메시지마다 이웃 둘을 새로 골라서 고정된 나무가 아니다 (진짜 Plumtree는 중복을 보낸 이웃을 가지치기해 나무를 굳힘). 굳히면 지연은 줄겠지만 바이트는 P2보다 작아질 수 없다.
- 의미: 평소 하루 바이트는 작다 (n = 1000, C-a: 꼭 받을 것 하루 약 0.9 MB, P0 약 6.2 MB, P2 약 1.1 MB). **중요한 곳은 폭주다.** 맞는 증명을 가진 스팸은 박스마다 P0에서 이웃 수만큼 (약 6.8배), P2에서는 약 1.2배 들어온다. 틀린 증명은 첫 박스가 버려 퍼지지 않는다 (O-b). 그래서 P2는 공격자 대역폭의 증폭을 약 6배 줄인다. 칩의 일은 바뀌지 않는다 (중복은 표 찾기에서 버림).
- 대가: 홉마다 왕복 하나가 더 들어 도착이 약 3배 늦다 (0.42 → 1.21 s). 새 글 5 s 목표 안이다.

## 답
1. **알고리즘으로 더 줄일 수 있는데 안 줄인 것은?** push 중복 (A: P2로 꼭 받을 바이트의 6.8배 → 1.2배). 나머지(교류, 중복 검사, 증명 검증, 스팸)는 이미 착취했다. **인코딩은 본래 필요하다** (B).
2. **A**: 줄일 수 있다. 평소 바이트는 작고, 맞는 증명을 가진 스팸이 오면 박스가 받는 양이 약 6배 준다.
3. **B**: 작성자 임베딩으로 인코딩 일을 줄일 수 없다. 익명이라 믿을 수 없고, 안전한 검증(FP16으로 다시 계산, τ = 0.9995)은 인코딩과 같은 비용이다. INT8로 검증하면 독살 이득이 230배다. 검색 때 검증은 이 칩에서 K2를 넘는다 (후보 하나 284 ms).
4. **계획에 없던 답: 정밀도 계약의 구멍.** CP12 이후 칩 모델은 INT8 텍스트만 셈해 엄격한 Recall@10이 0.878이다 (계약 0.95). 계약을 지키려면 FP16 수집이 필요하고, 텍스트 일은 약 4배다. **알고리즘을 짜내 보니 하드웨어의 일이 줄지 않고 오히려 늘었다.** CP19–CP23의 인코더 결론(K_crit, 밀린 수집)은 약 4배 낙관적이었다 (정정, 추정).

## 한계
- A는 교류 모델의 토픽 하나·봉투 1 KB. 폭주 증폭은 바이트 비율로 셈했다 (공격 장면을 따로 돌리지 않음).
- B1·B2의 "작성자 기기"는 같은 PC의 다른 정밀도로 대신했다. 맥과 윈도우의 실제 차이는 팀 운영 때 잴 수 있다 (같은 글의 임베딩을 박스끼리 비교).
- B3는 1차 근사다 (하루 총량, 줄 서기 없음). FP16 = INT8 × 4.0은 이미지 탑의 GEMM 비율을 텍스트에 쓴 것이다. 칩의 FP16 텍스트 경로는 매핑하지 않았다.
- B1의 공격자는 "임베딩을 검색어 쪽으로 돌리기"만 했다. 검증을 아예 통과하지 못하는 임베딩은 버려지므로 그보다 강한 독살은 없다.
- E3(검증 전 검색)의 "검증이 밀린 동안 독살 노출"은 재지 않았다 (고르지 않음).
