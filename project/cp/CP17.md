# CP17 — 박스 기능 스택 + 가상 가속기 + 이미지 글

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 설계는 [CP15.md](CP15.md), 앞 CP는 [CP16.md](CP16.md). 그림은 아키텍처 보드(L−1 아래 "박스 기능 스택")와 체크포인트 보드.

## 왜 이 CP인가
CP16은 메시지의 개수와 도착 시각만 다뤘다. 이번 CP는 박스가 메시지로 **실제로 하는 일**을 붙인다: 서명·증명·복호화·인코딩·색인·검색·피드·투표 집계·삭제·방. 결과(검색 결과, 집계, 삭제 여부)는 진짜 코드로 내고, 시간은 칩 모델(가상 가속기)과 Pi 5 환산으로 낸다. 그 기록이 CP18(인코더 다시 판정)의 입력이다.
CP16이 남긴 두 결정을 먼저 한다: 이미지를 어떻게 전달하나 (Q4에서 이미지만 실패), 투표 증명을 어떻게 만드나 (투표가 검증 메시지의 약 90%).
- 형식: **목적형**. [디자인] [구현] [측정].
- 답할 질문:
  - 이미지 글을 5초 안에 검색되게 하면서 박스의 이미지 인코딩과 업링크를 가장 적게 쓰는 전달 방식은?
  - 투표가 "한 사람 한 표, 속도 제한, 익명"을 모두 지키려면 증명이 무엇을 담아야 하고, 검증 비용은 얼마나 늘어나나?
  - 박스 1만 대 커뮤니티의 하루를 기능까지 돌리면 검색·삭제·방·투표가 맞게 동작하나? 박스마다 칩 유닛은 얼마나 바쁜가?

## 그림 (설계, 결과 전)
```
 사용자 행동 (CP16 매개변수 + 이번에 더함: 검색 0.4/DAU/일 출처 기반, 피드 열기·이미지 열기·삭제 (추정))
        │ 글·댓글·투표·삭제·방 메시지         ▲ 검색 결과, 피드
        ▼                                    │
 ┌ 박스 (실제 코드) ───────────────────────────────────────────────────────────────────────────────┐
 │ 받기: 중복? → 서명(Ed25519, 글마다 일회용 키) → 증명(RLN + 투표면 글별 nullifier) → 복호화(ChaCha20) │
 │       → 텍스트: 인코딩(MiniLM INT8) → 색인          이미지: 전달 방식 I1/I2/I3에 따라 (아래)            │
 │ 상태: 글·댓글 저장, 색인(정확 검색), 투표 집계(nullifier 집합), 벌칙 받은 신원, 지운 글                 │
 │ 쿼리: 검색 = 쿼리 인코딩 + top-10   피드 = 구독 서브의 글을 투표·시간으로 순위 (Reddit hot 식)         │
 │ 망각: 작성자가 같은 일회용 키로 서명한 삭제 → 원본·임베딩·색인에서 지움                                 │
 │ 방: 그룹 키로 암호화, 방 토픽은 구성원만 구독                                                           │
 │ ── 가상 가속기 (유닛마다 FIFO, 결과는 진짜로 계산하고 같은 메시지는 한 번만 계산해 나눠 씀) ──        │
 │   verify   : CP14 6×6 단건 26,542사이클 (11,303/s)                                                    │
 │   enc_text : CP12 32×32 500 MHz, 164토큰 8.05 ms, 토큰 수에 비례하는 MAC으로 환산 (추정)              │
 │   enc_image: CLIP ViT-B/32 MAC ÷ MiniLM MAC × 8.05 ms (추정, CP18에서 Timeloop로 바꿈)               │
 │   host     : 서명·복호화·색인·검색·피드를 노트북에서 재고 × 2.93 (A76 = 185H의 1/2.93, CP12 출처)      │
 └───────────────┬──────────────────────────────────────────────────────────────────────────────────────┘
                 ▼ 흔적: 시스템(메시지별), 박스(유닛별 시간대·Perfetto), 시간당 유닛 바쁨 (박스 1만 대 전부)
```
- 규모: 박스 1만 대 × 가상 하루. gossip 전달은 모든 박스가 한다. 기능 상태(색인, 집계, nullifier 집합)는 **표본 박스 20대**가 전부 갖고, 나머지 박스는 같은 메시지의 같은 결과를 나눠 쓰며 일의 양과 시간만 센다 (CP15 X1의 "대부분 E3, 표본만 E2"를 처음부터 씀: 박스마다 색인을 따로 두면 30일 치 글로 수 GB).
- 30일 치 지난 글은 "이미 동기화된 상태"로 넣고 (gossip 없이 구독 서브만), 하루 동안 새 글은 gossip으로 퍼진다. 글 본문은 Reddit 2010 글(CP2의 코퍼스), 이미지는 합성 그림 (이미지 데이터셋을 받지 않음).

### 결정 1: 이미지 전달
| | 방식 | 박스가 받는 것 | 검색되는 시점 | 박스의 이미지 인코딩 |
|---|---|---|---|---|
| I1 | 전부 밀기 (CP16) | 이미지 177 KB를 이웃 D = 6에게 | 이미지 도착 + 인코딩 | 구독 박스 전부 |
| I2 | 봉투 밀기 + 당겨 오기 | 봉투(헤더 + 썸네일 10 KB 추정)를 밀고, 본문은 봉투를 준 이웃에게서 한 번 당겨 옴 | 본문 도착 + 인코딩 | 구독 박스 전부 |
| I3 | 봉투 + 작성자 임베딩, 표본 검사 | 봉투에 작성자 박스가 낸 임베딩(INT8 512 B)을 넣음. 박스마다 확률 q = min(1, c/n)으로 본문을 당겨 다시 인코딩해 대조, 다르면 신고 → 받은 박스는 그 글을 숨기고 다시 인코딩해 확인 | 봉투 도착 | 글마다 평균 c대 (n = 서브의 박스 수) |
- I3의 위험: 거짓 임베딩 (그림과 무관한 검색어에 걸리게 하기). c = 14면 아무도 검사하지 않을 확률 ≈ e⁻¹⁴ = 8×10⁻⁷. 거짓 신고도 증명이 붙은 메시지라 속도 제한을 받고, 신고 하나가 만드는 일(받은 박스마다 인코딩 한 번)은 I2에서 이미지 글 하나가 만드는 일과 같다 → 공격자가 얻는 증폭은 I2 이하.
- 허용 오차 τ: 같은 그림이라도 박스마다 칩·정밀도가 다르면 임베딩이 조금 다르다. FP32 vs INT8 CLIP의 같은 그림 코사인으로 정한다 (이번에 측정).
- **규칙 R1** (판정, 박스 9,420대 서브 = CP16의 가장 큰 서브, 이미지 글 300개, 업링크 5/20/100 Mbps):
  1. 신선도: 이미지 글이 구독 박스 P99에서 검색 가능해지는 시간 ≤ 5초 (20 Mbps). 못 지키면 탈락.
  2. 무결성 (I3만): (a) 정직한 그림의 FP32–INT8 코사인 최솟값이 τ보다 커서 오경보 ≤ 10⁻³, (b) 거짓 임베딩이 모든 박스에서 숨겨지기까지 P99 ≤ 60초 (추정 목표), (c) 미검사 확률 ≤ 10⁻⁶. 하나라도 못 지키면 I3 탈락.
  3. 남은 것 중 상위 1% 박스의 이미지 인코딩 수가 가장 적은 것. 같으면 박스당 업링크 바이트가 적은 것.
- 뒤집을 조건: 5 Mbps에서만 신선도를 못 지키면 결정은 그대로 두고 "느린 회선의 박스"를 한계로 적는다.

### 결정 2: 투표 증명
| | 증명이 담는 것 | 한 사람 한 표 (같은 글) | 속도 제한 | 글 사이 연결 불가 |
|---|---|---|---|---|
| W1 | RLN만 (에폭 nullifier + 비밀 공유 조각) | 아님: 에폭 한도 안에서 같은 글에 여러 번 가능 | 예 | 예 |
| W2 | Semaphore식 글별 nullifier만 (scope = 글 ID) | 예 | 아님: 글이 다르면 무한 | 예 |
| W3 | 둘 다 (RLN 조각 + 글별 nullifier, 공개 입력 하나 더) | 예 | 예 | 예 |
| W4 | 에폭마다 투표 여러 개를 증명 하나로 | 예 | 예 | 예 |
- **규칙 R2**: 세 성질을 모두 지키는 것 중 박스의 투표당 검증 비용이 가장 낮은 것. 비용은 CP14 모델(곱셈 수)로.
- W4는 CP16에서 묶음당 투표가 1.00개였으므로(한 사람이 짧은 시간에 여러 번 투표하지 않음) 증명 수를 줄이지 못한다. 묶음 창을 늘리면 반영이 늦어져 Q2(60초)를 어긴다. → 표에만 두고 판정에서 뺀다 (CP16 데이터로).
- 기능 에뮬레이션: 증명 자체(페어링)는 맞음/틀림 표시 + 비용 모델이지만, **nullifier와 RLN 비밀 공유는 진짜로 계산**한다 (BN254 스칼라체에서 y = a0 + a1·x). 한 에폭에 한도를 넘기면 두 조각에서 신원 비밀 a0가 복원되어 벌칙을 받는 것까지 돈다.
- RLN 한도: 에폭 600초에 메시지 20개 (추정). 하루 실행에서 정직한 사용자가 한도를 넘는 비율을 재고, 0이 아니면 한도를 올린다.

### 기능 시험 (하루 실행에 공격·사건을 섞어 넣고 판정, 모두 통과해야 함)
| | 시험 | 통과 조건 |
|---|---|---|
| F1 | 검색: 표본 박스에서 글 제목으로 검색 (CP2의 자기 검색) | 그 박스가 가진 글이면 top-10에 있음 ≥ 0.95. 이미지는 같은 그림으로 검색해 1등 |
| F2 | 망각: 작성자가 글 10개 삭제 | 삭제 뒤 표본 박스 어디서도 검색·피드에 안 나옴. 삭제 전파 P99 ≤ 5초 |
| F3 | 방: 구성원 8명 방 | 구성원 박스는 모두 복호화, 구성원 아닌 표본 박스는 방 메시지를 받지 않고, 암호문을 줘도 복호화 실패 |
| F4 | 투표: 같은 글에 두 번 투표 3건, 에폭 한도를 넘는 신원 1명 | 두 번째 투표는 모든 표본 박스에서 거부, 한도 넘은 신원은 비밀이 복원되어 벌칙 |
| F5 | 틀린 증명 5건 | 첫 이웃에서 버려져 더 퍼지지 않음 (받은 박스 ≤ D) |
| F6 | 집계 일치 | 표본 박스의 글별 투표 수 = 실제로 보낸 정직한 투표 수 (구독 서브의 글에 대해) |
| F7 | 거짓 임베딩 (I3을 고르면) 2건 | 모든 표본 박스에서 숨겨짐, R1-2(b) 시간 안 |

### 박스 작업 기록 (CP18의 입력)
- 박스 1만 대 전부: 시간당 유닛별 바쁨 시간 (verify, enc_text, enc_image, host). 피크 시간의 상위 1% 박스와 중앙값 박스.
- 표본 박스: Perfetto 흔적 (유닛마다 작업 구간, 검색·피드 지연).
- 쿼리 지연: 검색 = 쿼리 인코딩(칩) + top-10(호스트). P99.
- **규칙 R3** (CP18로 넘길 판정): 상위 1% 박스 피크 시간에 enc_text + enc_image 바쁨이 1% 미만이면, CP18의 인코더 크기는 처리량이 아니라 **검색 지연(P99)과 밀린 수집**으로 정한다고 적는다.

### X5 (M1 vs M2), X2 (E1 vs E2)
- X5는 CLIP 텍스트 탑이 필요하다 (이번에 받은 것은 이미지 탑만). 이번 CP는 M1 (텍스트 MiniLM, 이미지 CLIP 이미지 탑)으로 돈다. 텍스트로 이미지 찾기는 글 제목·본문으로만 된다 → 한계에 적음.
- X2는 E1(실시간 데모)이 생기는 CP21에서 한다.

### CLIP 허용 오차 (측정, 합성 그림 300장)
| | 최소 | 0.1% | 중앙값 |
|---|---|---|---|
| 같은 그림, FP32 vs INT8 (동적, 채널별) | 0.877 | 0.877 | 0.987 |
| 다른 그림끼리, FP32 | | 상위 1% 0.965 · 최대 **0.981** | 0.883 |
- 정직한 INT8 임베딩이 FP32와 0.877까지 벌어지는데, 다른 그림의 임베딩은 0.981까지 가깝다. **τ를 어디에 두어도 "정밀도가 다른 정직한 박스"와 "다른 그림의 임베딩을 넣은 거짓"을 가를 수 없다.**
- 덤으로 찾은 것: **동적 INT8 CLIP은 같은 그림이라도 함께 묶인 그림(배치)에 따라 임베딩이 바뀐다** (배치 1 vs 16: 코사인 최소 0.977, 비트 단위로 다름). 활성값 스케일을 배치 전체에서 잡기 때문. 같은 배치를 다시 돌리면 비트 단위로 같고, FP32는 스레드 수·배치와 무관하게 비트 단위로 같다.
- 합성 그림은 CLIP에게 서로 비슷해 보인다 (다른 그림끼리 중앙값 0.883). 사진이면 다른 그림끼리 거리가 더 멀 것이다 (확인 안 함, 데이터셋을 받지 않음).

## 해석
1. **박스 소프트웨어가 기능으로 선다.** 박스 1만 대 커뮤니티의 하루에서 검색, 망각, 방, 한 사람 한 표, 속도 제한 벌칙, 틀린 증명 차단, 집계가 실제 코드로 맞게 돈다 (F2–F6). 운영자 없이 사용성 기능을 대신한다는 C5의 첫 근거다. 이미지 검색 실패(F1)는 시험 그림 탓으로 확인했지만 사진 데이터로 다시 봐야 한다.
2. **평소 칩은 거의 논다.** 10⁴명 커뮤니티의 가장 바쁜 박스에서도 인코더가 하루 0.7초 일한다. CP16의 결론(평소 부하는 칩 크기를 정하지 않음)이 기능 실행으로도 같다. 칩의 몫은 (a) 폭주, (b) 검색 지연, (c) 오프라인 뒤 밀린 수집, (d) 유휴 전력이다. (d)가 하루 에너지를 다 차지하므로 **전력 게이팅이 평소의 유일한 손잡이**다 (CP12 민감도와 같은 결론).
3. **이미지 전달은 업링크 문제였고 I2는 반만 푼다.** 바이트는 0.21배로 줄지만 5 Mbps 회선의 박스에서는 5초를 못 지킨다. 진짜로 빠른 것은 I3(0.4초, 인코딩 0.01배)인데, 막힌 이유가 **하드웨어 성질**이다: 박스마다 같은 그림에서 같은 임베딩을 내지 못한다 (FP32 vs INT8 0.877, 동적 INT8은 배치에 따라서도 바뀜). 프로토콜이 "표준 인코더" (정해진 정수 연산, 배치와 무관한 정적 양자화)를 정하고 모든 박스가 비트 단위로 같은 값을 내면 τ = 완전 일치로 둘 수 있다. **결정적(deterministic) INT8 데이터패스가 칩 요구사항이 될 수 있다** → CP18에서 따진다.
4. **투표는 증명 내용을 바꿔야 맞다.** RLN만으로는 같은 글에 여러 번 투표할 수 있다. 글별 nullifier를 공개 입력에 더하면 검증 비용은 1.3%만 늘고 세 성질이 다 선다.

## 한계
- 이미지는 합성 그림이다 (데이터셋 없음). 허용 오차와 F1 이미지 결과는 사진에서 다를 수 있다. 사진 데이터셋은 받을 때 허락이 필요하다.
- 텍스트로 이미지 찾기는 제목·본문으로만 된다 (CLIP 텍스트 탑 없음, X5 미판정).
- 증명의 페어링은 실행하지 않는다 (맞음/틀림 표시 + CP14 비용). nullifier와 RLN 비밀 공유는 진짜 계산.
- 표본 박스 20대만 기능 상태 전부를 갖는다. 나머지 박스는 같은 메시지에 같은 결과를 나눠 쓴다. 중계 박스의 거부 판정은 "먼저 게시된 것이 이긴다"는 기준 판정을 쓴다 (실제로는 박스마다 본 순서에 따름).
- 박스는 하루 내내 켜져 있거나 꺼져 있다. 꺼졌던 박스의 밀린 수집은 없음 (CP19).
- 이미지 열람(다른 박스에서 본문 가져오기), 피드 썸네일 전달 비용은 세지 않음. 피드 열기 빈도 (하루 10번/DAU)와 투표 방향 (90% 추천), 투표 대상 (최근 300개 중 무작위)은 (추정).
- 고아 투표 (대상 글보다 먼저 도착한 투표)는 대상이 60초 이상 지난 글만 고르게 해서 피했다. 실제 프로토콜은 대기열이 필요하다.
- 호스트 비용은 예비 측정 × Pi 5 환산 (추정).

## 계획에서 달라진 점
- before: F5 "받은 박스 ≤ D". after: "작성자와 그 메시 이웃 밖으로 0". 메시 연결이 양방향이라 박스 하나의 이웃이 D보다 많을 수 있다 (작성자 차수 6–11). 의도(첫 홉에서 멈춤)는 같다.
- before: R1-2(a) "FP32–INT8 최솟값이 τ보다 커서 오경보 ≤ 10⁻³". after: τ = 정직한 쪽 0.1% 분위수로 두고, 그 τ가 다른 그림의 임베딩을 막는지(다른 그림 최대 < τ)로 판정. 규칙 문장이 τ를 정하는 법을 빠뜨려서 판정 전에 이렇게 읽었다.
- before: CP16 Q2 V2 (50초 묶음). after: 투표는 하나씩 (W3). 묶음당 1.00표라 이득이 없고, 글별 nullifier가 투표마다 따로 필요하다.
- Perfetto 흔적은 박스 2대 × 피크 1시간만 남김 (하루 전부 × 20대면 수십 MB).
