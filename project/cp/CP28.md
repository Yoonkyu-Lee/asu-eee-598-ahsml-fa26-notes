# CP28 — 계약 정밀도의 박스와 데모: FP16 텍스트로 칩 결론 다시, 데모 박스 = 설계

2026-11-07 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP27.md](CP27.md) (정정: 정밀도 계약의 구멍).

## 왜 이 CP인가
- CP27 감사에서 CP12 이후 칩·박스 모델이 CP3 정밀도 계약을 지키지 않았다는 것을 찾았다. 텍스트를 INT8로만 셈해서 엄격한 Recall@10은 0.878이었다 (계약 0.95). 계약을 지키는 FP16 수집이면 텍스트 일은 약 4배다. CP19–CP23의 인코더 결론(크기 8×8, 밀린 수집, 스팸 K_crit)은 약 4배 낙관적이었다 (추정).
- 같은 감사에서 push는 "ID 먼저"(P2)로 정했다. 데모 박스는 아직 이웃마다 봉투를 바로 보내고(P0), 텍스트는 INT8 MiniLM이다.
- 팀 운영(미니 PC 상시 + 팀원은 언제든 빠짐)은 데모 박스가 설계대로일 때 한다.
- 형식: **목적형**. [측정·모델] CP19·CP20·CP22·CP23을 FP16 텍스트로 다시 [구현] 데모 박스 P2 + FP16급 텍스트 [측정] 데모 = 모델.
- 답할 질문:
  - 계약 정밀도에서도 8×8 인코더가 K1–K5를 지키는가? 아니면 어느 크기가 필요한가? 스팸 K_crit(CP23 I5 + F1: 오래된 2,842 · 새 7,044)는 얼마가 되는가?
  - 데모 박스에 P2와 FP16급 텍스트를 넣어도 기능 시험(L1–L7, P1–P4)과 데모 = 모델(CP26 D)이 그대로인가?

## 그림 (설계, 결과 전)
```
 칩 모델 (CP19 EncTable)                          FP16 텍스트 (이번 CP)
 text1(L) INT8 8×8 500 MHz: 164토큰 70.9 ms   ─▶   text1(L) × 4.0 (CP20 GEMM FP16 / INT8, 추정): 164토큰 약 284 ms
 검색어 12토큰 10.9 ms                        ─▶   × 4.0: 약 44 ms (K2 50 ms 안이어야 함)
 사진 FP16 0.552 s (CP20 그대로)                    그대로
 → sim_cp19 (S1–S5, 규칙 Q·C·S), sim_cp20 (V2·F·A, 하나씩 끄기), sim_cp22 (T1–T3), sim_cp23 --i5 (I5 + F1)

 데모 박스 (box_server x2)
   push: 봉투를 이웃 D에게 (P0)            ─▶   ID를 이웃에게 (IHAVE), 없는 이웃만 요청 (IWANT), 봉투는 한 번 (P2)
   텍스트: MiniLM INT8 (CPU)                ─▶   MiniLM FP32 (CPU; FP16과 Recall 0.999로 같은 급, CP27 B2)
   검색어: INT8                              ─▶   FP32
```

## 대안 (결과를 보기 전에 적음)
- **칩의 FP16 텍스트를 어떻게 셈하나**
  - M-a: INT8 시간 × 4.0 (CP20 이미지 탑 GEMM 비율을 텍스트에). ← 고름. 바꿀 조건: FP16 텍스트를 Timeloop로 매핑할 때 (칩 재설계 CP).
  - M-b: FP16 텍스트를 Timeloop로 새로 매핑. 정확하지만 CP12 툴체인(WSL)과 시간이 든다.
- **데모의 FP16급 텍스트**: CPU에서 FP16 ONNX는 느리거나 지원이 고르지 않다. FP32 MiniLM을 쓴다 (CP27 B2: FP32와 FP16 Recall 0.999).
- **데모의 P2**: IHAVE는 메시지 하나마다 바로 보낸다 (묶지 않음). 모델과 같다. 요청을 받은 박스가 꺼졌으면 1 s 뒤 다음 알린 박스에 (모델 `req_timeout_s`).

## 판정 규칙 (결과를 보기 전에 적음)
- **R1 (칩 결론 다시)**: CP19 규칙 Q·C·S, CP20 규칙 V2·F·A, CP22·CP23의 규칙 S2·S3를 FP16 텍스트로 그대로 다시 돌린다 → `results/cp28/`.
  - 고른 것이 바뀌면 정정 (CHECKPOINT·보드에 정정 표시). 8×8이 K1–K5를 못 지키면 CP19 규칙 S대로 지키는 가장 작은 인코더를 적는다.
  - K_crit와 밀린 수집은 바뀐 숫자를 정정으로 적는다.
- **R2 (데모)**: L1–L7, P1–P4 통과. CP26 D 장면(박스 다섯)에서 따라잡기 네 칸이 모델과 같고, **push 칸도 모델과 같은 분류로**: 받은 봉투 수(중복 포함), 받은 IHAVE 수가 다른 칸은 경쟁 (c)만.
- R1과 R2가 끝나면 팀 운영 준비 점검표 (미니 PC 상시, 팀원은 언제든 빠짐)를 적는다.

### R1 둘째: FP16 텍스트에서 규칙 Q를 지키는 인코더 (모델, 추정, `results/cp28/encoders.json`)
CP19 규칙 Q의 장면(S2 피크, S3 8·24시간 밀린 수집, Q2, 실시간 먼저).

| 인코더 | 164토큰 글 | 검색어 | 검색어 P99 S2 / S3 최대 | 8시간 밀린 수집 | 24시간 | 판정 |
|---|---|---|---|---|---|---|
| 8×8 1 MB | 284 ms | 43.6 ms | 110 / 125 ms ✗ | 64.5분 ✗ | 163분 | ✗ |
| **16×16 2 MB, B = 1** | 74 ms | 11.0 ms | 24 / 32 ms | 14.1분 | 35.6분 | **통과 (가장 작음)** |
| 16×16 2 MB, B = 8 | | | 24 / 57 ms ✗ | 14.1분 | | ✗ |
| 32×32 2 MB | 32 ms | 8.9 ms | 12 / 18 ms | 5.9분 | 14.9분 | 통과 |
- **판정 (R1): 계약 정밀도에서는 16×16 (B = 1)이 필요하다.** FP16의 16×16은 예전 INT8의 8×8과 속도가 거의 같다 (164토큰 74 ms 대 71 ms).
- 면적: CP20 하나씩 끄기의 "8×8 1 MB → 16×16 2 MB"가 +3.98 mm² (INT8 MAC 기준). FP16 MAC은 INT8보다 크므로 이것은 아래 경계다. 칩은 5.61 mm² → 9.6 mm² 이상 (추정, 매핑하지 않음).

### R1 셋째: 16×16 FP16에서 스팸 결론 (모델, 추정, `results/cp28/cp22_16`, `cp23_16`)
| | 8×8 INT8 (CP22·CP23) | 8×8 FP16 | **16×16 FP16** |
|---|---|---|---|
| CP22 규칙 S2 고른 것 | T1 + T2 + T3 | 없음 | T1 + T3 |
| CP23 I5 (손잡이 없음) K_crit 오래된 / 새 | 1,558 / 6,200 | 0 / 0 | 1,518 / 5,915 |
| **CP23 I5 + F1 K_crit 오래된 / 새** | **2,842 / 7,044** | 0 / 0 | **2,712 / 6,722** |
| 기준 장면 검색어 P99 (I5 + F1) | 20 ms | 78 ms | 20 ms |
| CP23 규칙 S3 | 통과하는 구현 없음 | 없음 | 통과하는 구현 없음 (같음) |
- **16×16 FP16은 8×8 INT8의 스팸 몫을 거의 그대로 되찾는다** (K_crit 4–5% 적음). CP23의 결론("회원 1% 새 신원의 텍스트 스팸은 운영자 없이 못 막는다, 신원 비용이 필요")은 그대로다.
- CP23 I5는 첫 실행의 I0–I4 행(INT8)과 섞여 규칙 S3을 다시 낸다. 그래서 S3 판정은 I5 행만 본다 (I0–I4는 FP16으로 다시 돌리지 않음).
- CP22 S2의 고른 것이 T1 + T3로 바뀐 것은 기록만 한다 (CP23이 무게 한도를 I5로 이미 바꿈).

### R2: 데모 박스 = 설계 (P2 ID 먼저, FP32 텍스트) — 시험하며 찾은 것
- 첫 실행 (`logs/cp28_exchange_check_run1_brokencfg.json`): **내 실수.** `lan.py`의 `community(...)` 호출 줄 중간에 주석을 넣어 같은 줄의 `base_port`, `proto="cp24"`, `hosts`, `room` 인자가 주석이 됐다. 박스가 CP21 박스로 떠서 L1–L7·P1–P4가 멈추고 D가 엉켰다. 고침.
- 둘째 실행 (`logs/cp28_exchange_check_run2.json`, `logs/cp28_persist_check_run2.json`): L1–L7 통과, D의 따라잡기 네 칸은 모델과 같음. 둘이 남았다.
  1. **P3 실패 — 가짜 지우기가 진짜 글을 막았다.** `ihave1`이 그 번호의 지운 글 표시(tomb)가 있으면 공개키를 보지 않고 "원하지 않음"이라 답했다. 지운 글 표시는 가짜 지우기도 남긴다. ID만으로는 공개키를 비교할 수 없다. **사진 당기기와 사진 주기(CP25부터)도 같은 구멍**이었다 (P3이 텍스트 글만 시험해서 못 봄). 고침: "가졌다가 잊은 글"(`gone`)만 막는다. 나머지는 받아서 `deliver`가 공개키로 가린다.
  2. **push 칸이 모델보다 많음** (IHAVE 28 대 12, 봉투 20 대 10). 대본에서 센 기댓값(켜진 박스 k개면 글 하나에 봉투 k − 1, IHAVE (k − 1)²)은 모델과 정확히 같았다. 데모는 한 번도 연락하지 않은 박스를 켜져 있다고 보고 보냈다. 실패한 전송을 몇 초 다시 시도하는 사이 그 박스가 켜지면 늦게 닿았다 (박스 4가 켜지자마자 11–13 s 전의 글 둘을 받음). 고침: **켜져 있다고 아는 박스에게만 보낸다** (인사해 왔거나, 인사에 답했거나, 보낸 것이 온 박스). 모델의 "메시는 켜진 박스끼리"와 같다. 전송에 실패하면 꺼진 것으로 본다.
- 셋째 실행 (`logs/cp28_exchange_check_run3.json`): 박스 2–4는 모델과 같고, 박스 0·1만 봉투 +2, IHAVE +2. 꺼진 박스를 아직 켜진 줄 아는 동안 보낸 ID의 **재시도**(세 번, Windows에서 닫힌 포트 연결이 시도마다 약 2 s)가 약 7 s 이어져, 그 사이 다시 켠 박스에 늦게 닿았다. 모델에는 보내는 쪽 재시도가 없다. 고침: **ID 먼저 모드에서는 재시도하지 않는다.** 한 번 실패하면 꺼진 것으로 본다. 놓친 박스는 다른 박스의 IHAVE로 1 s 뒤 받거나 켜질 때 따라잡기로 받는다 (CP24·CP26 재현용 예전 모드는 세 번 그대로).
- 모두 결과를 보고 고친 것이다.

### R2: 판정 (측정: 진짜 박스, 이 PC, Tailscale 주소)
- **L1–L7 통과** (`results/cp28/lan_check.json`), **P1–P4 통과** (`results/cp28/persist_check.json`, 시계 차 ≤ 0.88 ms, P3의 "가짜 지우기가 먼저 온 글"이 세 박스 모두에 보임).
- **D 통과** (`results/cp28/exchange_check.json`): 박스 다섯의 여섯 칸이 모두 모델과 같다.

| 박스 | 따라잡기 요청 | 따라잡기 봉투 | 내놓은 ID | 원한 ID | 받은 IHAVE | 받은 봉투 (push) |
|---|---|---|---|---|---|---|
| 0 (상시, 한 번 꺼짐) | 2 | 7 | 5 | 0 | 5 | 4 |
| 1 | 3 | 13 | 7 | 0 | 4 | 3 |
| 2 | 2 | 11 | 4 | 0 | 1 | 1 |
| 3 | 2 | 13 | 8 | 0 | 2 | 2 |
| 4 | 1 | 8 | 0 | 0 | 0 | 0 |
- push로 받은 봉투 합 10 = 대본에서 센 기댓값 (켜진 박스 k개면 글 하나에 k − 1). 중복 0 (P0이었다면 켜진 박스마다 이웃 수만큼).
- FP32 텍스트 인코딩 (이 PC, 1스레드, 짧은 글, 예비 측정): P50 4.8–5.2 ms (INT8 3.3–3.7 ms).

| 항목 | 상태 | 근거 |

| 같은 글이 이웃마다 한 부 | 고침 | P2 ID 먼저 |
| 검색 정밀도 | 고침 | FP32 MiniLM (계약) |
| 팀원 설치 | 문서 있음 | LAN.md, REMOTE.md (Tailscale 초대는 사용자) |
| 미니 PC에서 박스를 부팅 때 자동으로 | 안 함 | 사용자가 명령을 켜 둠 (원하면 작업 스케줄러) |
| 증명 | 깃발 | 실제 Groth16 검증은 로드맵 |

## 답
1. **계약 정밀도에서 8×8?** 못 지킨다. 평소에도 검색어 P99 104 ms (K2 50 ms), 8시간 밀린 수집 64.5분 (K3 60분). **16×16이 필요하다** (B = 1: 검색어 24–32 ms, 8시간 14.1분). 면적 +3.98 mm² 이상 (INT8 MAC 기준 아래 경계), 칩 5.61 → 9.6 mm² 이상 (추정).
2. **스팸 K_crit?** 16×16 FP16이면 CP23 I5 + F1이 오래된 2,712 / 새 6,722로, 8×8 INT8(2,842 / 7,044)과 거의 같다. "신원 비용이 필요하다"는 결론은 그대로.
3. **데모 = 설계?** 그렇다. P2와 FP32 텍스트를 넣고 L1–L7, P1–P4, D(여섯 칸)가 모두 통과한다. 거기까지 가며 CP25부터의 지운 글 표시 구멍(가짜 지우기가 진짜 글의 ID·사진을 막음)과, 데모가 꺼진 박스에 보내던 것을 고쳤다.

## 한계
- 칩의 FP16 텍스트는 INT8 × 4.0 (이미지 탑 GEMM 비율, M-a). FP16 MAC의 면적·에너지는 매핑하지 않았다. 16×16의 면적은 아래 경계다.
- CP20의 Hailo-8L 비교는 Hailo 텍스트를 INT8로 둔 채라 계약 정밀도에서 공정하지 않다 (다시 하지 않음).
- CP23 I5만 다시 돌렸다 (I0–I4는 INT8 결과 그대로).
- 데모는 한 컴퓨터 안. 진짜 절전, 네트워크만 끊김, 맥에서의 FP32 속도는 팀 운영에서.

## 계획에서 달라진 점
- R1에 "인코더 크기별 규칙 Q 장면"(`encoders`)과 "16×16으로 CP22·CP23"(`rerun16`)을 더함 (8×8이 실패한 것을 보고, 규칙 R1의 "지키는 가장 작은 인코더" 때문).
- R2를 하며 데모의 설정 실수(내 것), 지운 글 표시 구멍, 꺼진 박스에 보내기, 재시도를 고치고 다시 돌림 (결과를 보고).
