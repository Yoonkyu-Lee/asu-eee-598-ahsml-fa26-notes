# CP24 — 정합성 빚 정리: 고친 박스 모델, 설계대로 도는 데모 박스, 여러 컴퓨터

2026-11-03 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP23.md](CP23.md) (다음 CP 줄), [CP22.md](CP22.md) (한계 "모델 버그 하나를 고쳤다"), [CP21.md](CP21.md) (한계 "데모 박스와 시뮬레이터는 CP17의 검사 순서"). 그림은 아키텍처 보드(L1 "무게 한도", 새 절 "데모 박스")와 체크포인트 보드.

## 왜 이 CP인가
- CP19–CP23에서 고른 것들이 서로 다른 코드에 흩어져 있다.
  - 증명 먼저(O-b, CP19), 실시간 128토큰(F1, CP23), 사진 뒤로(T2)·나이 그룹(T3, CP22), 텍스트 단위 + 사진 개수 한도(I5, CP23)는 **박스 한 대 모델**(`sim_cp19`–`sim_cp23`)에만 있다.
  - 진짜 프로세스로 도는 데모 박스(CP21)와 여러 박스 시뮬레이터(DayNet, CP17)는 아직 CP17의 박스다: 서명 먼저, 256토큰, 한도는 "10분에 메시지 20개".
- CP22에서 고친 모델 버그(미래 시각의 일이 코어를 미리 잡음)는 CP19–CP20 실행에 남아 있다. CP19의 K_crit와 CP20의 비교표에 조금 섞였을 수 있다.
- CP22·CP23 결론이 기대는 **s_new (새 사용자 몫)의 출처가 없다**. CP23은 "s_new ≤ 2.8%면 I1(1) + F1로 회원 1%를 지킨다"를 뒤집을 조건으로 남겼다.
- (계획 추가, 2026-11-03) 내일(11-04) 팀원 셋이 맥북 두 대와 윈도우 노트북 한 대로 커뮤니티에 직접 참여해 본다. 지금 데모는 한 컴퓨터의 `127.0.0.1`에서만 돌고, 모든 신원과 방 키를 시드 하나에서 뽑는다 (박스가 남의 비밀을 다 앎). 여러 컴퓨터에서 돌려면 신원과 방 키가 각자에게만 있어야 한다.
- 형식: **목적형**. [구현] 고친 모델로 다시 돌리기, 데모 박스·DayNet에 설계 넣기 [데모] 여러 컴퓨터 모드 [조사] s_new 출처.
- 답할 질문:
  - 고친 모델에서 CP19–CP20의 결정이 바뀌는가?
  - 설계(O-b, F1, I5, T2/T3)를 넣은 데모 박스와 DayNet이 작업 수 단위로 여전히 같은가 (CP15 규칙 X2)? 데모 기능 시험은 그대로 통과하는가?
  - 각자의 컴퓨터에서 각자의 신원으로 참여할 수 있는가?
  - s_new는 실제로 얼마인가?

## 그림 (설계, 결과 전)
박스 한 대의 수집 (CP24 박스 = 설계):
```
 메시지 ─▶ ① 표 찾기: (epoch, nullifier, x)가 이미 있으면 버림   (재전송, 0.013 ms)        O-b (CP19)
         ─▶ ② 증명 (검증 유닛): 검증키 = (텍스트 번호 n_t, 사진 n_p)   틀리면 버림           I5 (CP23)
              사진이 붙었는데 n_p = 0이면 버림 (봉투에 보임)
         ─▶ ③ Ed25519 서명                                                틀리면 버림
         ─▶ ④ nullifier n_t + n_p개: 같은 번호에 다른 x → 비밀 복원 → 벌칙 알림       RLN
         ─▶ 이웃에게 전달
         ─▶ ⑤ 복호화 → 토큰 수로 필요한 번호 수 확인 (모자라면 색인 안 함)          I5, 회로 밖
         ─▶ ⑥ 인코더 줄 (우선순위): 검색어 0 > 오래된 텍스트 1 > 새 텍스트 3 > 오래된 사진 4 > 새 사진 5
              텍스트는 앞 128토큰만 (F1)                                   T2·T3 (CP22), F1 (CP23)
```
한도 (CP23 I5 + F1 결과 그대로; 1번호 = 1/4단위, 단위 = 256토큰 텍스트의 칩 인코딩 시간):

| 그룹 | 창 | 텍스트 번호 | 사진 | 투표·삭제 (계획 추가: CP23 모델 밖) |
|---|---|---|---|---|
| 오래된 (가입 30일 이상) | 10분 | 7 (= 1.75단위) | 1 | 10분에 20 (CP17 RLN 한도) |
| 새 | 1시간 | 18 (= 4.5단위) | 2 | 같음 |

글 하나의 텍스트 번호 수 = ⌈4 × 칩 시간(min(토큰, 128)) / 칩 시간(256)⌉ (짧은 글 1개, 128토큰 2개). 정직한 클라이언트는 남은 번호가 모자라면 다음 창까지 기다린다 (화면에 남은 몫을 보임).

## 대안 (결과를 보기 전에 적음)
- **데모 박스의 설계 반영**
  - D-a: 데모 박스에 O-b·F1·I5·T2/T3을 모두 넣는다 (인코더 줄은 실제 우선순위 스레드). ← 고름
  - D-b: 데모는 기능 시연이니 CP17 박스 그대로 둔다. 바꿀 조건: 없음 (CP21 한계가 이것을 빚으로 적었다).
- **DayNet의 설계 반영**
  - N-a: O-b(검사 순서·작업 수), F1(인코딩 토큰), I5(번호·nullifier 수)만 넣는다. 우선순위(T2/T3)는 넣지 않는다. ← 고름
    - 근거: DayNet의 장치는 FIFO이고, 쓰는 출력은 시간당 바쁜 시간(박스 전력)과 작업 수다. 우선순위는 대기 순서만 바꾸고 바쁜 시간 합은 그대로다. 지연은 박스 한 대 모델(`sim_cp19`–`sim_cp23`)이 맡는다.
    - 바꿀 조건: 여러 박스 사이의 지연(전파 + 우선순위)이 결정에 쓰이는 CP가 오면 DayNet 장치를 우선순위 큐로 바꾼다.
  - N-b: 우선순위까지 넣는다 (장치를 사건 큐로 다시 짬).
- **옛 결과 재현**: `sim.box`·`DayNet`의 기본값은 CP17 그대로 두고, CP24 박스는 새 모듈(`src/sim/proto24.py`)과 플래그로 켠다. CP17–CP21 명령은 같은 숫자를 낸다.
- **여러 컴퓨터의 설정 나누기**
  - L-a: 모두 같은 명령 (IP 목록 + 자기 번호). 방 키는 방 암호에서 (만나서 말로 전함). ← 고름
  - L-b: 한 사람이 설정 파일을 만들어 나눠 줌. 방 키가 파일로 돈다 (디스코드 같은 운영자 서버를 거침).
  - L-c: 부트스트랩 서버. 운영자 비슷한 것이 생김 → 탈락.
- **사진**: 팀원 맥에는 COCO가 없다. 화면에서 자기 사진 파일을 고르면 브라우저가 224×224로 잘라 보낸다. COCO가 있는 박스는 "아무 사진" 단추도 남긴다.
- **보안 (여러 컴퓨터)**: 박스는 `0.0.0.0`에 묶이지만 주인 API(`/`, `/api/*`)는 `127.0.0.1`에서 온 요청만 받는다. 피어 API는 IP 목록에 있는 주소만 받는다. 같은 와이파이의 다른 사람이 내 이름으로 쓰지 못하게.

## 판정 규칙 (결과를 보기 전에 적음)
- **R1 (다시 돌리기)**: 고친 호스트(미래 시각의 일은 세기만 하고 코어를 잡지 않음; CP22 `Box22.host`와 같고, 시간당 바쁜 시간에도 넣음)로 `sim_cp19.main`, `sim_cp20.main`을 그대로 다시 돌린다 → `results/cp24/rerun/`.
  - CP19 규칙 Q·C·S, CP20 규칙 V2·F·A와 하나씩 끄기 표 중 **고른 것이 바뀌면 정정** (CHECKPOINT·보드에 정정 표시).
  - 고른 것은 같고 K_crit나 표의 숫자가 10% 넘게 움직이면 그 숫자를 정정으로 적는다. 아니면 "확인, 그대로".
- **R1b (R1을 돌리는 중에 추가, R1b 결과를 보기 전에 적음)**: CP22의 고침은 "미래 시각의 일"을 모두 코어 밖으로 뺀다. 그런데 `sim_cp19`의 호스트 일은 앞 단계가 끝나는 시각으로 미리 예약되는 연쇄 단계가 많다. 그래서 사진 복호화뿐 아니라 **연쇄 단계 전부의 코어 경쟁이 빠진다** (호스트 경쟁을 덜 셈). 실제 박스에 가까운 모델은 **빈 시간 메우기**다. 모든 호스트 일이 자기 시각 이후의 코어 빈틈 중 가장 이른 곳에 들어가고, 먼저 온 일은 나중 시각으로 예약된 일 앞의 빈 시간을 쓴다 (`sim_cp24.gapfill`).
  - 같은 비교를 `results/cp24/rerun_gap/`으로 한다.
  - R1과 R1b가 결정에서 갈리면 R1b를 쓴다. 그리고 CP22·CP23의 결론(CP22 S-t, CP23 I5 + F1)도 빈 시간 메우기 모델로 다시 낸다.
  - 갈리지 않으면 "CP22 고침으로 결정은 같다"고 적고, 숫자 차이만 적는다.
- **R2 (데모 = 설계)**: CP21의 장면 실행기를 CP24 박스로 다시 돌린다 (`x2.py --cp24`).
  - X2: 박스별 작업 수가 데모 박스(E1)와 DayNet(E2)에서 같다 (CP21과 같은 분류 규칙).
  - D1–D6이 그대로 통과한다.
  - 새 시험: D7 한도 (정직한 클라이언트는 몫이 모자라면 기다림; 같은 번호를 다시 쓰면 벌칙 알림이 모든 박스에 가고 그 뒤 글은 버려짐), D8 F1 (색인 인코딩이 128토큰 이하), D9 O-b (서명만 바꾼 재전송은 증명 전에 버려짐: 증명 수가 늘지 않음).
- **R3 (여러 컴퓨터)**: 이 컴퓨터에서 박스 셋을 `0.0.0.0`에 띄우고, 서로를 사설 IP로 부른다. 통과 = 글·투표·삭제·방·사진 업로드가 다른 박스에 퍼지고, 사설 IP에서 온 주인 API 요청은 403. 진짜 세 대 시험은 11-04 팀원들과 (결과는 다음 CP에 적음).
- **R4 (s_new)**: 실제 커뮤니티에서 **가입 30일 미만 계정이 쓴 글·댓글의 몫**을 잰 출처를 찾는다 (Reddit, Stack Exchange, 위키백과, Discourse 등). 비슷한 정의(첫 달 사용자, 신규 기여자)는 정의 차이를 적고 쓴다.
  - 출처 값이 2.8% 이하 → CP23의 뒤집을 조건대로 I1(1) + F1 (새 그룹 6단위/h)이 회원 1%를 지킨다고 적는다 (I5 + F1과 비교).
  - 2.8% 초과 → 신원 비용(NORTHSTAR 5)이 필요하다고 적는다.
  - 출처가 없으면 그렇게 적는다.

## 결과

### R1: CP22의 고침으로 CP19·CP20 다시 (모델, 추정)
`results/cp24/rerun/compare.json`: CP19 숫자 1,010개 중 54개, CP20 786개 중 82개가 10% 넘게 움직였다.
| 결정 | 처음 (CP19·CP20) | R1 | |
|---|---|---|---|
| CP19 규칙 Q (인코더 스케줄) | Q2 B = 8 (호스트·검증 실시간 먼저일 때만) | Q2 B = 8 | 고른 것은 같음 |
| CP19 규칙 Q, 계획대로(호스트·검증 FIFO) | 아무것도 못 지킴: 따라잡기 중 새 글 P99 1 h 3.3 s, 8 h 18.9 s, 24 h 54.5 s | **Q2 B = 8, B = 1 통과**: 새 글 P99 0.14–0.22 s (1 h·8 h·24 h) | **갈림** |
| CP19 규칙 C (검사 순서) | O-b | O-b (폭주 중 호스트 0.85 → 1.14 코어, K4 2코어 안) | 같음 |
| CP19 규칙 S (스팸 K_crit) | 8×8 L-b 310 등 6칸 | 6칸 모두 같은 값 | 같음 |
| CP20 규칙 V2·F·A | | 모두 같음 | 같음 |
- 갈린 것은 CP19가 첫 실행 뒤에 넣은 "호스트·검증도 실시간 먼저"가 필요했느냐다. CP20 하나씩 끄기 표의 "실시간 먼저 → FIFO: 따라잡기 중 새 글 18.9 s (K1 실패)"도 같은 숫자다.
- 그런데 R1의 고침은 앞 단계가 끝나는 시각으로 미리 예약한 연쇄 단계의 코어 경쟁을 모두 뺀다 (위 R1b). 그래서 FIFO가 통과한 것이 고침의 효과인지, 경쟁을 덜 센 효과인지는 R1b로 가린다.
- 폭주 중 호스트 코어가 오른 것: 버그 모델에서는 뒤로 밀린 일이 실행 끝(폭주 60 s + 120 s) 뒤로 넘어가 세지지 않았다 (추정, 해석). 다른 설명은 확인하지 않았다.

### R2: 데모 박스 = 설계 (측정: 진짜 프로세스 다섯 개, 세컨컴 CPU)
- 장면 146개 (CP21의 145개 + 서명만 바꾼 재전송 1개), 메시지 141개.
- 박스 0–2는 오래된 그룹, 3–4는 새 그룹. 정직한 클라이언트가 다음 창을 기다린 것은 23번이다 (대부분 사진 미리 넣기: 오래된 그룹은 10분에 1장).
- **X2: CP21과 같은 결과.** 모든 박스의 모든 작업 칸(새 칸 `lookup` 포함)이 데모 박스와 DayNet24에서 같다. 다른 칸은 사진 당기기와 중복 수신뿐이고, 합은 같다 (412 / 412, 524 / 524). CP21 분류 (c), 실제 네트워크의 경쟁이다.
  - 합: 증명 666, 텍스트 인코딩 600, 사진 516, 전송 1,055 / 1,055.
- **D1–D6 통과** (D1 새 글 정착 최대 0.72 s).
- **D7 통과**: 정직한 기다림 23번, 벌칙은 재사용한 신원 하나뿐, 정직한 텍스트 메시지의 번호 수는 모두 규칙대로다.
- **D8 통과**: 박스 다섯 대 모두 색인 인코딩 최대 128토큰. 128토큰을 넘는 글은 1개다.
- **D9 통과**: 재전송은 어느 박스에서도 증명 검사까지 가지 않았다 (판정 `dup_lookup`만).
- CP21 모드가 그대로인지 확인했다 (`logs/cp24_cp21check/`, 커밋한 `results/cp21`은 덮어쓰지 않음). DayNet 열은 모든 칸이 같고, 박스 열은 경쟁 칸만 다르다. D1–D6은 통과한다.

### R4: s_new 출처 (조사)
- **"가입 30일 미만 계정이 쓴 글·댓글의 몫"을 직접 잰 출처는 찾지 못했다.** Reddit, Stack Overflow, 위키백과, Mastodon, Lemmy, Hacker News를 찾았다. 찾은 것은 모두 **사용자 몫**이거나 일부 메시지에 대한 값이다 (출처, 정의는 아래).

| 출처 | 커뮤니티 | 정의 | 값 | 메시지/사용자 |
|---|---|---|---|---|
| Larsen & Silge, Stack Overflow Blog, 2018-01-15 | SO, Jon Skeet이 답한 질문 | 질문 때 계정 나이 < 1개월 | 21.9% | 질문자 (일부) |
| Wikimedia Meta "Portuguese Wikipedia trends ... Editor Trends" (2012) | pt.wikipedia 2004–2011 | 그달 첫 편집 | 월 편집자의 약 40–50% (편집 5회 넘는 편집자 중 약 25%) | 사용자 |
| Veselovsky & Anderson, ICWSM 2023 | Reddit 2020–21 | 한 달 댓글 50개 넘는 사용자 | 활동의 약 73% | 메시지 (활동량 기준, 나이 아님) |
| Zia et al., arXiv 2302.14294 (2023) | Mastodon, 트위터 이주 2022 | 인수 뒤 만든 계정 | 약 79% | 사용자 (이주자 표본) |
| Lemmy 팀 공지 2023-06-17 | Lemmy, Reddit 블랙아웃 | 월 활성 1,000 → 27,000 | 활성의 96% 이상이 새 사용자 | 사용자 |

- 환산 (추정): s_new = (새 사용자 몫 u) × (새 사용자 한 명의 쓰기 / 평균). u ≈ 0.25–0.5 (위키백과 정상 상태). 둘째 항은 출처가 없다. 활동이 소수에 몰리는 것(Reddit 73%, 위키백과 편집 100회 미만 편집자가 편집의 약 20%)으로 보아 1보다 훨씬 작다. 0.1–0.3이면 s_new ≈ 2.5–15%다. **2.8%의 양쪽을 다 포함한다.**
- 이주·급성장 때는 새 사용자가 활성의 80–96%다. 그때 s_new는 5%보다 훨씬 크다. 우리 같은 새 커뮤니티의 첫 몇 달이 바로 이 경우다.
- **판정 (R4): 출처 없음.** CP23의 뒤집을 조건(s_new ≤ 2.8%)은 열린 채로 둔다. 정상 상태 대리값도 이주 때 값도 2.8% 위를 포함하므로, **새 그룹을 익명 한도만으로 지킨다는 주장은 하지 않는다.** 신원 비용(NORTHSTAR 5)이 필요하다는 CP23의 결론을 유지한다.
- 직접 잴 길: Pushshift 같은 Reddit 댓글 덤프에서 댓글 시각과 작성자 가입 시각을 비교한다. 데이터를 받아야 해서 (사용자 허락 필요) 하지 않았다.
