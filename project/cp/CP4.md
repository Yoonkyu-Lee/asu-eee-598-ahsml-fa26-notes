# CP4 — 약한 기기용 수집 가속기의 첫 비용 모델

2026-10-31 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 그림은 체크포인트 보드 아티팩트.

## 왜 이 CP인가
CP3에서 정밀도 계약이 정해졌다: **수집은 INT8, 쿼리에서 상위 20개만 고정밀로 재순위.** 이제 처음으로 하드웨어 크기를 숫자로 정할 수 있다. 목표는 CP2에서 본 약한 기기 문제다. 저전력 E코어 하나로는 8시간치 밀린 수집(33만 건, 가정)을 10.3시간에 처리해 못 따라잡았다.
목표 (가정): **8시간치를 1시간 안에**, 그리고 새 글 하나는 5초 안에 (P99 길이 게시물).
NORTHSTAR 7번의 3번 질문("기존 하드웨어로 충분하지 않다는 근거")에 답하려면 이 노트북에 이미 있는 **NPU**도 같이 재야 한다.

## 환경·의존성 (CP3 표에 추가)

| 무엇을 | 왜 | 기대 | 이후 CP 의존성 |
|---|---|---|---|
| OpenVINO 2026.4.1 (`pip install openvino`) | 이 노트북의 Intel NPU(AI Boost)로 같은 인코더를 돌린다 | 장치 목록에 `NPU` (확인됨). NPU 플러그인은 FP16으로 계산 | 기존 하드웨어 기준선. 이후 iGPU 비교에도 같은 도구 |
| `models/variants/fp32_mask_bias.onnx` (git 제외, `src/bench_cp4.py`가 생성) | 이 NPU 드라이버의 컴파일러가 (1) I64 입력, (2) 그래프 안에서 int 마스크로 어텐션 마스크를 만드는 부분을 못 내림 | 어텐션 마스크를 밖에서 FP 덧셈 마스크(B,1,1,L)로 넣음. 계산은 같음. FP32와 코사인 0.99999 | NPU 측정 전부 |
| `src/model_cp4.py` | 분석 비용 모델 (Timeloop/Accelergy 전 단계) | 단가는 수업 L7 Horowitz 표 (45 nm, 0.9 V) | CP5에서 Timeloop/Accelergy로 검증할 대상 |

## 방법
1. **워크로드 해부** (`src/model_cp4.py`): CP2/CP3 코퍼스 2만 개의 실제 토큰 길이로 게시물당 MAC과 바이트를 센다.
2. **분석 비용 모델** (같은 파일 → `results/cp4/cp4_model.json`). 설계점 하나:
   - INT8 weight-stationary 배열 R×C → 가중치 GEMM 36개 (CP3 계약)
   - FP16 유닛 (R²/4 MAC/사이클) → QKᵀ, AV (CP2에서 FP16은 Recall 0.999)
   - 벡터 유닛 (R 원소/사이클) → LayerNorm, GELU, softmax, 잔차, 동적 양자화
   - 전역 SRAM: 활성값 + (가중치 전부 상주 또는 GEMM 하나씩 이중 버퍼로 스트리밍)
   - 선택: 배열 옆 32 KB 로컬 버퍼 (입력 재사용, INT32 누산)
   - DRAM: 가중치(상주가 아니면)와 임베딩 표
   - 단가 (L7, 45 nm): INT8 곱 0.2 + INT32 덧셈 0.1 pJ, FP16 곱 1.1 + 덧셈 0.4 pJ, SRAM 32비트 읽기 8 KB 5 / 32 KB 10 / 1 MB 100 pJ (사이 값은 로그 보간, 1 MB 위는 외삽), DRAM 32비트 640 pJ.
   - **모델에 없는 단가 (추정)**: PE 파이프라인 레지스터 0.5 pJ/MAC, 벡터 원소당 FP16 연산 5개. 누설 전력은 넣지 않음 (동적 에너지만).
   - 탐색: 배열 8/16/32/64, 0.5/1 GHz, 배치 1/8/32, 가중치 상주/스트리밍, DRAM 8.5/17 GB/s (가정), 로컬 버퍼 유무 = 192점. 게시물 2,000개 표본.
3. **기존 하드웨어 측정** (`src/bench_cp4.py` → `results/cp4/cp4_npu.json`), CP3와 같은 조건 (풀파워, 최고 성능 오버레이, AC, 브라우저 없음, GPU 계산 프로세스 없음 확인):
   - NPU, FP16, 배치 1, 길이 버킷 (32/64/128/256)으로 정적 모양 컴파일. 1,000개 속도·에너지 + 2만 개 품질.
   - NPU 처리량 모드: 배치 2 이상은 이 드라이버에서 어텐션 MatMul 컴파일 실패 → 배치 1 요청을 1/4/8개 동시에 (`AsyncInferQueue`, THROUGHPUT 힌트).
   - NPU 고정 길이 호출 시간 (버킷별 100회).
   - CPU 약한 기기 기준선을 CP3 계약으로 다시: 저전력 E코어 1개, 채널별 INT8.

NPU 고정 길이 호출 (버킷별 100회): L = 32: 4.1 ms, 64: 6.2 ms, 128: 16.2 ms, **256: 53.5 ms**. 실효 113–225 GOPS (FP16). 이 버킷 시간으로 예측한 평균 33 ms/게시물이 실측 30–31 ms와 맞으므로, 느린 것은 호스트 부담이 아니라 NPU 계산 자체다.
Intel 사양의 NPU 최대치는 **INT8 11 TOPS** (Intel ARK, Core Ultra 9 185H). 실효치는 그 1–2%다 (FP16이라 최대치가 더 낮을 수 있음, FP16 최대치는 미확인).

## 해석
1. **약한 기기의 목표는 아주 작은 하드웨어로 충분하다 (추정).** INT8 16×16 배열(256 MAC) + 2 MB SRAM + 로컬 버퍼면 8시간치를 56분에, 게시물당 8.6 mJ, 평균 0.85 W. 45 nm 단가라 최신 공정이면 더 싸다.
2. **에너지를 지배하는 것은 연산이 아니라 데이터 이동이다.** MAC은 6%뿐. 로컬 버퍼 하나가 4.9배를 가른다 (L10 데이터플로 강의의 결론 그대로). 벡터 연산(LayerNorm, GELU, softmax)도 15%로 무시 못 한다.
3. **가중치 10.6 MB를 칩에 다 올리는 것은 이득이 아니다** (이 단가로는). 게시물마다 DRAM에서 가중치를 흘려 넣는 편이 더 쌌다. 다만 1 MB 넘는 SRAM 단가를 외삽했기 때문에 가장 불확실한 결론이다 → CP5에서 Accelergy/CACTI 단가로 다시 본다.
4. **기존 NPU는 목표를 못 지킨다 (측정, 이 드라이버·도구 기준).** 174분으로 목표의 약 3배. 이유는 계산이 느려서다: 최대치의 1–2%만 쓰고, 긴 게시물(L = 256, 전체의 17%가 잘릴 만큼 많음)에서 특히 느리고, 배치 2 이상은 컴파일되지 않는다. 대신 FP16이라 **품질은 재순위 없이 0.996**이고, 활성 에너지 41 mJ는 CPU 저전력 코어(54 mJ)보다 작다.
5. **그래서 하드웨어의 몫(P) 후보가 좁혀진다.** "MAC이 부족하다"가 아니다 (256 MAC이면 충분). 후보는 (a) 길이가 들쭉날쭉한 짧은 시퀀스를 배치 1로 처리할 때 범용 NPU가 거의 놀고 있다는 것, (b) 그래서 비용이 데이터 이동과 벡터 연산에 있다는 것. 단, (a)가 NPU 구조 탓인지 드라이버·컴파일러 탓인지는 아직 구별 못 했다. 이건 NORTHSTAR 7-3에 답하기 전에 반드시 가려야 한다.
6. **CPU 저전력 코어도 INT8로 바꾸면 8시간 안에는 따라잡는다** (FP32 620분 → INT8 286분). 하지만 "1시간"이라는 목표에는 5배 모자란다. 목표 자체(1시간)는 가정이므로 출처나 사용자 시나리오로 정당화가 필요하다.

## 한계
- 분석 모델은 누설 전력, 제어, 온칩 연결망을 빼고, 1 MB 위 SRAM 단가를 외삽했다. 공정(45 nm)이 실측 칩(Intel 4)과 다르므로 모델 J와 실측 J를 직접 나누지 않는다.
- 실측 "활성 J"는 직전 2초 유휴 전력을 뺀 값이라 유휴 전력이 흔들리면(6–9 W) 같이 흔들린다 (NPU 동시 요청 실험에서 0.041–0.085).
- NPU는 FP16만 쟀다. NNCF로 INT8을 만들면 더 빠를 수 있다 (미측정).
