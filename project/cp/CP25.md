# CP25 — 원격 커뮤니티: 껐다 켜도 같은 신원, 집에서 집으로 (Tailscale), 여러 날

2026-11-07 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP24.md](CP24.md) (다음 CP 줄: 11-04 세 대 실측).

## 왜 이 CP인가
- CP24의 다음 CP는 11-04에 팀원 셋이 만나서 하는 세 대 실측이었다. **만나는 것이 어려워졌다** (2026-11-07). 대신 각자 집에서 Tailscale로 박스를 묶는다.
- 원격 실험은 만나서 하는 두 시간보다 길다. 며칠 동안 셋이 각자 편할 때 켜고 끈다. 그런데 지금 데모 박스는 모든 상태를 메모리에만 둔다 (CP24 한계):
  - 껐다 켜면 새 신원이 된다. 글마다의 일회용 Ed25519 키도 사라져서 **예전 글을 지울 수 없다**.
  - 글과 색인도 사라진다. 셋이 각자 한 번씩 껐다 켜면 커뮤니티의 글이 모두 사라질 수 있다.
  - (계획을 쓰며 찾음) 신원만 저장하면 더 나쁘다. 창 안에서 쓴 번호(`World24.used`)가 0으로 돌아가서, 다시 켜고 글을 쓰면 **같은 번호를 다시 써서 자기 비밀이 드러난다** (벌칙). 실제 RLN 클라이언트도 쓴 번호를 저장해야 한다.
  - (계획을 쓰며 찾음) 지금도 망각이 새고 있다. 지운 글의 암호문이 `self.msgs`에 남아 `/sync`로 늦게 켠 박스에 계속 간다 (지운 기록과 함께 가서 화면에는 안 보이지만, 암호문은 퍼진다). 디스크에 저장하면 이 새는 곳이 디스크까지 간다.
- 형식: **목적형**. [구현] 박스 상태 저장·복원, 망각 지키기, 측정 로그, Tailscale 주소 [데모·측정] 팀원 둘과 원격 실측.
- 답할 질문:
  - 껐다 켜도 같은 신원, 같은 글, 같은 색인으로 돌아오는가? 쓴 번호를 다시 쓰지 않는가?
  - 저장을 넣어도 망각이 지켜지는가 (지운 글은 디스크에도, 동기화에도 없다)?
  - 집과 집 사이(진짜 인터넷, NAT, 중계)에서 새 글이 모든 켜진 박스에서 검색되기까지 얼마나 걸리는가? 며칠 꺼져 있던 박스가 따라잡는 데는?
  - 맥과 윈도우 CPU에서 인코딩 시간은 (로드맵 "Mac·Windows 실측")?

## 그림 (설계, 결과 전)
박스 하나의 저장 (상태 폴더 `project/state/box{i}/`, git 제외):
```
 identity.json   신원 비밀 a0, 그룹(tier), 쓴 번호 used{(공간, 창): 다음 번호}     ← 쓰기 전에 먼저 저장 (번호를 다시 쓰지 않게)
 keys.json       내 글마다의 일회용 Ed25519 비밀키 (mid → 32바이트)               ← 지우기 권한
 msgs.jsonl      받은 메시지 봉투, 도착 순서 (암호문 그대로; 평문은 저장 안 함)
 img/<mid>.rgb   사진 본문 224×224×3
 tomb.json       지운 글 (mid, 작성자 일회용 공개키): 늦게 오는 원본을 버림

켜기:  identity.json → World24에 내 a0, used 넣기 → keys.json → msgs.jsonl을 도착 순서로 다시 deliver
       (다시 보내지 않음, 사진은 img/에서) → 인코더가 색인을 다시 만듦
지우기: delete가 적용되면 → msgs.jsonl에서 원본 봉투를 빼고 다시 씀, img/<mid>.rgb 삭제, tomb.json에 추가
       → /sync는 지운 원본을 주지 않음 (지운 기록은 줌)
늦은 지우기: 원본보다 delete가 먼저 오면 → (target, delete의 공개키)를 tomb에 → 원본이 오면 공개키가 같을 때만 버림
```
측정 로그 (상태 폴더의 `events.jsonl`, 평문 없음):
```
 recv   {t, mid, frm, kind, verdict}          받은 시각 (이 컴퓨터 시계)
 write  {t, mid, kind}                        내가 쓴 시각
 enc    {t, mid, what, ms, tokens}            이 CPU의 인코딩 시간 (W4)
 index  {t, mid}                              검색에 들어간 시각 (W1: 정착 = index 시각 − 작성 시각)
 peer   {t, peer, rtt_ms, offset_ms}          20초마다 /hello 왕복 시간과 시계 차 (NTP 방식 추정)
 sync   {t, peer, new}  ·  start {t, restored, ms}
```
원격 (계획 추가):
```
 맥북 A (집)                맥북 B (집)                윈도우 (집)
 100.x.x.x  ◀── WireGuard 직접 (NAT 뚫기), 안 되면 Tailscale 중계(DERP) ──▶  100.y.y.y ...
 lan.py --hosts 100.a,100.b,100.c --me i --room-pass "DM으로 전한 암호"     ← 코드는 CP24 그대로
 events.jsonl 셋을 모아 → remote_report.py → 정착 시간, 따라잡기, RTT, CPU별 인코딩
```

## 대안 (결과를 보기 전에 적음)
- **저장 형식**
  - S-a: JSON 파일 + 메시지 JSONL (도착 순서), 지울 때 다시 씀. 의존성 없음, 사람이 읽을 수 있음. ← 고름
  - S-b: SQLite (표준 라이브러리). 지우기가 쉽지만 지운 행이 빈 페이지에 남는다 (`secure_delete`와 VACUUM이 필요).
  - 바꿀 조건: 메시지가 10⁴개를 넘거나 다시 쓰기가 1초를 넘으면 S-b (보관과 메모리 CP에서).
- **켤 때 색인**
  - E-a: 임베딩을 저장하지 않고 다시 인코딩한다 (저장한 것과 색인이 어긋날 일이 없음). ← 고름
  - E-b: 임베딩도 저장. 바꿀 조건: 켜기가 60초를 넘으면.
- **신원 비밀 보호**
  - K-a: 파일 + OS 권한 (맥에서 0600). ← 고름 (팀 셋의 실험)
  - K-b: 암호로 잠금. 바꿀 조건: 팀 밖 사람이 쓰게 될 때. 키 탈취 대응은 NORTHSTAR 5의 열린 문제로 남는다.
- **집과 집 연결**
  - T-a: Tailscale. 코드 변경 없음. 단 조정 서버가 tailnet의 기기와 키를 안다 (내용은 못 봄, WireGuard 종단 간). **실험 비계이지 설계가 아니다.** ← 고름 (지금)
  - T-b: 각자 공유기 포트 포워딩. 팀원이 공유기를 못 만질 수 있음.
  - T-c: 박스가 직접 NAT 뚫기 + 박스가 하는 중계. 설계가 가야 할 곳. 별도 CP.
  - NORTHSTAR 7의 합리화 테스트 1(불변식: 특권 운영자 없음)에 T-a는 "아니오"다. 이유: 연결 시험을 위한 임시 도구이고, 박스의 프로토콜·내용·신원에는 관여하지 않는다. CHECKPOINT에 적는다.
- **리포**: 새 리포를 만들지 않는다 (데모 박스가 `src/sim`을 같이 써서 X2의 근거가 같은 코드). 바꿀 조건: 팀원이 코드를 push해야 할 때, 박스가 따로 설치되는 제품이 될 때, 팀 밖 사람이 참여할 때 → `git subtree split`.

## 판정 규칙 (결과를 보기 전에 적음)
- **P1 (껐다 켜기, 이 PC)**: 박스 셋 (사설 IP, CP24 R3처럼). 박스 0이 글·사진·투표를 쓴 뒤 끄고 켠다. 통과 = 신원(commit) 같음, 글 수·색인 수(텍스트, 사진)가 끄기 전과 같음, 켠 뒤 자기 예전 글을 지울 수 있고 모든 박스에서 사라짐, 남은 몫이 이어짐.
- **P2 (번호를 다시 쓰지 않음)**: 같은 창 안에서 글 → 끄기 → 켜기 → 글. 통과 = 벌칙 알림 0개, 두 글 모두 모든 박스에.
- **P3 (망각)**: 지운 뒤 지운 박스와 받은 박스 모두 `msgs.jsonl`에 원본 봉투가 없고 `img/`에 사진이 없고, `/sync`가 원본을 주지 않음. 지우기가 원본보다 먼저 온 박스(원본을 주는 옛 박스를 흉내 냄)는 원본을 버림. 남이 만든 가짜 지우기(공개키 다름)는 원본을 버리게 하지 못함.
- **P4 (측정 로그)**: 박스 셋의 `events.jsonl`로 `remote_report.py`가 정착 시간·RTT·시계 차·인코딩 시간을 낸다. 한 컴퓨터라 시계 차는 |offset| < 5 ms여야 한다.
- **W (원격, 팀원 둘과)**: 아래 숫자를 낸다. 통과선은 W1만 둔다.
  - W1: L1–L7을 Tailscale 위에서. 그리고 켜진 박스들 사이 새 텍스트 글의 정착 시간 P99 ≤ 5 s (NORTHSTAR 6의 "새 게시물 5초 안 검색 가능"). 시계 차를 offset으로 고친 값, 고치기 전 값 둘 다 적는다.
  - W2: 경로(직접 / 중계, `tailscale status`)와 RTT, 사진 당기기 시간.
  - W3: 1시간 이상 꺼졌던 박스가 켜진 뒤 따라잡는 시간 (밀린 메시지 수와 함께).
  - W4: 기기별 MiniLM 한 글·CLIP 사진 한 장 인코딩 시간 (예비 측정: 각자의 전원·발열 조건을 확인하지 않음).
  - W5: 며칠 동안 쓴 글 수, 글 길이(토큰), 사진 비율. 내용은 기록하지 않는다 (개수만). 표본이 작아 일화로만 쓴다.
- P1–P4가 이 PC에서 통과해야 팀원에게 원격 안내를 보낸다.

  - 새 텍스트 글 정착 P50 0.03 s, 최대 0.11 s (n = 8). 사진 0.14 s (n = 2).
  - 인코딩: MiniLM INT8 한 글 P50 3.5–3.9 ms, CLIP 사진 한 장 102–109 ms (스레드 1).

### 계획을 쓰며, 시험하며 찾은 것
- **신원만 저장하면 자기 비밀이 드러난다** (계획 때 찾음). 쓴 번호(`used`)를 함께, 그리고 메시지가 나가기 전에 저장한다. P2가 그 확인이다.
- **지운 글의 암호문이 `/sync`로 계속 퍼지고 있었다** (CP24 데모, 계획 때 찾음). 이제 지운 박스는 원본을 디스크와 동기화에서 빼고, 지우기가 먼저 온 박스는 원본이 와도 버린다 (`tomb`). 지우기의 공개키가 원본의 일회용 공개키와 같을 때만 버리므로 남이 지우게 할 수 없다 (P3).
- **토큰 수 버그 (CP24 데모)**: `tokenizer.json`이 128로 고정 패딩한다. 그래서 `tokenize()`를 한 번도 부르지 않은 토크나이저의 `encode()`는 어떤 글이든 128을 준다.
  - 박스(`box_server.write`): 켠 뒤 첫 글은 짧아도 128토큰으로 세어 텍스트 번호 2개를 썼다. 정직한 사람이 몫을 더 쓸 뿐이고 박스 검사(번호 ≥ 필요)는 통과한다. attention mask로 세게 고쳤다.
  - CP24 R2 장면 실행기(`x2.py`)는 **모든** 텍스트 메시지를 128토큰(번호 2개)으로 만들었다. `no_padding()`으로 고치고 다시 돌렸다 (`results/cp25/x2_tokfix.json`):

| | CP24 R2 | 고친 뒤 |
|---|---|---|

### W1–W5: 원격 (팀원 둘과) — 돌리지 않음
- 돌리기 전에 전제 둘이 무너졌다 (2026-11-07, 사용자와 문답).
  1. **팀원은 며칠씩 켜 둘 수 없다.** 상시 켜 둘 수 있는 것은 사용자의 미니 PC 하나다. 그러면 실험은 "셋이 각자 켜고 끈다"가 아니라 **상시 박스 하나 + 잠깐씩 들어오는 박스들**이어야 한다. 이게 NORTHSTAR 3의 상시 홈 노드 그림에 더 맞다.
  2. **박스 사이 교류가 폴링이었다.** CP24 데모 박스는 20초마다 목록의 **모든** 박스에게 가진 메시지 **전부**를 달라고 한다 (`sync_loop`, `/sync`). 박스 하나의 비용은 (n − 1) × M / 20 s, 네트워크 전체는 n(n − 1) × M이다. 쌓인 메시지 수 M도 n과 함께 늘어서 사용자 수에 대해 약 n³으로 는다 (추정: 코드에서 셈). 20초에는 근거가 없고, CP24의 대안 표에도 오르지 않았다.
- 2는 데모만의 문제가 아니다. 시뮬레이터(DayNet)는 새 글의 밀어 주기(push 가십)만 모델링한다. 꺼졌던 박스가 **무엇을 놓쳤는지 어떻게 아는지**는 설계에 없다. CP19의 밀린 수집은 "놓친 것만 내려받는다"고 가정했다. `src/sim`에는 동기화가 없어서 CP17–CP23의 설계 규모 숫자에 폴링이 섞이지는 않았다 (확인: `src/sim`에 sync 없음).
- 사용자 원칙 (2026-11-07): **하드웨어 컴퓨트를 최적화해야 한다는 주장은 알고리즘 로직을 착취할 수 있는 만큼 다 착취했다는 가정 위에서만 의미가 있다.** 폴링으로 생긴 부하는 하드웨어의 근거가 될 수 없다. 그래서 원격 실측(W)을 하지 않고, 교류 방식을 다음 CP에서 처음부터 세운다. 팀원에게 보여 주는 것도 그 뒤로 미룬다.
- 만든 측정 도구(`events.jsonl`, `remote_report.py`, 시계 차 보정)와 `REMOTE.md`는 다음 원격 실측에서 쓴다. REMOTE.md의 "며칠 동안 셋이" 전제는 그때 고친다.

## 답
1. **껐다 켜도 같은 회원인가?** 그렇다 (P1, P1b, P2). 쓴 번호를 함께 저장해야 자기 비밀을 드러내지 않는다.
2. **저장을 넣어도 망각이 지켜지는가?** 그렇다 (P3). 저장 전부터 있던 구멍(`/sync`로 지운 글이 퍼짐)도 막았다.
3. **집과 집 사이 정착 시간, 따라잡기, 기기별 인코딩은?** 재지 않았다. 교류 방식이 폴링이라 그 위의 숫자는 설계를 대표하지 못한다.
4. 계획에 없던 답: CP24 데모의 토큰 수 버그 (CP24 D7 정정 23 → 22번), 그리고 **교류 조건이 설계에 없다**는 것.
