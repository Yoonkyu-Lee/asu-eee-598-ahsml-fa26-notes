# CP15 — 실물만 빼고 다 있는 커뮤니티: 시스템 설계

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 그림은 아키텍처 보드(L−1 "시스템 전체")와 체크포인트 보드.

## 왜 이 CP인가
2026-11-01 NORTHSTAR 6을 고쳤다: 실물 기기와 반도체만 빼고 다 만든다. 이미지 글도 범위에 넣는다 (사용자 결정).
지금 칩 숫자(CP12–CP14)는 가정 세 개 위에 있다: 박스마다 하루 10⁶건(모든 글을 받음), 메시지 1 KB, 100 Mbps 폭주. 이미지는 한 번도 다루지 않았다.
이번 CP는 코드 전에 **시스템 전체의 설계**를 정한다: 무엇을 진짜로 돌리고 무엇을 모델로 대신하는지, 흔적을 어떻게 남기는지, 어떤 순서로 만드는지.
- 형식: **목적형**. [디자인] [조사].
- 답할 질문: 노드 박스 N대와 사용자 M명을 노트북 한 대에서 어떻게 돌리나? 그 결과가 칩 설계로 어떻게 돌아가나? 보고서의 주장마다 근거가 무엇이고 빈칸은 어디인가?

## 1. 주장–근거 표 (최종 보고서 기준, 빈칸이 이후 CP를 정한다)
| | 주장 | 지금 근거 | 빈칸 |
|---|---|---|---|
| C1 | server-blind 커뮤니티에서 운영자 일은 박스의 수집(검증·복호화·인코딩·색인)과 쿼리로 옮겨 온다 | CP1 측정 (텍스트만) | **박스 하나가 실제로 받는 양**(구독·복제 정책, 시간대 몰림)이 가정. **이미지** 없음 |
| C2 | 기존 박스급 하드웨어는 ML은 되지만 증명 폭주를 못 막는다 | CP5–CP6 측정·출처, CP12 모델 | 같은 자원(면적·공정)에서의 공정 비교 없음 |
| C3 | 우리 칩(11.3 mm², 45 nm)은 100 Mbps 폭주를 ≤ 1.05 W로 막는다 | CP9–CP10 합성(곱셈기), CP11–CP14 모델 | 덧셈기·시퀀서 RTL 없음, 이용률 가정, 폭주가 박스에 닿는 모양(이웃 수)이 가정 |
| C4 | 평소 하루 박스 전력은 호스트 유휴가 정한다 | CP12 모델 | 실제 박스별 부하(시뮬레이션), 이미지 인코더 몫 |
| C5 | 사용성(검색, 피드, 이미지, 방, 망각)을 버리지 않는다 | 없음 | **구현과 데모** |
| C6 | 스팸이 수집 자원을 고갈시키지 않는다 (불변식 4) | CP13–CP14 모델 (폭주 모양 가정) | 공격자를 넣은 네트워크 시뮬레이션 |

## 2. 그림 (설계, 결과 전)
```
 ┌─ 시나리오 (평소 / 저녁 피크 / 오프라인 후 밀린 수집 / 스팸 폭주) ─────────────────────────────┐
 │ 사용자 M명: 행동 모델 (접속, 글, 이미지 글, 열람, 검색, 투표, 삭제, 방 대화)  공격자: 틀린 증명, 봇 │
 └──────────────┬────────────────────────────────────────────────────────────────────────────────┘
                ▼ 클라이언트 API (같은 API를 웹 UI도 씀 → 사람이 직접 써 볼 수 있음)
 ┌─ 노드 박스 × N (실제 코드, 기능은 진짜) ──────────────────────────────────────────────────────┐
 │ 네트워크: gossip (gossipsub v1.1 규칙: 메시 D, 검증 후 전달, 벌점), 서브 구독, 동기화(밀린 수집)   │
 │ 수집: 서명 → 증명 검증 → 복호화 → 텍스트 인코딩 / 이미지 인코딩 → 색인 → 저장                    │
 │ 쿼리: 검색, 피드 랭킹, 열람    망각: 삭제 전파    방: 그룹 키                                    │
 │ ── 가상 가속기: verify / encode_text / encode_image 를 부르면                                   │
 │      결과는 CPU에서 진짜로 계산 (같은 메시지는 한 번만 계산해 모든 박스가 나눠 씀)                │
 │      시간·에너지는 칩 모델 (CP11–CP14 사이클 모델, CP12 Timeloop/Accelergy)                     │
 │    호스트 일(복호화, 색인, 검색)의 시간은 Pi 5급 환산                                            │
 └──────────────┬────────────────────────────────────────────────────────────────────────────────┘
                ▼ 흔적 (세 단계)
   시스템: 메시지마다 언제 어느 박스에 닿아 무엇이 됐나 (가상 시각)
   박스:   유닛별 바쁨 타임라인 (Perfetto/Chrome trace 형식 → 브라우저에서 파형처럼 확대)
   유닛:   표본 몇 건만 사이클 단위 (CP11 스케줄러의 연산 발행 기록)
                ▼
   박스별 초 단위 작업량 → 칩 크기·전력 다시 판정 (CP12–CP14 규칙 그대로)
```

### 에뮬레이션인가 시뮬레이션인가
- **기능은 에뮬레이션**: 박스 소프트웨어는 실제 코드다. 실제 암호문, 실제 서명, 실제 임베딩, 실제 검색 결과. 다른 하드웨어(노트북 CPU)에서 같은 기능을 낸다.
- **시간·에너지는 시뮬레이션**: 박스 N대를 실시간으로 돌릴 수 없으니 가상 시계(이산 사건)로 돌린다. 각 작업의 시간은 칩 모델과 Pi 5 환산에서 온다.
- 데모 모드만 실시간: 박스 몇 대를 실제 프로세스로 띄우고 웹 UI로 글을 쓴다.
- 칩 내부는 RTL이 아니다 (곱셈기만 RTL). 신호 수준 파형은 곱셈기(VCS)에만 있고, 나머지는 거래 수준(TLM) 흔적이다.

## 3. 대안과 판정 규칙 (결과를 보기 전에 적음)

### 실행 방식
| | 방식 | 박스 수 | 무엇을 잃나 |
|---|---|---|---|
| E1 | 전부 실시간 프로세스 | ~10 | 규모. 시간이 노트북 속도에 묶임 |
| **E2** | 이산 사건 + 기능 실행 + 메시지별 결과 공유 | ~100–1,000 | 계산 비용이 메시지 수에 비례 |
| E3 | 통계만 (기능 없음, 비용 표본) | ~10⁵ | 기능 정확성, 데모 |
- 규칙 X1: E2를 기본으로 한다. 박스 100대, 사용자 10,000명, 가상 하루가 노트북 CPU에서 2시간 안에 끝나지 않으면 대부분의 박스를 E3로, 표본 박스만 E2로 돈다. 데모는 E1.
- 규칙 X2: 같은 소규모 시나리오(박스 5대)를 E1과 E2로 돌려 박스별 작업 수가 같아야 한다 (같지 않으면 E2를 고친다).
- GPU는 쓰지 않는다 (사용자가 GPU를 쓰는 중일 수 있음, project/CLAUDE.md 5).

### 네트워크
| | 방식 | 판정 |
|---|---|---|
| N1 | 실제 libp2p (Rust/Python) | 데모 모드 후보 |
| **N2** | gossipsub v1.1 규칙을 직접 구현 (메시 차수, 검증 후 전달, P4 벌점, 끊기) | 시뮬레이션 기본: 흔적을 다 남길 수 있음 |
| N3 | 단순 범람 | 기준선 (gossip이 폭주를 얼마나 줄이나 비교용) |
- 규칙 X3: 매개변수는 출처 기본값(gossipsub 명세, nwaku)에서. 출처 없는 값은 (추정)으로 적고 민감도를 돈다.

### 복제 정책 (박스 하나가 받는 양을 정함 → 칩 크기에 직결)
| | 정책 |
|---|---|
| P-all | 모든 박스가 모든 공개 글을 받는다 (지금 칩 가정) |
| P-sub | 주인이 구독한 서브만 받는다 |
| P-sub+k | 구독한 서브 + 가용성을 위해 무작위 k개 서브를 더 맡는다 |
- 규칙 X4: 정책마다 (박스별 수집량, 글 가용성 = 작성자가 꺼졌을 때도 읽을 수 있는 비율, 검색 결과의 범위)를 재고, 가용성 ≥ 99%를 지키는 가장 가벼운 정책을 기본으로 한다. 칩 크기는 그 정책의 P99 박스로 다시 판정한다.

### 증명과 암호
- 서명·암호화(Ed25519, ChaCha20-Poly1305)는 진짜.
- RLN 증명: 시뮬레이션에서는 "맞음/틀림" 표시 + 검증 비용은 모델 (진짜 증명 생성은 사용자 기기 몫이라 박스 부하가 아님). 데모 모드에서 진짜 Groth16을 붙일지는 나중에 정한다 (`src/crypto_bench`의 arkworks).
- 방(사적 그룹): 그룹 키 하나로 암호화 (MLS 같은 키 갱신은 뒤로).

### ML
| | 텍스트 | 이미지 | 검색 |
|---|---|---|---|
| M1 | MiniLM (지금) | CLIP ViT-B/32 이미지 탑 | 텍스트→텍스트는 MiniLM, 텍스트→이미지는 CLIP 텍스트 탑도 필요 (모델 3개) |
| M2 | CLIP 텍스트 탑 | CLIP 이미지 탑 | 한 공간에서 다 (모델 2개, 텍스트 검색 품질은 따져야 함) |
- 규칙 X5: CP2–CP3의 텍스트 Recall@10 ≥ 0.95 계약(FP32 MiniLM 기준)을 M2가 지키면 M2 (모델 수가 적어 칩이 단순). 못 지키면 M1.
- 이미지 인코더의 칩 비용은 CP12 방식(Timeloop/Accelergy)으로 따로 잰다. 인코더 전역 SRAM 크기(원래 CP15 계획)는 이때 같이 정한다: 이미지가 들어오면 SRAM 요구가 바뀌기 때문.

### 행동 모델
- 매개변수(글 빈도 분포, 시간대 곡선, 이미지 비율, 읽기:쓰기, 검색 빈도, 서브 인기 분포)는 출처에서 (Reddit·커뮤니티 공개 통계, 논문). 없으면 (추정) + 민감도.
- 규칙 X6: 칩 판정은 매개변수 민감도 범위의 가장 나쁜 쪽(P99 박스, 피크 시간)으로 한다.

## 4. 순서 (각 CP 끝에 쓸 수 있는 결과가 남게)
| CP | 무엇 | 끝나면 남는 것 |
|---|---|---|
| 16 | 행동 매개변수 조사 + 시뮬레이터 핵심 (이산 사건, gossip, 사용자, 텍스트 글, 흔적) | 박스별 텍스트 수집량 분포 (C1, C4 빈칸 일부) |
| 17 | 박스 기능 스택 (수집·쿼리·피드·망각·방) + 가상 가속기 + 이미지 글 | 기능이 도는 커뮤니티, 박스별 전체 작업 기록 (C5) |
| 18 | 이미지 인코더의 칩 비용 + 인코더 SRAM 크기 (Timeloop/Accelergy) | 이미지가 들어간 칩 견적 |
| 19 | 시나리오 실행: 평소, 피크, 밀린 수집, 폭주(공격자 + 이웃 구조) | 칩 크기·전력 재판정 (C3, C4, C6) |
| 20 | 같은 자원 공정 비교 + ablation | C2, 보고서 중심 표 |
| 21 | 데모 (웹 UI, 박스 몇 대 실시간) | 발표용 |
중간 보고서(13주차)는 CP12–CP14 결과 + 이 설계로 쓴다.

## 5. 조사 (이 CP 안에서)
- 노트북 `.venv`에 있는 것: onnxruntime 1.31, OpenVINO 2026.4, cryptography 50, networkx, numpy. 없는 것: torch, simpy → 이산 사건 엔진은 heapq로 직접 (흔적을 남기기 쉬움).
- CLIP 모델 파일은 아직 없음. 내려받기는 사용자 허락 후 (CP17).
