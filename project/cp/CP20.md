# CP20 — 같은 조건 비교 + 하나씩 끄기 + 사진 품질

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP19.md](CP19.md). 그림은 아키텍처 보드(L1 "같은 조건 비교")와 체크포인트 보드.

## 왜 이 CP인가
CP15 주장 표의 C2 ("기존 박스급 하드웨어는 ML은 되지만 증명 폭주를 못 막는다")는 아직 CP12의 "박스마다 하루 10⁶건" 표에 서 있다. CP19가 장면(S1–S5)과 계약(K1–K5)을 만들었으니, 같은 장면·같은 계약·같은 박스 소프트웨어(O-b, 실시간 먼저)로 기존 조합과 우리 칩을 다시 비교한다. 그리고 CP19에서 고른 손잡이를 하나씩 꺼서 각각이 무엇을 지키는지 보인다 (보고서의 중심 표).
같이 푸는 빈칸 둘 (사진 데이터 받음, 사용자 허락 2026-11-01):
- CLIP 이미지 탑을 INT8로 돌려도 되나? CP18에서 정적 INT8이 합성 그림 보정으로 FP32 대비 0.798 (뒤집을 조건 걸림).
- Hailo-8L의 MiniLM은 128토큰 고정이다. 128에서 자르면 검색 품질이 얼마나 떨어지나? (CP12에서 "재지 않음")
- 형식: **목적형**. [측정] (사진 품질, CPU 인코더 시간) [디자인] (CP19 박스 모델로 비교·하나씩 끄기).
- 답할 질문:
  - 같은 장면과 계약에서 Pi 5 CPU만 / Pi 5 + Hailo-8L / 검증 칩 + Hailo-8L / 우리 칩 중 무엇이 어디를 지키나? 전력은?
  - CP19의 손잡이(증명 먼저, 층 양보, 실시간 먼저, 한도 L-b, 블록 끄기)를 하나씩 끄면 무엇이 깨지나?
  - 증명 먼저(O-b)로 재전송 섞기 공격이 사라졌으니, 검증 유닛을 CP14보다 줄일 수 있나?
  - 사진에서 INT8 이미지 탑은 검색 품질을 지키나?

## 그림 (설계, 결과 전)
```
 같은 장면 S1–S5, 같은 계약 K1–K5, 같은 박스 소프트웨어 (증명 먼저, 실시간 먼저, 검색어 우선)
 ┌──────────────┬──────────────────────┬────────────────────────┬───────────────────────────┐
 │ X0 Pi 5만     │ X1 Pi 5 + Hailo-8L    │ X2 Pi 5 + 검증 칩       │ X3 Pi 5 + 우리 칩 (CP19)   │
 │              │                      │      + Hailo-8L         │                           │
 │ 검증: CPU 4코어│ 검증: CPU 4코어        │ 검증: 6×6 (2.12 mm²)    │ 검증 6×6 + 인코더 8×8·1 MB │
 │ 인코더: CPU   │ 인코더: Hailo (128토큰) │ 인코더: Hailo (128토큰)  │ (5.61 mm²)                │
 │ 1코어         │ 작업 단위 우선순위      │ 작업 단위 우선순위        │ 층 경계 양보               │
 └──────────────┴──────────────────────┴────────────────────────┴───────────────────────────┘
   Jetson Orin Nano: 검증(CPU 6코어)만 출처가 있어 폭주 줄에만 넣음. GPU 인코더 수치는 출처 없음.

 하나씩 끄기 (X3에서):  증명 먼저 → 서명 먼저 │ 층 양보 → 작업 단위 │ 실시간 먼저 → FIFO │ 한도 L-b → L-a
                        검증 6×6 → 5×5 · 5×6 │ 인코더 8×8 → 16×16 │ 블록 끄기 → 항상 켬
```

## 대안과 판정 규칙 (결과를 보기 전에 적음)

### 결정 1: 이미지 탑 정밀도 (사진, 측정)
- 데이터: COCO val2017 이미지 5,000장 + 캡션 25,014개 (images.cocodataset.org, val2017.zip 815,585,330 B, annotations_trainval2017.zip 252,907,541 B → `data/coco/`, git 제외). 앞 300장 = 보정용, 나머지 4,700장 = 평가.
- 대상: FP32, 동적 INT8 (CP17), 정적 INT8 합성 보정 (CP18), **정적 INT8 사진 보정** (새로), 필요하면 혼합 (첫·마지막 블록을 양자화에서 뺌).
- 지표: (a) 캡션 → 그림 Recall@1/5/10 (CLIP 텍스트 탑 FP32 질의, 4,700장 중), (b) 이웃 일치 Recall@10 (같은 캡션 질의에서 FP32 색인의 상위 10과 겹치는 비율; NORTHSTAR 6 계약 ≥ 0.95), (c) 같은 그림 FP32와의 코사인 최저·0.1% 분위수, (d) 서로 다른 그림 FP32끼리 최대 코사인 (CP17 I3 허용 오차를 사진으로 다시).
- **규칙 P**: (b) ≥ 0.95 **그리고** (a) Recall@10이 FP32보다 0.01 넘게 낮지 않은 것 중 가장 싼 것: 정적 INT8 (사진 보정) → 혼합 → FP16. 정적 INT8이 통과하면 CP18의 "혼합 정밀도 따로 따짐"은 닫는다.

### 결정 2: Hailo 조건의 품질 (측정)
- CP3 자기 검색(코퍼스 2만, 제목 질의 1,000)에서 MiniLM FP32를 128토큰에서 자른 Hit@10 vs 256토큰.
- 판정에는 쓰지 않고 비교 표에 적는다 (같은 Recall 규칙: 0.5%p 넘게 떨어지면 "같은 품질 아님"으로 표시).

### 결정 3: 같은 조건 비교 (C2)
- **규칙 F**: C2가 선다 = X0·X1·Jetson 중 S4 (100 Mbps 틀린 증명, 증명 먼저 + 연결 끊기)에서 K1·K4를 지키는 것이 없고 X3는 지킴. 하나라도 지키면 C2를 고친다.
- **규칙 A**: 한 칩(X3)을 유지 = X2가 지키는 계약을 X3도 다 지키고, S1 박스 전력이 X2 이하 (Hailo 유휴 0으로 둔 X2, 즉 X2에 가장 유리하게). 아니면 X2 (검증 칩 + 기존 인코더 칩)를 대안으로 올림.
- S5는 K_crit (한도 L-b)만 적는다 (CP19 규칙 S: 칩으로 못 막는 공격이라 판정에 안 씀).

### 결정 4: 검증 유닛 다시 (증명 먼저 이후)
- CP14 크기(6×6)는 "맞는 증명 재전송 15% 섞기"가 최악이었다. 증명 먼저(O-b)에서는 재전송이 표 찾기에서 끝나서 최악이 "전부 틀림"(f = 1)이 된다.
- **규칙 V2**: CP14 V4 곡선의 16가지 중 S4 (증명 먼저 + 끊기, 전부 틀림)에서 K1·K2·K4·K5를 지키고 **검증 유닛 바쁨 ≤ 0.95**인 것 중 면적이 가장 작은 것. 6×6보다 작으면 CP14를 뒤집는다.
- 뒤집을 조건: 맞는 증명을 싸게 많이 얻는 길(신원 비용이 낮음)이 생기면 섞기 공격이 돌아오므로 6×6으로.

### 결정 5: 하나씩 끄기 (X3에서, ablation)
- 끄는 것: O-b → O-a, Q2 → Q1, 실시간 먼저 → FIFO, L-b → L-a, 검증 6×6 → 결정 4의 것, 인코더 8×8 → 16×16 (2 MB), 블록 끄기 → 항상 켬.
- 각 줄에 S1–S5의 계약 통과 여부, 칩 면적, 평소 칩 전력. 판정이 아니라 보고서 표.

## 결과

### 결정 1: 이미지 탑 정밀도 (측정, COCO val2017 평가 4,700장 · 캡션 23,513개)
| 변형 | 캡션→그림 R@1 | R@10 | 이웃 일치 R@10 (FP32 기준) | 같은 그림 FP32와 코사인 최저 / 0.1% / 중앙 | 규칙 P |
|---|---|---|---|---|---|
| FP32 | 0.310 | **0.671** | 1 | 1 | 기준 |
| 동적 INT8 (CP17) | 0.304 | 0.667 | 0.759 | 0.840 / 0.873 / 0.981 | 실패 |
| 정적 INT8, 합성 보정, 모든 연산 (CP18) | 0.197 | 0.527 | 0.410 | 0.048 / 0.102 / 0.813 | 실패 |
| 정적 INT8, 사진 보정, 모든 연산 | 0.194 | 0.516 | 0.403 | −0.126 / 0.137 / 0.809 | 실패 |
| **정적 INT8, 사진 보정, 칩과 같은 범위** (선형층만) | 0.297 | 0.660 (−0.011) | **0.631** | 0.752 / 0.791 / 0.935 | 실패 |
| 혼합 (위 + 패치 임베딩·블록 0·11은 실수, 노드 13개) | 0.302 | 0.664 (−0.007) | **0.814** | 0.952 / 0.966 / 0.988 | 실패 |
| FP16 가중치 (활성값 FP32, 지표용) | 0.310 | 0.671 | **0.999** | 1.000 / 1.000 / 1.000 | 통과 |
- **규칙 P → FP16.** 캡션→그림 Recall@10은 INT8도 0.7–1.1%p만 떨어지지만, 이웃 일치(NORTHSTAR 6의 "FP32 정확 검색 기준 Recall@10 ≥ 0.95")를 넘는 INT8 변형이 없다. CLIP의 그림 점수는 서로 가까워서 작은 오차로도 상위 10개가 바뀐다.
- CP18의 정적 INT8 품질 문제(0.798)는 보정 데이터보다 **양자화 범위**가 원인이었다: 기본 설정은 어텐션 행렬곱·덧셈까지 8비트로 만든다 (칩은 어텐션을 FP16으로 함). 칩과 같은 범위로 줄이면 같은 그림 코사인 중앙값 0.81 → 0.94.
- 사진에서 서로 다른 그림 FP32끼리 최대 코사인 0.984 (99% 분위수 0.714). INT8 같은 그림 최저(0.75–0.95)가 이보다 낮아 CP17 I3(작성자 임베딩 + 대조)는 사진에서도 INT8로는 안 됨.
- **칩 영향 (추정)**: 이미지 탑의 선형층을 FP16 유닛(8×8 배열에서 16 MAC/주기)에서 돌리면 한 장 0.143 → **0.552 s**, 27 → **64 mJ** (행렬곱 0.136 → 0.545 s). 면적은 그대로 (이미 있는 FP16 유닛). E2 (한 장 ≤ 1 s)는 지킴.

### 결정 2: Hailo 조건의 품질 (측정, CP3 자기 검색)
| MiniLM FP32 | Hit@1 | Hit@10 | MRR |
|---|---|---|---|
| 256토큰 (지금) | 0.866 | 0.943 | 0.895 |
| 128토큰 (Hailo-8L 입력) | 0.909 | **0.968** | 0.932 |
- 글의 45.2%가 128토큰을 넘지만 이 지표에서는 자르는 쪽이 **더 좋다** (+2.5%p): 제목 질의가 글 앞부분과 겹치기 때문으로 읽음. "128토큰이면 품질이 떨어진다"는 CP12의 걱정은 이 지표로는 서지 않는다 (같은 품질로 표시).
- Hailo-8L의 CLIP 이미지 탑은 출처에서 Cifar100 top-1 65.3 → 62.3 (하드웨어). 우리 지표로는 재지 않음.

- **규칙 F → C2 섬.** CPU로 증명을 검증하는 조합(X0, X1, Jetson)은 100 Mbps 틀린 증명 폭주에서 호스트가 14–37코어어치 일을 받아 새 글이 끝나지 않는다. 검증 유닛이 있는 X2·X3만 지킨다.
- **규칙 A**: 글자 그대로 적용하면 X3(층 경계 양보)가 K2에 걸려(FP16 이미지 한 층 = 46 ms 동안 검색어가 기다림) **X2를 대안으로 올린다.** CP19 규칙 Q가 미리 적어 둔 다음 단계(층보다 잘게, GEMM 경계에서 양보)를 넣은 X3g는 계약을 다 지키고, 평소 가속기 전력 3.9 mW가 X2(Hailo 유휴를 0으로 둔 가장 유리한 경우에도 4.5–6.0 mW)보다 낮다 → **한 칩 유지, 단 GEMM 경계 양보가 하드웨어 요구.**
- 그래도 X2가 나은 곳이 분명하다: 스팸 K_crit 23배 (2,327 vs 100), 따라잡기 1.0분 vs 17.8분, 이미지 지연. 차이 나는 평소 전력은 0.6–2.1 mW (+ Hailo 유휴, 출처 없음).
- 같은 품질 규칙: X3g는 FP16이라 이미지 품질 FP32와 같음. Hailo 쪽 MiniLM(128토큰)은 같은 품질, CLIP 이미지 탑은 출처 기준 3%p 하락 (우리 지표로 재지 않음).

## 해석
1. **C2는 같은 조건에서도 선다.** 기존 박스급 조합은 인코딩은 넉넉하지만(Hailo-8L은 우리 8×8보다 MiniLM 8.6배, CLIP 이미지는 FP16 기준 17배 빠름) 증명 폭주 때 CPU가 14–37코어어치 일을 받는다. 같은 박스 소프트웨어(증명 먼저)를 써도 마찬가지라, 차이는 검증 유닛 하나에서 나온다.
2. **"우리 인코더"의 근거는 얇다.** 한 칩(X3g)이 두 칩(X2)을 이기는 것은 평소 전력 몇 mW와, 아직 출처가 없는 Hailo 유휴 전력이다. 스팸·따라잡기·이미지 지연은 X2가 낫다. 보고서는 "검증 유닛이 우리 기여의 중심이고, 인코더는 같은 칩에 올렸을 때의 전력·면적 이득"으로 써야 정직하다.
3. **사진이 정밀도를 바꿨다.** NORTHSTAR의 이웃 일치 계약으로는 CLIP 이미지 탑을 INT8로 돌릴 수 없다 (혼합도 0.81). 칩은 이미지 탑을 FP16 유닛에서 4배 느리게 돌리고, 그래서 검색어 양보를 GEMM 경계까지 잘게 해야 한다. 이웃 일치가 이 모델에 너무 엄격한 계약인지(캡션 Recall은 1%p 안)는 열어 둔다.
4. **MiniLM은 128토큰이면 충분했다.** 우리 지표에서 자르는 쪽이 더 좋아, 인코더 활성값(1 MB SRAM을 정한 256토큰 786 KB)을 절반으로 줄일 여지가 생긴다 (따지지 않음).

## 한계
- 기존 조합은 출처·추정 숫자다 (Hailo 처리량은 x86 호스트 기준 벤더 값, Pi 5 CPU는 노트북 × 2.93, Hailo 유휴 전력 없음, Jetson GPU 인코더 없음).
- FP16 품질은 가중치만 FP16으로 둔 지표다 (활성값 FP16의 영향은 안 봄). 칩의 FP16 이미지 탑 비용은 GEMM MAC 수 × FP16 단가로 셈 (Timeloop 매핑 아님).
- GEMM 경계 양보는 이미지 한 장을 49토막(층마다 GEMM 4개 + 패치 임베딩)으로 나눈 것으로 셈. 제어기 면적은 셈에 없음.
- MiniLM 128토큰 결과는 제목 자기 검색 하나의 지표다.
- CP19의 S3 전력 계산 오류를 이번에 고쳤다 (CP19.md "정정").

## 계획에서 달라진 점
- before: "정적 INT8 (사진 보정)" = onnxruntime `quantize_static` 기본 (모든 연산). after: 첫 실행에서 어텐션 행렬곱·덧셈까지 8비트가 되는 것을 보고, **칩과 같은 범위(선형층만)**를 규칙 P의 대상으로 바꿈. 모든 연산 결과도 표에 남김.
- 혼합 변형은 첫 실행에서 노드 이름을 잘못 찾아(`layers.0.` vs 실제 `layers.0/`) 실수로 남긴 노드가 1개뿐이었음 → 고쳐 13개로 다시.
- FP16은 가중치만 FP16으로 반올림한 지표로 잼 (Pillow처럼 변환 도구를 새로 설치하지 않으려고).
- 규칙 P가 FP16을 고른 뒤 칩 비용(FP16 유닛에서 이미지 탑)과, 그 때문에 걸린 K2를 CP19 규칙 Q의 다음 단계(GEMM 경계 양보)로 푼 X3g를 더함. 규칙 A는 두 경우를 다 적음.
- CP19 S3 전력 창을 고치며 CP19를 다시 돌림 (판정 그대로).
