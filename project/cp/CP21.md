# CP21 — 데모 + 실시간 vs 시뮬레이터 (X2)

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP20.md](CP20.md), 전체 설계는 [CP15.md](CP15.md) (실행 방식 E1/E2, 규칙 X2). 그림은 아키텍처 보드(L−1c "데모: 진짜 박스 다섯 대")와 체크포인트 보드.

## 왜 이 CP인가
CP16–CP20의 숫자는 전부 시뮬레이터(E2: 이산 사건 + 같은 메시지는 한 번만 계산해 나눠 씀)에서 나왔다. 두 가지가 남았다:
- **X2 (CP15)**: 같은 소규모 장면을 실제 프로세스(E1)와 시뮬레이터(E2)로 돌려 **박스별 작업 수가 같아야** 한다. 다르면 E2의 숫자를 믿을 수 없다.
- **C5 (사용성을 버리지 않는다)**: 지금까지 기능은 시뮬레이터 안에서만 돌았다. 사람이 직접 써 보는 박스(웹 UI)가 없다.
- 형식: **목적형**. [구현] (박스 서버, 웹 UI, 장면 실행기) [측정] (X2 작업 수, 데모 기능 시험).
- 답할 질문:
  - 진짜 박스 다섯 대가 진짜 암호·임베딩·검색으로 서로 메시지를 주고받을 때, 시뮬레이터와 박스별 작업 수가 같은가?
  - 글쓰기, 검색, 말로 사진 찾기, 투표, 삭제(망각), 방, 벌칙이 사람이 쓰는 화면에서 동작하는가?

## 그림 (설계, 결과 전)
```
 브라우저 (박스마다 화면 하나: 127.0.0.1:8601–8605)
   │  글·사진 올리기 / 피드·투표 / 검색 / 말로 사진 찾기 / 삭제 / 방 / 박스 작업 수 + 가상 칩 시간
   ▼
 ┌─ 박스 프로세스 × 5 (src/demo/box_server.py, 표준 라이브러리 HTTP) ────────────────────────────┐
 │  /gossip  받기 → Ed25519 → 증명(표시 + 칩 모델 시간) → RLN·nullifier → 이웃에 전달 (검증 후 전달) │
 │           → 복호화 → MiniLM INT8 임베딩 → 색인 / 투표 집계 / 삭제 / 벌칙                       │
 │  /pull    사진 본문 (I2: 봉투를 준 이웃에서 당겨 옴, 없으면 그 이웃이 자기 부모에서 먼저 당김)       │
 │  CLIP 이미지 탑 (FP32 = CP20의 FP16과 같은 품질), CLIP 텍스트 탑 (말로 사진 찾기)                │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
        ▲ 같은 메시지 목록 (World, 씨앗 고정), 같은 메시 (sim.network.meshes, D = 2)
 ┌─ 장면 실행기 (src/demo/x2.py) ─────────────────────────────────────────────────────────────┐
 │  E1: 박스 다섯 개를 띄우고 메시지를 작성자 박스에 하나씩 넣음, 조용해질 때까지 기다림              │
 │  E2: 같은 메시지를 sim.stack.DayNet에 (작업 이름별로 셈)                                          │
 │  → 박스 × 작업 (ed25519, 증명, rln, 복호화, 텍스트, 이미지, 색인, 집계, 삭제, 검색어, 전송, 중복)   │
 └─────────────────────────────────────────────────────────────────────────────────────────────┘
```
- 커뮤니티: 박스(= 사용자) 5명, 공개 서브 A (5명 전부), 서브 B (3명), 방 R (3명, 방 키), 벌칙 알림 주제 (전부). 메시 차수 D = 2라서 중계가 생긴다 (D ≥ 4면 전부 직접 이웃이라 중계를 시험하지 못함).
- 장면 (약 50개, 순서대로): 글 12 (그중 사진 글 4, COCO 사진 + 캡션), 댓글 8, 투표 10 (이중 투표 1), 삭제 2, 방 메시지 3, 틀린 증명 1, 한도 초과 재사용 1 (→ 벌칙), 벌칙 뒤 그 신원의 글 1, 검색어 5.

## 판정 규칙 (결과를 보기 전에 적음)
- **규칙 X2**: 박스 × 작업 칸이 E1과 E2에서 모두 같으면 E2를 믿는다. 다른 칸은 원인을 셋으로 나눈다:
  - (a) 시뮬레이터의 지름길 → **E2를 고친다** (CP15).
  - (b) 박스 서버의 버그 → E1을 고친다.
  - (c) 실제 네트워크의 경쟁(누가 먼저 보나) → 기록하고, 프로토콜로 결정적으로 만들 수 있으면 그렇게 한다.
  고친 뒤 다시 돌려 모든 칸이 같아질 때까지. 고친 것이 CP16–CP20 숫자를 바꾸면 그 크기를 적는다.
- **데모 기능 시험** (E1에서, 다 통과해야 함):
  - D1 검색: 글마다 제목으로 검색하면 그 서브를 가진 모든 박스에서 1등 (5초 안).
  - D2 말로 사진 찾기: 박스의 사진 검색 결과가 같은 모델로 따로 계산한 순위와 똑같다 (기능이 진짜인지). 그리고 COCO 사진 100장을 먼저 올려 둔 뒤 캡션 20개로 찾으면 Recall@10을 적는다.
  - D3 망각: 작성자가 지운 글은 모든 박스의 검색·피드에서 사라진다.
  - D4 방: 방 밖 박스는 방 메시지를 읽지 못하고 검색에도 안 나온다.
  - D5 한 사람 한 표·속도 제한: 이중 투표는 집계에 안 들어가고, 한도 초과 재사용은 신원을 드러내 벌칙, 그 뒤 그 신원의 글은 모든 박스에서 거부.
  - D6 틀린 증명은 첫 이웃에서 멈춘다 (작성자의 메시 이웃이 아닌 박스는 검증하지 않음).
- GPU·NPU는 쓰지 않는다. 박스는 127.0.0.1에만 열고, onnxruntime은 박스마다 1스레드.

- 한 칸만 적은 열은 E1과 E2가 **정확히 같다** (박스 5 × 작업 11 = 55칸).
- 다른 칸은 사진 보내기와 중복 수신뿐이고, **합은 같다** (사진 412 / 412, 중복 524 / 524). 누가 먼저 봉투를 전해 주느냐(→ 누구에게 사진을 당겨 오나, 어느 사본이 중복이 되나)가 실제 지연(로컬 밀리초)과 시뮬레이터의 지연 모델(홉 50 ms + 20 Mbps 업링크)에서 달라서다 → **(c) 경쟁**. 사진을 당겨 올 이웃을 결정적으로 정하면(예: 가장 작은 번호) 같아지지만 지연이 늘어 하지 않음.
- 첫 실행에서 고친 것 (**(a) 시뮬레이터 지름길 → E2를 고침**): 한도 초과 재사용을 찾은 박스가 둘(0, 2)인데, 시뮬레이터는 "네트워크 전체에서 처음 찾은 박스 하나만 벌칙 알림을 낸다"는 전역 지식을 썼다. 실제 박스는 이를 모른다. `sim/stack.py`를 "찾은 박스마다 알림을 내되, 알림은 드러난 비밀 하나에 메시지 하나(같은 id)라 이미 받은 박스는 내지 않음"으로 고침 → 전송 칸이 같아짐. CP17 하루 실행에서 이 차이는 벌칙 알림의 전송·중복 몇 개 (1.37억 사건 중)라 다시 돌리지 않음.
- **규칙 X2 → E2를 믿는다** (결정적인 작업은 박스마다 정확히 같고, 순서에 달린 작업은 합이 같음). 단 사진 보내기(I2 업링크)의 박스별 분포는 지연 모델에 달려 있다 (CP17 I2 업링크의 박스별 숫자는 그 모델의 결과).

| 시험 | 결과 | 판정 |

| D1 검색 | 글 22개(글 12 − 삭제 2 + 미리 올린 사진 글 10) × 그 서브를 가진 박스 = 94번 모두 1등. 메시지 하나가 모든 박스에서 끝나기까지 평균 0.56 s, 최대 0.81 s (≤ 5 s) | 통과 |
| D2 말로 사진 찾기 | 캡션 20개 (올릴 때와 다른 캡션): 박스의 결과가 같은 모델로 따로 계산한 순위와 20/20 똑같음. 사진 104장 중 Recall@10 1.00 | 통과 |
| D3 망각 | 삭제된 글 2개 × 가진 박스 = 8번 모두 검색·피드에서 사라짐 | 통과 |

| D6 틀린 증명 | 작성자(1)와 그 메시 이웃(0, 2)만 검증, 3·4는 검증하지 않음 | 통과 |
- 첫 실행에서 D1·D5가 **시험 장면의 실수**로 실패했다 (박스 동작은 맞음): 방 메시지가 글 제목을 그대로 써서 그 제목 검색에서 방 메시지가 1등이 됨, 그리고 "정상 투표 10개" 중 2개가 같은 사람·같은 글이라 이중 투표로 정확히 거부됨. 장면을 고쳐(방 메시지는 다른 문장, 투표는 사람·글 쌍이 겹치지 않게) 다시 돌림.
- 박스마다 가상 칩 시간 약 58–59 s (대부분 FP16 이미지 104장 × 0.55 s, 추정).
- 데모 화면: 박스마다 글쓰기(사진 첨부 = COCO), 피드(추천·비추천·내 글 삭제), 텍스트 검색, 말로 사진 찾기(사진 격자), 방(멤버가 아니면 "키가 없어 못 읽음"), 이 박스의 작업 수 + 가상 칩 시간.

## 해석
1. **시뮬레이터의 숫자를 믿어도 된다.** 진짜 프로세스 다섯 개가 진짜 암호·임베딩으로 메시지 140개를 주고받을 때, 검증·인코딩·색인 등 칩 크기를 정하는 작업 수는 박스마다 시뮬레이터와 정확히 같았다. 다른 것은 "누가 먼저"에 달린 사진 보내기·중복뿐이고 합은 같다.
2. **X2가 시뮬레이터의 지름길 하나를 잡았다.** 벌칙 알림을 "처음 찾은 박스 하나"가 낸다는 것은 전역 지식이었다. 실제로는 찾은 박스마다 내고, 알림을 드러난 비밀에 묶인 하나의 메시지로 만들어야 중복이 줄어든다 (프로토콜 결정).
3. **사용성 기능이 사람이 쓰는 화면에서 돈다 (C5).** 검색, 말로 사진 찾기, 투표, 망각, 방, 벌칙이 운영자 없이 박스 다섯 대에서 동작한다.

## 한계
- 박스 다섯 대, 한 노트북의 로컬 통신 (실제 지연·손실·NAT 없음). 메시 차수 D = 2.
- 증명은 진짜 Groth16이 아니라 표시 + 칩 모델 시간 (시뮬레이터와 같음).
- 사진은 COCO (중앙 자르기 224×224 원본을 그대로 보냄, 썸네일 따로 없음).
- 사람 사용자 시험(사용성 평가)은 하지 않음.
- 데모 박스와 시뮬레이터(DayNet)는 CP17의 검사 순서(서명 먼저)를 그대로 쓴다. CP19의 "증명 먼저"(O-b)는 박스 한 대 모델(`sim_cp19`)에만 들어가 있다. 작업 수(X2)는 순서와 상관없음.
- `cp21.json`의 `x2.pass`는 "모든 칸이 같음"의 엄격한 값이라 false다 (사진 보내기·중복 칸). 판정은 위 규칙대로 (c)로 분류한 뒤의 것.

## 계획에서 달라진 점
- 벌칙 알림 규칙을 시뮬레이터에서 고침 (위 (a)). 박스 서버도 "이미 알림을 받았으면 내지 않음"으로 맞춤.
- 시험 장면 두 곳을 고쳐 다시 돌림 (위). 판정 규칙은 그대로.
