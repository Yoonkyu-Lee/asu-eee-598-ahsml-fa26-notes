# CP18 — 인코더 다시 판정: 처리량이 아니라 지연·밀린 수집·결정성으로

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP17.md](CP17.md), 인코더의 원래 판정은 [CP12.md](CP12.md). 그림은 아키텍처 보드(L1 칩 아래 "인코더 다시 판정")와 체크포인트 보드.

## 왜 이 CP인가
CP12의 인코더(32×32, 500 MHz, 전역 SRAM 2 MB, 9.22 mm², 칩 면적의 82%)는 "박스마다 하루 10⁶건"과 "8시간 치 33만 건을 60분 안에" 가정으로 정했다. CP16–CP17이 보인 것:
- 사용자 10⁶명 커뮤니티에서도 박스가 받는 텍스트는 그 가정의 1/26 (CP16 S1), 평소 인코더 바쁨은 0.003% (CP17 R3).
- 이미지 글이 들어왔고 (CLIP ViT-B/32, 텍스트 글의 2.36배 MAC), 이미지 전달을 빠르게 하려면 **박스마다 같은 임베딩**이 필요하다 (CP17 I3 탈락 이유).
그래서 이번 CP는 인코더를 세 가지로 다시 판정한다: 모델을 몇 개 올리나(X5), 결정성을 칩 요구로 삼을 수 있나, 배열과 SRAM은 얼마면 되나.
- 형식: **목적형**. [측정] [디자인] (Timeloop/Accelergy 모델).
- 답할 질문:
  - CLIP 하나(텍스트 탑 + 이미지 탑)로 텍스트 검색 품질을 지키나? (모델 수 = 칩이 다룰 가중치·형태 수)
  - INT8 인코더가 배치·스레드·구현에 상관없이 비트 단위로 같은 임베딩을 내나? 아니면 그게 칩만이 줄 수 있는 성질인가?
  - 행동 기반 부하에서 인코더 배열과 전역 SRAM의 가장 작은 크기는? 칩 면적은 얼마나 줄어드나?

## 그림 (설계, 결과 전)
```
 쓰는 곳 (CP17)                         요구 (이번 CP의 규칙)                     칩 손잡이
 ─────────────────────────────────────────────────────────────────────────────────────────────────
 쿼리: 검색어 인코딩 (12토큰)       →  E2 쿼리 인코딩 ≤ 50 ms (추정)           ┐
 새 글: 텍스트·이미지 한 건 (B = 1) →  E1 새 글 P99 ≤ 5초 (기존 계약)          ├→ 배열 R (8/16/32)
 밀린 수집: 꺼졌던 박스             →  E1 8시간 치를 60분 안 (CP4·CP12 계약),  │   전역 SRAM (512 KB / 1 / 2 MB)
                                       물량만 CP16 행동 모델로 바꿈             ┘   모델 수 (M1 2개 / M2 2개 다른 조합)
 작성자 임베딩 동봉 (I3)            →  결정성: 같은 그림 → 비트 단위로 같은 값 → 정수만 쓰는 인코더 = 칩 요구?
```
```
 인코더 (CP12 구조 그대로, 형태만 바꿔 Timeloop로 다시 매핑)
   DRAM (가중치: MiniLM 10.6 MB, CLIP 이미지 탑 87 MB) ──▶ 전역 SRAM ──▶ 입력 16 KB · 누산 16 KB ──▶ R×R INT8 MAC
                                                           └─▶ FP16 어텐션 (R²/4) · 벡터 (R)
   CLIP 이미지 탑: d = 768, FFN 3,072, 12층, 토큰 50 (패치 49 + CLS) → GEMM 4종 (768→2304, 768→768, 768→3072, 3072→768)
```

### 결정 1: 모델 수 (CP15 X5)
| | 텍스트 글 | 이미지 | 검색어 | 칩에 올라가는 모델 |
|---|---|---|---|---|
| M1 | MiniLM | CLIP 이미지 탑 | MiniLM (텍스트), CLIP 텍스트 탑 (말로 이미지 찾기) | 3개 |
| M2 | CLIP 텍스트 탑 | CLIP 이미지 탑 | CLIP 텍스트 탑 | 2개 |
- CP15의 X5 문장은 "M2가 Recall@10 ≥ 0.95 (FP32 MiniLM 기준)를 지키면"이었다. 그런데 Recall@10 vs FP32 MiniLM은 **같은 모델의 정밀도 변형**끼리의 이웃 일치를 재는 계약이라, 다른 모델(CLIP)에는 맞지 않는다 (CLIP은 MiniLM과 다른 이웃을 고르는 것이 당연하고, 그게 품질이 나쁘다는 뜻은 아님). 결과를 보기 전에 판정 지표를 바꾼다:
- **규칙 X5′**: CP3의 자기 검색(코퍼스 2만, 제목 질의 1,000, 같은 표본)에서 CLIP 텍스트 탑 FP32의 Hit@10이 MiniLM FP32보다 0.5%p 넘게 낮지 않으면 M2 (0.5%p는 CP3 조건 (b)와 같은 폭). 아니면 M1.
- CLIP 텍스트 탑은 77토큰에서 자른다 (MiniLM은 256). 본문이 긴 글이 손해를 보는지 따로 적는다.

### 결정 2: 결정성 (같은 입력 → 비트 단위로 같은 임베딩)
| | 확인 | 방법 |
|---|---|---|
| 배치 | 배치 1 vs 16에서 같은 그림 | onnxruntime CPU |
| 스레드 | 1 vs 전부 | onnxruntime CPU |
| 구현 | onnxruntime CPU vs OpenVINO CPU (같은 ONNX 파일) | "다른 칩"의 대리 |
- 대상: FP32, 동적 INT8 (CP17), **정적 INT8** (활성값 스케일을 보정 데이터로 미리 정함 → 배치와 무관해야 함; QDQ, 채널별 가중치, 합성 그림 100장으로 보정).
- **규칙 D**: 정적 INT8이 세 축 모두에서 비트 단위로 같으면 "표준 인코더 + 작성자 임베딩(I3c)"을 이미지 전달의 설계 목표로 올리고 CP17 R1을 τ = 완전 일치로 다시 판정한다. 구현 축에서 다르면 I2를 유지하고, "모든 연산을 정수로 정한 인코더(정수 전용 GELU·Softmax·LayerNorm)"를 **칩 요구 후보**로 적는다 (출처: I-BERT, arXiv 2101.01321: 정수 전용 트랜스포머 추론). 품질은 정적 INT8과 FP32의 같은 그림 코사인으로 함께 적는다.
- GPU·NPU는 쓰지 않는다 (OpenVINO도 CPU 장치만).

### 결정 3: 배열과 전역 SRAM
- 물량 (CP16 해석식, 사용자 10⁶명, P-all = 상위 박스의 위쪽 경계): 하루 텍스트 25,889건 + 이미지 1,143건. 8시간 밀림 = 텍스트 8,630건 + 이미지 381건.
- 텍스트 길이는 CP4 표본 분포 (MiniLM) 그대로. 이미지는 토큰 50 고정.
- **규칙 E** (배열 R ∈ {8, 16, 32} @ 500 MHz, 전역 SRAM ∈ {2 MB, 1 MB, 512 KB}):
  - E1: 8시간 밀림을 60분 안 (배치 B = 8 허용) **그리고** 새 글 한 건 P99 ≤ 5초 (B = 1). CP4–CP12와 같은 계약, 물량만 행동 모델.
  - E2: 검색어(12토큰) 인코딩 ≤ 50 ms, 이미지 한 장 (B = 1) ≤ 1초 (추정 예산: 검색 응답 100 ms, 이미지 글 5초 중 전달 2초).
  - 지키는 것 중 인코더 면적이 가장 작은 것 (배열을 먼저, 그다음 SRAM). 같은 면적이면 하루 에너지가 낮은 것.
  - 모델은 결정 1의 결과 (M1이면 MiniLM + CLIP 이미지 탑, M2면 CLIP 텍스트 탑 + 이미지 탑).
- 뒤집을 조건:
  - 고른 배열이 지키는 커뮤니티 크기의 상한(같은 행동 비율로 선형 외삽)이 10⁶명 아래면 R을 한 단계 올린다.
  - 정적 INT8 품질이 FP32와 같은 그림 코사인 0.95 미만이면, 이미지 탑의 정밀도는 CP3처럼 혼합(일부 층 FP16)을 따로 따진다.
- SRAM 512 KB·1 MB는 Timeloop를 고른 R에서 다시 매핑한다 (전역 버퍼 크기가 매핑을 바꿈). 면적·누설은 같은 CACTI 플러그인.

## 결과

### 결정 1: 모델 수 (X5′, 측정, CP3 자기 검색 같은 표본)
| | Hit@1 | Hit@10 | MRR | Hit@10, CLIP 토큰 77 이상인 글 (695건) |
|---|---|---|---|---|
| MiniLM FP32 (CP3 재현) | 0.866 | **0.943** | 0.895 | 0.922 |
| CLIP 텍스트 탑 FP32 | 0.609 | **0.776** | 0.671 | 0.744 |
- 차이 −0.167 (기준 −0.005) → **M1** (텍스트 MiniLM, 이미지 CLIP 이미지 탑, 말로 이미지 찾기만 CLIP 텍스트 탑).
- 코퍼스 글의 70.3%가 CLIP 77토큰에서 잘린다 (중앙값 = 77). 긴 글만 봐도 CLIP이 0.18 낮고 짧은 글에서도 낮다 → 자르기만의 문제가 아니라 CLIP 텍스트 탑이 문장 검색용으로 학습되지 않은 탓으로 읽는다.
- 확인: 패딩한 배치 vs 한 건씩 차이 0.0, 자른 뒤에도 끝 토큰(EOS) 유지.

### 결정 2: 결정성 (측정, 합성 그림 48장, CLIP 이미지 탑)
| | 배치 1 vs 16 | 스레드 1 vs 전부 | onnxruntime vs OpenVINO | FP32와 같은 그림 코사인 (최저) |
|---|---|---|---|---|
| FP32 | 같음 | 같음 | 다름 (최대 차 1.4×10⁻⁵, cos 1.000) | 1 |
| 동적 INT8 (CP17) | **다름** (cos 0.982) | 같음 | 다름 (cos 0.990) | 0.941 |
| 정적 INT8 (QDQ) | 같음 | 같음 | **다름** (최대 차 2.07, cos 0.872) | **0.798** |
- 정적 INT8은 한 구현 안에서는 배치·스레드와 무관하게 비트 단위로 같다 (OpenVINO 안에서도 배치 1 vs 16 같음). 그런데 **같은 ONNX 파일이 구현에 따라 다른 값**을 낸다 (구현마다 양자화 연산을 합치고 다시 반올림하는 자리가 다름).
- **규칙 D → I2 유지.** "모든 연산을 정수로 정한 인코더 (정수 전용 GELU·Softmax·LayerNorm, I-BERT)"를 **칩 요구 후보**로 적는다: 파일이 아니라 연산 순서와 반올림까지 정한 명세여야 박스끼리 같은 값이 나온다.
- **뒤집을 조건 걸림**: 정적 INT8 품질 0.798 < 0.95 → 혼합 정밀도(일부 층 FP16)를 따로 따져야 한다. 보정이 합성 그림 100장이라 사진으로 보정하면 오를 수 있다 (한계).

- **고름: R = 8, 전역 SRAM 1 MB.** 인코더 9.22 → 3.53 mm² (−62%), 칩 11.3 → **5.61 mm²** (−50%, 추정). 뒤집을 조건(지키는 사용자 수 ≥ 10⁶) 통과: 5.3배 여유.
- 1 MB에서 밀림 배치는 가장 긴 텍스트에서 1, 이미지는 3까지 내려가지만 시간은 2 MB와 같다 (R = 8은 계산이 병목).
- 하루 (10⁶명 P-all 물량, 인코더만): 일한 에너지 271 J, 바쁨 2,041 s, 유휴 누설 118 J (CP12 배열은 누설만 1,403 J). CP17의 칩 유휴 2,480 J는 약 1,195 J로 준다 (추정).

## 해석
1. **텍스트 검색 모델은 하나로 줄일 수 없다.** CLIP 텍스트 탑은 제목으로 글을 찾는 일에서 MiniLM보다 0.17 낮다. 칩은 모델 셋(MiniLM, CLIP 이미지 탑, 말로 이미지 찾기용 CLIP 텍스트 탑)을 다룬다. 가중치는 DRAM에 있으니 비용은 면적이 아니라 DRAM 용량 (INT8로 MiniLM 10.6 MB + CLIP 이미지 탑 87 MB + 텍스트 탑 약 63 MB, 추정)이다.
2. **"같은 그림 → 같은 임베딩"은 소프트웨어로는 안 된다.** 정적 양자화로 배치·스레드 의존은 없앴지만, 같은 파일을 두 구현이 다르게 계산한다. 박스들이 서로 다른 칩·런타임을 쓰는 한 I3c(작성자 임베딩 + 완전 일치 검사)는 **연산 명세를 고정한 정수 데이터패스**가 있어야 열린다. 이것은 칩(또는 프로토콜 명세)만이 줄 수 있는 성질이라 후보로 올린다. 다만 지금 품질(0.798)로는 검색에 쓸 수 없으니 정수 전용 인코더의 품질부터 보여야 한다.
3. **인코더를 키운 것은 배열이 아니라 SRAM이었다.** CP12 인코더 면적의 74%가 2 MB 전역 SRAM이다. 행동 모델 물량(CP4 가정의 1/26)에서는 8×8 배열로도 밀림 11분, 새 글 0.13초라 계약을 넉넉히 지키고, SRAM은 "가장 긴 글 한 건의 활성값"(786 KB)이 정한다. 칩 면적이 절반이 되고 누설이 1/12이 된다 → CP17이 말한 "평소의 손잡이는 전력 게이팅뿐"의 압력도 준다.

## 한계
- 그림은 합성이다. 정적 INT8 보정도 합성 그림 100장. 사진에서 품질(0.798)과 구현 간 차이가 달라질 수 있다. 말로 이미지 찾기 품질은 재지 않았다 (사진 데이터셋은 받을 때 허락 필요).
- "다른 칩"의 대리는 같은 노트북의 두 런타임뿐이다. 실제 다른 하드웨어(ARM, NPU)는 재지 않았다.
- 512 KB는 Timeloop가 아니라 활성값 크기 식으로 뺐다. 활성값을 DRAM으로 내보내는 타일링을 쓰면 512 KB도 될 수 있다 (DRAM 트래픽·에너지와 맞바꿈, 따지지 않음).
- CLIP 텍스트 탑(검색어용) GEMM은 매핑하지 않았다. 검색어는 12토큰이라 MiniLM 검색어 10.9 ms와 같은 규모로 본다 (추정).
- 물량은 CP16 해석식(P-all, 상위 박스의 위쪽 경계)이고 텍스트 길이는 CP4 표본. 인코더 합산 모델은 CP12와 같은 가정(가중치는 GEMM마다 한 번 스트리밍, DRAM 대역폭 고정).
- 칩 면적은 CP14 칩에서 인코더만 바꾼 값이다. 다른 블록은 다시 합성하지 않았다.

## 계획에서 달라진 점
- before: CP15 X5 "M2가 Recall@10 ≥ 0.95 (FP32 MiniLM 기준)". after: X5′ 자기 검색 Hit@10 차이 ≤ 0.5%p. 결과 전에 계획에 적어 바꿈 (다른 모델끼리는 이웃 일치가 품질을 재지 않음).
- before: "512 KB·1 MB는 고른 R에서 Timeloop로 다시 매핑". after: 1 MB만 Timeloop, 512 KB는 활성값 식으로 뺌 (B = 1에서도 안 들어감).
- 1 MB 재매핑은 2 MB 판정이 나오기 전에 R = 8로 먼저 돌렸다 (2 MB 매핑이 몇 시간 걸려서). 고른 R이 8이라 다시 돌릴 필요는 없었다.
- 정적 INT8 품질 뒤집을 조건이 걸렸지만 혼합 정밀도는 이번 CP에서 하지 않고 다음 일로 남긴다.
