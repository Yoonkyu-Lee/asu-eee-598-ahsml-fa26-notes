# CP16 — 행동 매개변수 + 시뮬레이터 핵심

2026-11-01 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 설계는 [CP15.md](CP15.md), 그림은 아키텍처 보드(L−1 아래 "시뮬레이터 핵심")와 체크포인트 보드.

## 왜 이 CP인가
CP12–CP14의 칩은 "박스마다 하루 10⁶건을 전부 받는다"는 가정으로 크기를 정했다 (CP15에서 드러남). 이번 CP는 사용자 행동과 네트워크를 넣어 **박스 하나가 실제로 받는 일**을 낸다. ML은 아직 돌리지 않는다 (CP17): 메시지의 종류·크기·개수와 도착 시각만 다룬다.
- 형식: **목적형**. [조사] [구현] [디자인].
- 답할 질문:
  - 커뮤니티 크기(사용자 10³–10⁶)와 복제 정책별로, 박스 하나가 초당 검증할 증명·인코딩할 글·이미지는? 피크 시간·상위 1% 박스에서는?
  - 그중 무엇이 큰가 (글, 댓글, 투표)?
  - 새 글이 커뮤니티 전체에 퍼지는 시간은 5초 예산 안인가?

## 그림 (설계, 결과 전)
```
 매개변수 (출처, 없으면 추정 + 민감도)
   참여 불평등 (읽기만 / 댓글 / 글), 1인당 하루 글·댓글·투표, 꼬리 분포, 시간대 곡선,
   서브 인기 분포, 1인당 구독 수, 이미지 비율·크기, 글·댓글 길이, 박스 온라인 비율
        │
        ▼ 사용자 M명 = 박스 M대 (한 집에 박스 하나)
 ┌ 사건 엔진 (가상 시계, heapq) ──────────────────────────────────────────────────────────┐
 │ 사용자 행동: 글 (텍스트 / 이미지) · 댓글 · 투표 · 삭제   (읽기·검색은 자기 박스 안 → CP17)   │
 │ 메시지 = 본문 암호문 + 서명 + RLN 증명  →  서브(토픽)에 게시                                │
 │ gossip (gossipsub v1.1 기본값: 메시 D = 6, 검증 후 전달, 이미 본 메시지는 검증 안 함)       │
 │ 복제 정책: P-all / P-sub / P-sub+k   →  박스마다 받는 서브가 정해짐                          │
 └──────────┬────────────────────────────────────────────────────────────────────────────────┘
            ▼ 흔적
   시스템: 메시지 (생성 시각, 서브, 종류, 크기, 박스별 도착 시각)
   박스: 초 단위 작업 수 (검증, 텍스트 인코딩 토큰, 이미지, 중복 수신 바이트) → Perfetto JSON
            ▼
   박스별 부하 분포 (평균, 피크 시간, 상위 1%) → 칩 용량(CP14: 13,429 증명/s, CP12 인코더)과 비교
```
- 큰 커뮤니티는 이산 사건으로 다 돌릴 수 없다. 박스별 **개수**는 해석식(구독한 서브의 메시지율 합)으로 내고, 이산 사건은 작은 규모에서 전파 시간·중복·폭주 모양을 재면서 해석식과 맞는지 확인한다.

## 대안과 판정 규칙 (결과를 보기 전에 적음)

### 복제 정책 (CP15 X4)
| | 정책 | 박스가 받는 서브 |
|---|---|---|
| P-all | 모든 박스가 모든 서브 | 전부 |
| P-sub | 주인이 구독한 서브만 | 구독 |
| P-sub+k | 구독 + 복제본이 r_min개 미만인 서브를 박스들이 나눠 맡음 | 구독 + 맡은 것 |
- 가용성 = 작성자 박스가 꺼져 있을 때 그 서브의 글을 가진 다른 박스가 하나라도 켜져 있을 확률 (박스 온라인 비율 u, 출처).
- **규칙 Q1**: 가용성 ≥ 99%를 모든 서브에서 지키는 정책 중, 피크 시간 상위 1% 박스의 검증율이 가장 낮은 것.

### 투표 (투표도 익명·속도 제한이 필요하다 → 증명이 붙는다)
| | 방식 | 증명 수 |
|---|---|---|
| V1 | 투표마다 메시지 하나 | 투표 수만큼 |
| V2 | 박스가 주인의 투표를 T초마다 묶어 메시지 하나 (RLN 한 번) | 투표한 사용자 × (하루 / T) 이하 |
| V3 | 투표는 전파하지 않음 (각 박스가 자기 주인 것만) | 0, 그러나 전역 인기 순위 불가 → 사용성 위반 (NORTHSTAR 4) |
- **규칙 Q2**: V3은 제외. V1과 V2 중 투표 수 반영 지연 ≤ 60초 (추정 목표: 피드 순위가 1분 안에 반영)를 지키며 상위 1% 박스의 검증율이 낮은 것.

### 시뮬레이션 규모 (CP15 X1, X2)
- **규칙 Q3**: 이산 사건으로 사용자(=박스) 1,000명 × 가상 1시간(피크)을 돌려, 박스별 메시지 수가 해석식과 2% 안에서 맞아야 한다 (안 맞으면 고친다). 그 뒤 큰 규모는 해석식으로.
- **규칙 Q4 (신선도)**: 전파 지연(게시 → 서브의 모든 온라인 박스 도착) P99 ≤ 1초 (5초 예산 중 네트워크 몫, 추정). 홉당 지연은 출처(가정용 인터넷 RTT) 없으면 (추정) 50 ms + 링크 대역.

뒤집을 조건:
- S1: 채택한 정책의 상위 1% 박스 텍스트 수집량(피크)이 CP12 가정(초당 11.6건)의 1/10 이하면, CP18에서 인코더 크기를 줄이는 쪽으로 다시 판정한다.
- S2: 투표 증명이 박스 검증의 절반을 넘으면, 투표 설계가 칩 크기의 손잡이임을 기록하고 Q2 결과로 검증 유닛 요구를 다시 계산한다.
- S3: 매개변수 하나가 출처 범위 안에서 결론(정책 선택)을 뒤집으면, 그 매개변수를 결과 표에 "결정을 좌우함"으로 표시한다.

## 결과 (전부 모델: 출처 기반 매개변수 + 추정)

### 박스 하나가 받는 일 (피크 시간, 정책 P-sub, 투표 V2)
| 커뮤니티 (사용자 = 박스) | 커뮤니티 하루 글 / 댓글 / 투표 | 박스 검증 /s (평균 박스 하루 평균 · 상위 1% 피크) | 텍스트 인코딩 /s (상위 1% 피크) | 이미지 /s (상위 1% 피크) |
|---|---|---|---|---|
| 10³ | 4 / 14 / 178 | 0.002 · 0.004 | 0.0003 | 0.00001 |
| 10⁴ | 37 / 204 / 2,208 | 0.026 · 0.045 | 0.0045 | 0.0002 |
| 10⁵ | 385 / 2,224 / 21,326 | 0.23 · 0.42 | 0.046 | 0.002 |
| 10⁶ | 3,810 / 22,079 / 213,595 | 2.1 · 4.2 | **0.45** | 0.02 |

- **CP12의 가정(박스마다 초당 11.6건)은 사용자 10⁶명 커뮤니티의 상위 1% 박스 피크보다 26배 크다.** 같은 행동 비율이면 그 가정에 닿는 것은 박스 주인 약 2,400만 명(상위 1% 피크 기준) 또는 3,900만 명(하루 평균 기준) 규모의 커뮤니티다 (P-all, 선형 외삽). 하루 활성으로는 Reddit DAUq의 약 1/19–1/12.
- 평소 검증 부하는 많아야 초당 4.2개. 검증 유닛 용량(13,429/s)의 0.03%. **검증 유닛은 평소가 아니라 폭주 때문에 존재한다** (CP6 결론을 행동 모델로 다시 확인).
- **투표가 검증 메시지의 89–91%.** 투표마다 증명이 붙기 때문 (S2 걸림).
- V2(50초 묶음)는 효과가 거의 없다: 묶음당 투표 1.00개. 사용자 한 명이 한 서브에서 50초 안에 두 번 투표하는 일이 드물다. 대신 반영이 평균 26초, 최대 50초 늦어진다.
- 정책: P-sub는 박스 평균 부하를 P-all의 0.78배로 줄이지만, 상위 1% 박스는 0.94배뿐. 활동이 인기 서브에 몰려 있고 모두가 그 서브를 구독하기 때문. 가용성은 모든 정책·규모에서 모든 서브가 99% 이상 (구독자가 3명 미만인 서브가 없음) → P-sub+k = P-sub.

### 이산 사건 실행 (사용자 10⁴명 = 박스 10⁴대, 피크 1시간, P-sub V2)
- 사건 943만 개, 노트북 30초 (CP15 X1: 박스 10⁴대의 하루도 피크 속도로 쳐서 12분 이하 → 이 규모까지는 기능 실행 가능).
- **전달 완전성 1.000**: 켜져 있는 모든 구독 박스가 모든 메시지를 받음.
- 해석식과 총 전달 수: 6.1% 차이. 1시간에 메시지가 166개뿐이라 포아송 잡음(약 8%)이 지배. → 생성기만 2,000시간 돌려 비교: 글 1.9%, 댓글 0.04%, 투표 0.2% (Q3 통과, "계획에서 달라진 점" 참고).
- 중복 수신 바이트 = 고유 바이트의 5.6배 (메시 D = 6의 즉시 전달).
- 전파 지연 (가장 큰 서브, 구독 박스 9,420대, 업링크마다 텍스트 글 300개 + 이미지 글 300개):

| 업링크 | 텍스트 글 P99 | 이미지 글 (177 KB) P99 |
|---|---|---|
| 5 Mbps | 0.39 s | **7.3 s** |
| 20 Mbps | 0.36 s | **2.1 s** |
| 100 Mbps | 0.35 s | 0.69 s |

- **Q4: 텍스트 통과, 이미지 실패** (1초 예산). 홉마다 이미지를 이웃 6곳에 차례로 보내느라 업링크가 막힌다. 5 Mbps면 5초 예산 전체도 넘는다.

### 민감도 (사용자 10⁵명, P-sub V2의 상위 1% 피크 검증 /s, 기본 0.42)
- 투표 ×5: 1.93 · 활성 비율 0.10–0.50: 0.16–0.81 · 댓글 ×5: 0.58 · 시간대 피크 1.3–2.0: 0.34–0.53. 나머지는 ±10% 안.
- 정책 선택이 바뀐 것은 서브당 사용자 20,000 (서브 5개)뿐: 이때는 모두가 모든 서브를 구독해서 P-sub = P-all이고, 숫자 차이 없이 동률. S3에서 "결정을 좌우함"으로 볼 것은 없음.

### 판정
- **Q1: P-sub** (가용성 모두 ≥ 99%, 상위 1% 검증이 가장 낮음). 다만 P-all과의 차이는 6%.
- **Q2: V2** (규칙대로, 검증 0.1% 낮음). 차이가 사실상 없고 반영이 늦어지므로, 투표 설계는 CP17에서 다시 본다 (아래 해석 3).
- **Q3: 통과** (완전성 1.000, 생성기 ≤ 1.9%). **Q4: 텍스트 통과, 이미지 실패.**
- **S1 걸림**: 상위 1% 박스 텍스트 수집 0.45/s (10⁶명) ≤ 11.6/10. → CP18에서 인코더를 줄이는 쪽으로 다시 판정.
- **S2 걸림**: 투표가 검증의 약 90%. 다만 평소 검증 자체가 용량의 0.03%라 칩 크기는 바뀌지 않는다 (폭주가 정함).
- S3: 해당 없음.

## 해석
1. **칩의 두 유닛은 서로 다른 이유로 크기가 정해진다.** 검증 유닛은 공격(폭주)이, 인코더는 지금까지 숨은 가정(박스마다 하루 10⁶건)이 정했다. 행동 모델로 보면 10⁶명 커뮤니티의 평소 수집은 그 가정의 1/26이다. 인코더의 남은 근거는 오프라인 뒤의 밀린 수집과 이미지다 → CP18.
2. **이미지는 계산보다 전달이 먼저 문제다.** 텍스트는 0.35초에 퍼지지만 177 KB 이미지는 20 Mbps 업링크에서 2.1초. 홉마다 이웃 6곳에 차례로 보내는 구조 탓이다. 대안: 이미지 본문은 즉시 전달하지 않고 작은 봉투(썸네일·해시)만 퍼뜨린 뒤 필요한 박스가 가져가기, 또는 작성자 박스가 임베딩을 같이 보내기 (그러면 다른 박스는 이미지 인코딩을 안 해도 되지만, 거짓 임베딩을 믿어야 함). CP17의 첫 결정.
3. **투표는 메시지 수의 주인공이다.** 지금은 투표 하나에 증명 하나. 묶기는 사용자당 투표가 드물어 효과가 없다. 투표를 하루 단위 익명 집계나 증명 하나로 여러 투표를 덮는 방식으로 바꾸면 평소 검증이 약 9분의 1로 준다. 평소엔 칩 크기와 무관하지만 폭주 때 공격자가 가장 싸게 흉내 내는 메시지가 투표일 수 있다 → CP19 시나리오에서 본다.
4. 복제 정책은 생각보다 손잡이가 아니다: 활동이 인기 서브에 몰려 있어 구독만 받아도 상위 박스의 부하는 거의 같다.

## 한계
- 사용자 = 박스 하나 (한 집에 한 명). 한 박스를 여러 명이 쓰면 박스당 부하는 그 수만큼 커진다.
- 활동률은 Reddit DAUq 기준이라 로그아웃 방문자가 섞여 있다 (민감도 ×5로 덮음). 봇 활동도 섞여 있다.
- 시간대 곡선, Zipf 지수(직접), 구독 수, 온라인 비율, 업링크, 홉 지연은 (추정).
- 시간대는 하나 (모두 같은 시간대). 여러 시간대면 피크가 낮아진다.
- gossip은 즉시 전달만 (IHAVE/IWANT, 메시 유지 하트비트, 벌점 없음). 꺼진 박스는 그 시간 내내 꺼져 있고 메시는 켜진 박스끼리 이미 고쳐졌다고 둠.
- 읽기·검색·삭제는 아직 없음 (CP17).
