# CP2 — 인코더 기준선 확정

2026-10-30 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 그림은 체크포인트 보드 아티팩트.

## 왜 이 CP인가
CP1에서 수집 경로의 약 98%가 인코더였고, 기존 INT8 모델(`model_quint8_avx2.onnx`)은 Recall@10 0.875로 목표 0.95에 못 미쳤다. 제안서 규칙상 가속기는 **같은 Recall의 기준선**과 비교해야 하므로, 가속기 설계 전에 "0.95를 지키는 가장 싼 CPU 설정"과 그 ms·J를 확정한다.

## 환경·의존성 (CP1 표에 추가)

## 측정 조건
G-Helper "풀파워"(Turbo 기반, 전력 제한 미적용), Windows 최고 성능 모드, AC, 브라우저·Steam 종료, VS Code·Codex 켜짐.
에너지는 패키지 전체(유휴 포함)와, 직전 2초 유휴 전력을 뺀 "활성" 에너지 두 가지로 적는다.

## 방법
`src/bench_cp2.py` → `results/cp2/cp2_results.json`.
1. 변형 모델: FP32, 기존 동적 INT8(HF), 채널별 동적 INT8, 정적 QDQ INT8, FP16.
2. 품질: 코퍼스 2만 개 + 쿼리(제목) 1,000개. FP32 정확 검색이 정답. 보정용 게시물 200개는 평가 데이터와 겹치지 않게 뽑음.
3. 속도·에너지: 게시물 1,000개, (a) P코어 1개 1스레드 배치 1, (b) 전체 코어.
4. 통과한 것 중 가장 싼 설정 + 기존 INT8에 대해: 정렬 없는 배치 32, 길이 버킷 배치 8/32, E코어 1개, E코어 8개, 저전력 E코어 1개.
5. 밀린 수집: 하루 10⁶건 커뮤니티의 8시간치(약 33만 건, 가정)를 처리하는 데 걸리는 분.

## 진행 중 막힌 것 (재현할 때 참고)
1. `quant_pre_process`에 sympy 필요 → 설치.
2. 이 ONNX에서 기호 형태 추론 실패 → `skip_symbolic_shape=True`.
3. Percentile 보정은 샘플 길이가 같아야 함 → 보정 입력만 256토큰으로 패딩.

|---|---|---|---|
| FP32 | 1.000 (정답) | | |
| **FP16** | **0.999** | 1.0 | 0% |

## 해석
1. **CPU에서 0.95를 지키는 가장 싼 설정은 FP32다.** FP16은 품질은 같지만 CPU에 FP16 연산기가 없어 오히려 느리다. 기준선: FP32, 전체 코어, 길이 버킷 배치 8 → **7.15 ms, 0.53 J/게시물.** 1스레드 기준선: P코어 30.8 ms, 0.70 J.
2. **INT8의 값과 대가.** 채널별 동적 INT8은 FP32보다 P코어에서 **2.1배 빠르고 에너지 2.2배 적지만** Recall 0.878. 표준 양자화 도구로는 이 품질 격차를 못 메운다. → 가속기가 "INT8 비용으로 FP32 순위 품질"을 낼 수 있다면 그게 기여가 된다. 다만 **Recall@10 vs FP32라는 기준이 너무 엄격한지**(점수가 촘촘한 후보끼리 순서만 바뀐 것인지)를 먼저 따져야 한다.
3. **길이 버킷이 배치 손해를 되돌린다.** 정렬 없는 배치 32보다 1.8배 빠르고, 배치 1보다도 1.3배 빠르다. 소프트웨어로 풀리는 문제라 하드웨어 P는 아니지만, 가속기도 길이별 묶음을 전제로 설계해야 한다.
4. **약한 기기에서는 밀린 수집이 진짜 문제다.** 저전력 E코어 하나로는 8시간치를 처리하는 데 10.3시간이 걸려 **영원히 못 따라잡는다** (하루 10⁶건 가정). 패키지 J는 유휴 전력 탓에 느린 코어가 더 크지만, 활성 J는 E코어가 P코어보다 작다 (0.28 vs 0.47).
