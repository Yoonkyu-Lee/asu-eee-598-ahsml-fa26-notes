# CP26 — 박스 사이 교류 프로토콜: 언제, 누구와, 무엇을

2026-11-07 시작. 요약은 [CHECKPOINT.md](../CHECKPOINT.md), 앞 CP는 [CP25.md](CP25.md) ("W1–W5: 돌리지 않음").

## 왜 이 CP인가
- CP24 데모 박스는 20초마다 목록의 **모든** 박스에게 가진 메시지 **전부**를 달라고 한다. 박스 하나의 비용은 (n − 1) · M / 20 s다. 쌓인 메시지 수 M도 사용자 수 n과 함께 늘어서 네트워크 전체로는 약 n³이다 (추정: 코드에서 셈).
- 설계에는 이 자리가 비어 있다. DayNet(CP17)은 새 메시지를 메시 이웃에게 밀어 주는 것(push 가십)만 모델링한다. 박스는 95%가 처음부터 끝까지 켜져 있고, 메시는 고정이다. 꺼졌던 박스가 **무엇을 놓쳤는지 어떻게 아는지**, 조용히 빠진 메시지를 **어떻게 메우는지**가 없다. CP19의 밀린 수집은 "놓친 것만 내려받는다"고 가정만 했다.
- 사용자 원칙 (2026-11-07): **하드웨어 컴퓨트를 최적화해야 한다는 주장은 알고리즘 로직을 착취할 수 있는 만큼 다 착취했다는 가정 위에서만 의미가 있다.** 교류의 비용이 n·M으로 커지면 그건 하드웨어가 아니라 프로토콜의 문제다. 박스가 받는 일(검증, 인코딩)의 양도 교류 방식이 정한다. 중복으로 받은 것은 검증 전에 표에서 버리지만 대역폭은 쓴다.
- 형식: **목적형**. [디자인] 교류 조건과 대안 [구현] 교류 모델(churn, 메시 유지, 따라잡기, 복구) [측정] 모델에서 n·M을 키워 비교 [구현] 데모 박스 교체 [측정] 데모 = 모델 (요청 수·바이트).
- 답할 질문:
  - 놓친 것이 없고(완전성) 새 글이 빨리 오면서(신선도), 박스당 교류 비용이 n·M에 무관한 가장 단순한 교류 방식은?
  - 상시 박스 하나 + 잠깐씩 들어오는 박스들 장면에서, 들어온 박스가 따라잡는 데 걸리는 시간과 바이트는?
  - 데모 박스에 넣으면 모델과 같은 요청 수·바이트가 나오는가?

## 그림 (설계, 결과 전)
교류 조건 (사건이 계기. 시간이 계기인 것은 ⑤ 하나):
```
 ① 새 메시지 (썼거나, 받아서 검사 통과)  ── 봉투 push ──▶ 지금 켜진 메시 이웃 D개 (보낸 이웃 빼고)
 ② 메시 이웃이 꺼짐 (연결 실패, heartbeat 끊김) ── 켜진 박스 중 하나를 새 이웃으로 (graft) ── 메시는 켜진 박스끼리만
 ③ 내가 켜짐 (켜기, 절전 해제, 주소 바뀜)
      ├─ 따라잡기: 이웃 하나에게 "내 연속 수신 구간이 끝난 시각 T_off 이후에 받은 것" 요청
      │            답에 그 이웃의 연속 수신 구간 [T_on, 지금]이 붙음 → T_on > T_off면 빈 구간을 다른 이웃에게
      └─ 내놓기: 내가 꺼지기 직전 W초 동안 쓰거나 받은 메시지 ID를 새 이웃에게 (IHAVE) → 없는 것만 요청 (IWANT)
 ④ 무거운 본문 (사진) 필요 ── 봉투를 준 이웃에게 pull, 실패하면 ③처럼 다른 이웃에게
 ⑤ 조용한 손실 대비 (전송 중 끊김) ── T_d초마다 메시 이웃에게 최근 W초 ID 요약 (IHAVE) → 없는 것만 (IWANT)
```
비용의 기준 (박스 하나):
```
 꼭 받아야 하는 바이트 = 그 박스가 가져야 할 메시지 × 크기 (한 번씩)          ← 어떤 프로토콜도 못 줄임
 push 중복            ≈ (D − 1) × 봉투 (이웃마다 한 부씩 옴)                ← 메시 차수 D의 값, 이번 CP 밖 (아래)
 교류 오버헤드         = 요청 + ID 요약 + 이미 가진 것을 다시 받은 바이트        ← 이번 CP가 줄이는 것
 지금 (X1):   (n − 1) × M × 봉투 / 20 s        좋은 것: 새 메시지율 × D × ID 크기 + 꺼졌던 동안의 양만큼
```

## 대안 (결과를 보기 전에 적음)
| | 계기 | 상대 | 내용 | 비고 |
|---|---|---|---|---|
| **X0** | ① push만 | 메시 D | 봉투 | 기준선. 꺼졌던 박스는 영영 못 받음 |
| **X1** | ① + 20초 타이머 | **모든** 박스 | 가진 것 **전부** | 지금 데모 (CP24). 작은 n에서만 사건 모델, 큰 n은 식 |
| X1m | ① + 20초 타이머 | 메시 D | 가진 것 전부 | 상대를 줄이기만 하면 되는지 보려는 대조 |
| **X2** | ① ② ③ ④ | 메시 + 따라잡기 상대 | 놓친 구간만, 꺼지기 직전 ID | 사건만. 시간 계기 없음 |
| **X3** | X2 + ⑤ (T_d = 10 s, W = 60 s) | 메시 D | ID 요약 → 없는 것만 | gossipsub의 IHAVE/IWANT와 같은 꼴 (출처: libp2p gossipsub 명세, 기억으로 인용) |
| X4 | X2의 ③을 범위 기반 집합 비교로 | 이웃 하나 | 지문(구간 해시)을 주고받아 다른 것만 | Negentropy 같은 방식. 연속 수신 구간을 믿지 않아도 됨. 구현이 가장 복잡 |
- **쓰지 않는 것**: 보내는 쪽이 꺼진 이웃 몫을 쌓아 두는 보낼 함. 메시가 켜진 박스끼리만 이어지면 꺼진 박스는 메시에 없다. 꺼졌던 박스는 자기가 꺼졌던 것을 알므로 받는 쪽이 묻는 것(③)이 더 단순하다. 바꿀 조건: ③만으로 완전성이 안 나오면.
- **연속 수신 구간 (설계 요소, 새로)**: 박스는 "T_on 이후로 끊김 없이 켜져 메시에 있었다"를 안다. 따라잡기 답에 그 구간을 붙이면, 묻는 박스가 빈 구간을 알 수 있다. 상시 박스는 구간이 길어서 한 번에 끝난다.
- **이번 CP 밖**: push 중복((D − 1)배)을 줄이는 것 (봉투만 lazy push, IDONTWANT 등). 메시 차수 D = 6은 DayNet 그대로. 측정해서 숫자로 남기고 다음 감사 CP로 넘긴다.
- **모델 범위**: 교류만 본다 (박스 안의 검증·인코딩 시간은 CP19–CP24 모델이 맡음). 토픽 하나를 n개 박스가 모두 가진다 (토픽 여럿은 토픽마다 같은 일). 사진 본문은 봉투와 따로 세고 ④는 바이트만 셈.

## 장면과 숫자 (결과 전, 모두 추정)
- 메시지: 박스(사용자)당 하루 1개 (CP16 Params: DAU 0.25 × (글 0.05 + 댓글 0.5) + 투표 묶음 → 약 1, 추정). 봉투 1 KB. n개 박스가 모두 받음.
- 켜짐 (churn), 출처 없음, 아래 값을 바꿔 가며 민감도를 봄:
  - 상시 박스: 꺼짐이 하루 평균 1번, 길이 평균 10분 (재부팅·업데이트).
  - 간헐 박스 (노트북): 켜짐 평균 30분, 꺼짐 평균 1일.
  - 장면 C-a 모두 상시 (설계). C-b 상시 1 + 나머지 간헐 (우리 실험). C-c 절반씩.
- 손실: 전송 하나가 조용히 사라질 확률 p_loss = 10⁻³ (추정, 민감도 0, 10⁻²). 꺼지는 순간 날아가던 것은 따로 사라짐.
- 링크: 홉 50 ms, 업링크 20 Mbps (DayNet 그대로).
- n = 10, 30, 100, 300, 1000 (사건 모델). X1은 n ≤ 30만 사건 모델, 그 위는 식 (작은 n에서 식 = 모델을 확인).
- 기간: 2일 + 마지막에 모든 박스를 켜고 10분 (완전성 측정용).

## 판정 규칙 (결과를 보기 전에 적음)
- **E1 완전성**: 마지막 10분 뒤, (박스, 메시지) 쌍 중 빠진 것 ≤ 10⁻⁴. 장면 C-a·C-b·C-c 모두, p_loss = 10⁻³에서.
- **E2 신선도**: 둘 다 켜져 있을 때 받은 메시지의 도착 P99 ≤ 2 s (K1 5 s 중 교류 몫, 추정). 다시 켜진 박스가 켜지기 전 메시지를 모두 갖기까지 P99 ≤ 60 s (꺼졌던 시간 1일 이하).
- **E3 비용**: 교류 오버헤드(위 정의, push 중복 제외)가 꼭 받아야 하는 바이트의 10% 이하이고, n을 10 → 1000으로 키울 때 ~~박스당 오버헤드 바이트의~~ **그 비율(오버헤드 ÷ 꼭 받을 바이트)의** 기울기(log-log)가 0.1 이하.
  - (고침, 스모크 실행 뒤·규모 결과 전) 토픽 하나를 n개가 모두 가지는 모델에서는 꼭 받을 바이트가 n에 비례한다. 그래서 절대 바이트의 기울기는 어떤 방식이든 약 1이다. 뜻했던 것은 "필요한 것 위에 얹히는 몫이 n으로 커지지 않는다"이다.
- **고르기**: E1–E3을 모두 지키는 것 중 가장 단순한 것 (X0 < X2 < X3 < X4). 없으면 그 이유를 적고 다음 단계로.
- **D (데모)**: 고른 것을 데모 박스에 넣는다. ① CP24 L1–L7, CP25 P1–P4 그대로 통과 ② 박스 다섯 개 장면(상시 1 + 켜고 끄는 4)에서 박스별 요청 수·받은 바이트가 같은 장면의 모델과 맞는다 (CP21 X2와 같은 분류 규칙: 다른 칸은 (c) 경쟁만) ③ 같은 장면을 지금 데모(X1)로 돌린 값과 나란히 적는다.

## 모델을 만들며 고친 것 (스모크 실행, 그리드 결과 전)
- 앞 세션의 끄기·쓰기 사건이 다음 세션에서 터지던 것: 세션 번호로 막음 (모델 버그).
- 빈 구간만 다른 박스에 묻게 함: 처음 그림의 "빈 구간을 다른 이웃에게"를 구현할 때 [lo, 응답한 박스의 수신 시작)만 묻도록.
- **프로토콜 규칙 두 개를 보탬** (n = 300, C-b에서 X2가 메시지 쌍의 4%를 놓친 것을 보고):
  1. **다 따라잡기 전에는 옛 구간을 가졌다고 말하지 않는다.** 마지막에 모든 박스가 한꺼번에 켜질 때, 아직 따라잡지 못한 노트북이 "0초부터 다 가졌다"고 답해서 다른 박스가 그 노트북에게서 따라잡았다. 이제 따라잡기를 끝낸 박스만 예전 수신 시작을 내세우고, 그 전에는 이번 세션 시작부터라고 말한다.
  2. **내놓기는 지난 세션 전체.** 처음 그림의 "꺼지기 직전 W초"로는, 상시 박스가 잠깐 꺼진 사이 노트북이 쓴 글을 그 노트북이 꺼진 뒤 영영 못 받았다. 다시 켜진 박스는 지난 세션에 받은 ID 전체를 따라잡기 상대에게 내놓는다 (상대는 없는 것만 요청). 노트북 세션은 짧아서 ID 수가 적다.
  - 둘 다 그림의 ③을 고친 것이다. 고친 뒤 같은 장면에서 빠진 것 0, 오버헤드 0.57%.
- 따라잡기 시간 P99는 본 실행 동안의 재접속만 센다. 마지막 정리 단계에서는 모든 박스가 한꺼번에 켜져서 노트북 299대가 상시 박스 하나 앞에 줄을 선다 (27.9 s). 장면이 만든 값이다.
- 스모크 숫자 (n = 10, 하루, C-a): X1 오버헤드 = 꼭 받을 바이트의 약 2.9만 배, X1m 2.1만 배, X2 1.5%, X3 2.2배. **push 중복은 모든 방식에서 약 5.6–6배** (D = 6, 이번 CP 밖, 아래 결과에 따로 적음).

- **사전 규칙의 판정: 고른 것 없음.** X2는 E1(빠짐 0)과 E3(오버헤드 ≤ 7.6%, 비율의 기울기 −0.32 ~ −0.53)을 지키지만 **E2를 놓친다**: C-b의 n = 10·30에서 따라잡기 P99가 5,451 s · 1,272 s.
- **원인 (결과를 보고 나눠 셈, `results/cp26/e2_waits.json`과 `rules.*.waited_catch_ups`)**: 그 셋은 모두 **데이터를 가진 박스가 하나도 켜져 있지 않던** 경우다. 대부분 상시 박스 자신이다. 잠깐 꺼졌다 돌아왔는데 노트북이 하나도 켜져 있지 않아, 그동안 놓친 것이 없는지 확인해 줄 상대가 나타날 때까지 기다렸다. 그동안 이 박스는 "이번 세션부터"만 가졌다고 말한다 (고친 규칙). 아무도 없으면 어떤 방식도 받을 수 없다 (X3도 같은 셋을 기다림, X0은 아예 못 받음).
- **고른 것 (결과를 보고, 그렇게 표시): X2.** 데이터를 가진 박스가 하나라도 켜져 있을 때로 E2를 세면 X2가 E1–E3을 모두 지키는 가장 단순한 방식이다 (`pick_when_a_box_is_on`). 첫 그리드에서 E2를 통과한 것은 "아무도 없으면 다 따라잡았다고 말하던" 결함 때문이었다.
  - 이 실험에서 뜻하는 것: 상시 박스(미니 PC)가 꺼져 있는 동안에는 노트북끼리만 주고받는다. 미니 PC가 돌아와 혼자이면, 노트북이 하나 켜질 때까지 "이번 세션부터"로 남는다.
- X3은 E3 탈락 (ID 요약이 꼭 받을 바이트의 0.34–2.24배). X2가 이미 빠짐 0이라 주기 요약이 메울 것이 없다. X0은 E1 탈락.
- X4(범위 기반 집합 비교)는 돌리지 않았다. 고르는 순서상 X2가 먼저 통과해서 (켜진 박스가 있을 때). 바꿀 조건: 수신 범위 주장을 믿을 수 없는 상황(악의적 박스가 범위를 부풀림)이 문제가 되면.
- 민감도 (n = 100, X2): push 손실 0 / 10⁻² / 노트북 3일 꺼짐 / 상시 박스 1시간 꺼짐에서 모두 빠짐 0, 오버헤드 0.59–0.65%. push 손실은 메시의 D중 경로가 흡수한다.
- X1 식 (`x1_formula`)은 C-a·C-c에서 사건 모델과 20% 안 (n = 10: 3.9만 대 4.8만, n = 30: 12.5만 대 13.2만). **C-b에는 맞지 않는다** (평균 가용도로 셈해서 상시 박스 하나를 노트북이 폴링하는 몫을 0으로 만든다). C-b의 X1은 사건 모델 값만 쓴다.
- **push 중복** (이번 CP 밖, 숫자만): 꼭 받을 바이트의 C-a 5.3–5.8배 (D = 6이라 이웃마다 한 부), C-c 1.9–2.9배, C-b의 X2 0.01–0.11배 (켜진 박스가 적으면 메시가 작음). 교류 오버헤드(X2 0.5%)보다 두 자릿수 크다. 중복은 표 찾기에서 버려 검증·인코딩은 하지 않는다 (O-b). 그래도 알고리즘으로 줄일 수 있는 몫이라 다음 감사의 첫 항목이다.
- 따라잡기 P99가 n과 함께 느는 것 (C-b 0.87 s): 꺼졌던 동안의 메시지 수가 n에 비례하고, 상시 박스 하나의 업링크에 줄을 서기 때문 (해석).

## 답
1. **완전성과 신선도를 지키면서 박스당 비용이 n·M에 무관한 가장 단순한 교류는?** X2 (사건만). 새 메시지는 메시로 밀어 주고, 박스가 켜지면 지난 세션 ID를 내놓고 꺼진 구간만 받는다. 시간이 계기인 교류는 없다. 모델에서 빠짐 0, 오버헤드 0.5–7.6%로 n이 클수록 준다. 지금 데모의 폴링은 n = 1000에서 꼭 받을 바이트의 432만 배. 단, 데이터를 가진 박스가 하나도 켜져 있지 않으면 따라잡기는 누군가 켜질 때까지 기다린다 (사전 규칙 E2는 이 때문에 못 지킴).
2. **상시 박스 하나 + 잠깐씩 들어오는 박스들에서?** 바로 된 따라잡기 P99 0.11–0.87 s (n = 10–1000). 상시 박스가 돌아왔는데 아무도 없으면 0.9–1.6시간 기다린다 (n ≤ 30).
3. **데모 = 모델?** 그렇다. 박스 다섯 개의 따라잡기·내놓기 수가 모든 칸에서 같다. 거기까지 가며 설계 규칙 셋(못 메운 구간은 내세우지 않기, 상대가 나타나면 다시 묻기, 데모의 메시 다시 엮기)을 찾았다.

## 한계
- 모델은 토픽 하나, 박스당 하루 1메시지, 봉투 1 KB, 켜짐·꺼짐 길이는 출처 없는 추정 (민감도는 봄).
- 메시 다시 엮기는 모델에서 "켜진 박스 중 무작위", 데모에서 "같은 토픽 보유자 중 최근 소식 순". 박스 발견(누가 커뮤니티에 있는지)은 둘 다 주소 목록이 다 안다고 가정한다. 박스 발견과 NAT 뚫기는 별도 CP.
- 조용한 손실(켜진 채로 못 받은 것)은 모델에 push 손실로만 넣었다. 데모에서 네트워크만 끊겼다 이어지는 경우(절전 아님)는 알아채지 못한다. 그때는 다음 켜짐까지 빠진다 (실측에서 보이면 ⑤를 다시).
- 수신 범위는 발행 시각(t0, 작성자 시계) 기준이다. 작성자가 시각을 과거로 적으면 그 글은 따라잡기 범위에서 빠질 수 있다 (작성자 손해, 60 s 여유).
- push 중복(약 5.7배)은 그대로다.
- D는 한 컴퓨터 안 (경로는 로컬).

## 계획에서 달라진 점
- E3을 절대 바이트의 기울기에서 비율의 기울기로 (스모크 뒤, 그리드 전).
