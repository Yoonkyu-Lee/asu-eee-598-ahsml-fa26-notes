## CP1 — 노드 작업 한 건의 단계별 비용 해부   (상태: 완료, 2026-10-30)
- **테마**: server-blind 노드가 게시물 하나를 받고, 검색 하나에 답하는 데 어디에 시간이 드는지 처음으로 숫자를 얻는다.
- **목적**: 목적형. 메인 워크로드(인코더 / 암호 / 검색)를 측정으로 고를 근거를 만든다. 제안서 2단계의 최소 버전.
- **무엇을 하나**:
  - [구현] 참조 파이프라인 `src/`: 수집 = Ed25519 서명 검증 → ChaCha20-Poly1305 복호화 → 토큰화 → MiniLM INT8 인코딩 → 색인 삽입. 쿼리 = 인코딩 → 정확 top-10
  - [측정] 실제 Reddit 게시물 길이 분포로 단계별 ms (중앙값, P99), 1스레드와 전체 스레드
  - [측정] 인덱스 10⁴·10⁵·10⁶에서 정확 검색 ms
  - [측정] INT8 인코더의 Recall@10 (FP32 정확 검색 기준, 목표 ≥ 0.95)
  - [디자인] 부하 산수: 커뮤니티 규모 → 노드의 초당 게시물 → 이 노트북이 포화되는 지점
- **답할 질문**:
  - 수집 한 건에서 지배적인 단계는? 암호는 정말 인코더보다 한두 자릿수 싼가?
  - 10⁶개 정확 검색은 몇 ms인가? (CP0 교훈: 쌀 것이다)
  - INT8 인코더는 Recall@10 ≥ 0.95를 지키나?
  - 이 노트북은 사용자 몇 명 규모까지 5초 신선도를 지키나?
- **계획과 이행**: [cp/CP1.md](cp/CP1.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu)
- **기대 → 실제 → 교훈** (예비 측정: 전원 계획 균형, G-Helper 모드 미확인):
  - 수집 한 건: 1스레드 P50 21.5 ms / P99 53.9 ms, 전체 스레드 P50 7.0 ms. **인코딩이 약 98%, 암호(검증 + 복호화)는 약 0.5%.** 기대대로 인코더가 병목.
  - 쿼리: 10⁶개 정확 top-10 25 ms (1.5 GB, FP32), 쿼리 인코딩 3.4 ms. 기대대로 싸다.
  - **기대와 다름 1**: INT8 Recall@10 = **0.875** (목표 0.95 미달, 쿼리 31%가 0.9 미만).
  - **기대와 다름 2**: 배치 8/32가 배치 1보다 **약 2배 느림**. 길이가 들쭉날쭉해 패딩 낭비 (토큰 중앙값 128, 18%가 256에서 잘림).
  - 교훈: 평균 부하는 노트북에 문제가 아니다 (사용자 10⁵명 × 하루 10건이어도 1스레드 7.2 h/일). 진짜 압박은 **오프라인 후 밀린 수집**(전체 스레드로도 44분)과 **약한 기기**. 사용률은 가정이라 출처가 필요.
- **계획에서 달라진 점**: before: 단계별 ms + J. after: J는 못 잼 (Windows 전력 계측 도구 없음) → CP2로.
- **추가 (공식 조건 재측정)**: 예비 측정과 대부분 5% 안쪽 차이, 결론 그대로. 조건 정정: 예비 측정 때도 실제로는 Windows 최고 성능 모드였다 ("균형"은 전원 계획 이름일 뿐). 세부는 cp/CP1.md 끝.
- **다음 CP**: CP2 — 인코더 기준선 확정: Recall@10 ≥ 0.95를 지키는 가장 싼 설정과, 그 에너지

## CP2 — 인코더 기준선 확정   (상태: 완료, 2026-10-30)
- **테마**: 가속기와 비교할 공정한 CPU 기준선을 정한다. 제안서 규칙: 모든 하드웨어는 같은 Recall에서 비교.
- **목적**: 목적형. Recall@10 ≥ 0.95를 지키는 가장 싼 인코더 설정과, 그 설정의 ms·J를 확정한다.
- **무엇을 하나**:
  - [측정] 양자화 방식별 품질과 속도: 동적 INT8(현재 0.875), 정적 per-channel INT8(우리 게시물로 보정), FP16, FP32
  - [측정] 길이 버킷 배치 (같은 길이끼리 묶기) vs 배치 1
  - [구현] 에너지 측정 방법 확보 (Windows 패키지 전력 도구 또는 ASU Sol의 Linux RAPL)
  - [측정] 약한 기기 대용: E코어만 / 전력 제한 상태에서 수집 비용과 밀린 수집 시간
  - [측정] Recall 평가 확대 (코퍼스 2만 이상, 쿼리 1,000개)
- **답할 질문**:
  - 0.95를 지키는 가장 싼 설정은? INT8을 포기해야 하나?
  - 길이 버킷이 배치 손해를 얼마나 되돌리나?
  - 게시물 한 건 수집에 몇 J인가? 약한 기기에서 8시간치 밀린 수집은 몇 분인가?
- **계획과 이행**: [cp/CP2.md](cp/CP2.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). 에너지는 Windows "Energy Meter"(RAPL, 1단위 = 1 pWh)로 해결. 막힌 3곳(sympy, 형태 추론, 보정 길이)은 CP2.md에.
- **기대 → 실제 → 교훈** (공식 조건):
  - **0.95를 지키는 INT8은 없었다.** 채널별 동적 0.878, 기존 동적 0.862, 정적 QDQ 0.080(붕괴). FP16은 0.999지만 CPU에선 FP32보다 느림.
  - → **CPU 기준선 = FP32**: 전체 코어 + 길이 버킷 배치 8에서 **7.15 ms, 0.53 J/게시물**. P코어 1스레드는 30.8 ms, 0.70 J.
  - INT8의 값: 채널별 동적 INT8이 P코어에서 **2.1배 빠르고 에너지 2.2배 적음** (14.4 ms, 0.31 J). 품질 격차가 곧 기회일 수 있다.
  - 길이 버킷: 정렬 없는 배치 32보다 1.8배, 배치 1보다 1.3배 빠름. 기대대로.
  - 약한 기기: 저전력 E코어 1개는 FP32 111.6 ms/게시물. 8시간치(하루 10⁶건 가정) 처리에 **10.3시간 → 못 따라잡음.**
  - 교훈: 가속기를 설계하기 전에 **품질 계약부터** 정해야 한다. "Recall@10 vs FP32 ≥ 0.95"가 사용자에게 의미 있는 기준인지, 점수가 촘촘한 후보끼리 순서만 바뀐 것을 실패로 세는 너무 엄격한 기준인지 모른다.
- **계획에서 달라진 점**: before: "가장 싼 통과 설정은 INT8 중 하나일 것". after: 통과는 FP32/FP16뿐. 다음 CP의 질문이 "어느 INT8이 빠른가"에서 "어떤 품질 계약이 맞고, 그걸 지키는 가장 낮은 정밀도는 무엇인가"로 바뀜.
- **다음 CP**: CP3 — 정밀도 계약: 가속기 데이터패스가 어떤 정밀도로 계산해야 하는가

## CP3 — 정밀도 계약   (상태: 완료, 2026-10-31)
- **테마**: 가속기 데이터패스의 정밀도를 정하는 근거를 만든다. CP2에서 INT8은 2배 싸지만 Recall 기준을 못 넘었다.
- **목적**: 목적형. (1) 사용자에게 의미 있는 검색 품질 기준을 정하고, (2) 그 기준을 지키는 가장 낮은 정밀도 구성을 찾는다.
- **무엇을 하나**:
  - [측정] 품질 기준 비교: Recall@10 vs FP32 / 제목으로 자기 게시물 찾기 / 상위 1개 일치율 / 동점 허용 Recall (FP32 10등 점수 − δ 이내면 정답)
  - [측정] 층별·연산별 민감도: 하나씩만 FP32로 남기고 INT8 품질 측정 (10개)
  - [구현] 혼합 정밀도 모델: 이득 큰 순서로 FP32 그룹을 늘려 0.95를 처음 넘는 지점
  - [측정] 혼합 정밀도·INT8·FP32의 ms·J (CP2 기준선과 같은 조건), INT8 후보 + FP32 재순위의 품질과 비용
- **답할 질문**:
  - Recall@10 vs FP32 0.95는 의미 있는 기준인가? 대안 기준에서 INT8은 통과하나?
  - INT8 품질을 깎는 건 어느 층·연산인가?
  - 기준을 지키는 가장 싼 구성은? FP32 대비 몇 배 싸나?
- **계획과 이행**: [cp/CP3.md](cp/CP3.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). 결과를 보기 전에 계약 판정 규칙을 CP3.md에 먼저 적고 그대로 적용.
- **기대 → 실제 → 교훈**:
  - 계약: 미리 정한 규칙상 **Recall@10 vs FP32 ≥ 0.95 유지**. INT8의 동점 허용 Recall (δ = 0.01)이 0.949로 0.001 모자람.
  - 하지만 FP32 10등−11등 점수 차 중앙값은 0.0033뿐이고, 자기 검색 Hit@10은 모든 변형이 0.940–0.945 (FP32 0.943). 엄격한 기준이 깎는 건 대부분 거의 같은 점수끼리의 순서다. 기준 변경은 사람 판정 데이터로 따로 정당화해야 한다.
  - 기대와 다름: 몇 층만 FP32로 남기면 될 줄 알았는데, **0.95까지 가중치 MAC의 83%를 FP32로 남겨야** 했고 속도는 FP32의 1.1배. 오차가 고르게 퍼져 있다. 가장 민감한 건 FFN 출력(+0.032), 어텐션 출력은 무관.
  - 답: **INT8 수집 + FP32 재순위.** INT8 상위 20개를 FP32로 다시 매기면 Recall@10 **0.993**. 수집은 FP32 기준선보다 **1.9배 빠르고 2.2배 적은 에너지** (3.70 ms, 0.25 J/게시물). 대가는 쿼리당 약 252 ms, 18.7 J (추정) → 검색 1번당 수집 65건 이상이면 이득 (추정).
  - 교훈: 정밀도 계약은 인코더 하나가 아니라 **수집 경로와 쿼리 경로로 나눠** 지킬 수 있다. 가속기는 INT8 대량 경로 + 작은 고정밀 재순위 경로.
- **계획에서 달라진 점**: before: 혼합 정밀도가 답일 것. after: 혼합 정밀도는 기각, 재순위가 답. 품질 기준은 보류(사람 판정 데이터 필요).
- **다음 CP**: CP4 — 약한 기기용 수집 가속기의 첫 비용 모델: INT8 MiniLM을 어떤 크기의 배열·메모리로 몇 W에 돌려야 8시간치 밀린 수집을 1시간 안에 끝내나

## CP4 — 약한 기기용 수집 가속기의 첫 비용 모델   (상태: 완료, 2026-10-31)
- **테마**: CP3의 정밀도 계약(INT8 수집 + 고정밀 재순위)을 전제로, 수집 경로 하드웨어의 크기·전력·메모리를 처음으로 숫자로 정한다.
- **목적**: 목적형. 약한 기기에서 "8시간치 밀린 수집을 1시간 안에, 새 글은 5초 안에"를 지키는 가장 작은 하드웨어와, 기존 하드웨어(NPU)로 이미 충분한지를 가린다.
- **무엇을 하나**:
  - [측정] 워크로드 해부: 실제 게시물 길이 분포에서 게시물당 MAC(가중치 / 어텐션), 가중치·활성값 바이트, 길이 버킷 패딩
  - [디자인] 분석 비용 모델: INT8 weight-stationary 배열(크기·클럭) + FP16 어텐션 유닛 + SRAM + DRAM 대역폭 → ms·J/게시물, 밀린 수집 시간. 단가는 수업 L7의 Horowitz 표(45nm)
  - [측정] 기존 하드웨어 기준선: 이 노트북의 Intel NPU(OpenVINO)로 같은 인코더의 ms·J·품질
- **답할 질문**:
  - 수집 한 건에 연산과 메모리 이동이 얼마인가? 어텐션 비중은?
  - 목표를 지키는 가장 작은 배열·SRAM·대역폭은? 그때 J/게시물과 W는? CPU 대비 몇 배?
  - 기존 NPU로 이미 충분한가? 충분하다면 우리 하드웨어의 몫(P)은 어디에 남는가?
- **계획과 이행**: [cp/CP4.md](cp/CP4.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). NPU는 드라이버 컴파일러가 I64 입력과 그래프 안 마스크 생성을 못 내려서, 마스크를 밖에서 넣는 모델로 바꿔 해결 (계산 동일, 코사인 0.99999).
- **기대 → 실제 → 교훈**:
  - 해부: 게시물당 평균 1.74 GMAC(가중치) + 0.14 GMAC(어텐션, 6.6%), INT8 가중치 10.6 MB. 17%가 256토큰에서 잘림.
  - 모델 (추정): **INT8 16×16 배열 + 2 MB SRAM + 로컬 버퍼**면 8시간치를 56분, **8.6 mJ/게시물, 0.85 W**. MAC은 에너지의 6%뿐, 로컬 버퍼 유무가 4.9배를 가른다. 가중치 전부 상주(11.4 MB)는 오히려 손해 (외삽 단가라 불확실).
  - **기대와 다름**: 기존 NPU가 충분할 줄 알았는데 **174분**으로 목표의 약 3배 (측정). 최대치(INT8 11 TOPS, Intel ARK)의 1–2%만 쓰고, 256토큰 게시물에서 특히 느리며, 배치 2 이상은 컴파일 실패. 대신 FP16이라 Recall@10 0.996 (재순위 불필요), 활성 41 mJ/게시물.
  - CPU 저전력 코어 INT8은 286분 (FP32 620분에서 개선, 8시간 안에는 따라잡음).
  - 교훈: 병목은 MAC 수가 아니라 **데이터 이동과, 들쭉날쭉한 짧은 시퀀스를 배치 1로 돌릴 때 범용 NPU가 노는 것**. 다만 NPU가 노는 원인이 구조인지 드라이버인지 아직 모른다 → NORTHSTAR 7-3에 답하기 전에 가려야 한다.
- **계획에서 달라진 점**: before: 보드 계획에 NPU 없음. after: 기존 하드웨어 기준선(NPU, CPU 저전력 INT8)을 추가. 1시간 목표는 가정이라 근거 필요.
- **다음 CP**: CP5 — NPU는 왜 노는가: 구조 탓인지 소프트웨어 탓인지 가린다 (NPU INT8, iGPU 비교, Timeloop/Accelergy로 NPU형 구조에 같은 워크로드 매핑)

## CP5 — NPU는 왜 노는가   (상태: 완료, 2026-10-31)
- **테마**: CP4에서 NPU가 최대치의 1–2%만 썼다. 그 원인이 하드웨어 구조인지 소프트웨어(드라이버·컴파일러)인지 가린다.
- **목적**: 목적형. NORTHSTAR 7-3("기존 하드웨어로 부족하다는 근거")에 쓸 수 있는지 판정한다.
- **무엇을 하나**:
  - [측정] NPU 층별 작업 시간 (PERF_COUNT), 길이 버킷별
  - [측정] 마이크로벤치: 빈 호출, GEMM 하나, 가중치 GEMM 36개만, softmax만, 어텐션 코어를 단계별로 자르기, 마스크 모양 4가지
  - [측정] 전체 인코더 ablation (softmax 제거·분해·변형), NPU INT8 (NNCF), Arc iGPU FP16
  - [구현] 찾은 원인의 우회책을 전체 인코더에 적용해 속도·에너지·품질
- **답할 질문**:
  - NPU 시간은 어디로 가나? MAC 배열이 노는가, 다른 것이 막는가?
  - 소프트웨어로 고칠 수 있는가? 고치면 목표(8시간치를 1시간 안에)를 지키나?
  - 그러면 우리 하드웨어의 몫(P)은 어디에 남는가?
- **계획과 이행**: [cp/CP5.md](cp/CP5.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). 원인을 좁혀 가며 실험을 추가함 (프로파일 → ablation → 어텐션 자르기 → 마스크 모양).
- **기대 → 실제 → 교훈**:
  - 기대: MAC 배열 이용률이 낮을 것. 실제: **GEMM은 최대치의 40–50%** (L ≥ 256, FP16 4.75 TFLOPS 기준, 출처 Chips and Cheese).
  - **시간의 89%(L = 256)가 softmax**였다. softmax 자체가 아니라, 헤드 축으로 브로드캐스트되는 마스크 덧셈과 softmax의 조합을 컴파일러가 SHAVE의 느린 경로로 돈 탓이다 (따로 돌리면 3.4 ms, 모델 안에서는 48 ms).
  - 우회: 마스크를 (B, 12, L, L)로 펼쳐 넣으면 **31.3 → 8.15 ms/게시물, 8시간치 174 → 45분, Recall@10 0.997** (측정). 그래프 재작성(분해·축 변경)은 컴파일러가 되돌려서 효과 없음.
  - NPU INT8은 GEMM이 병목이 아니라 속도 이득 없음 (30.9 ms), 품질 0.932. iGPU FP16은 12–20분, 25–31 W.
  - 남는 구조적 한계: 짧은 게시물마다 가중치 10–21 MB를 약 21–23 GB/s로 다시 읽는다 (추정). 배치 2 이상은 컴파일 실패.
  - 교훈: **이 노트북에서는 "1시간 목표를 기존 하드웨어가 못 지킨다"가 성립하지 않는다.** P는 시간이 아니라 에너지·전력 예산에서 찾아야 한다 (고친 NPU 16 W·0.13 J/게시물 vs 분석 모델 0.85 W·8.6 mJ, 단 공정·범위가 달라 아직 비교 불가).
- **계획에서 달라진 점**:
  - before: Timeloop/Accelergy로 NPU형 구조를 모델링해 예측 vs 실측. after: 설치 못 함 (Docker·WSL 배포판 없음). 대신 마이크로벤치로 구조/소프트웨어를 직접 갈랐고, Timeloop은 다음 CP로.
  - before: 구조 탓이면 P가 생긴다. after: 대부분 소프트웨어 탓 → 시간 기준 P가 약해짐.
- **다음 CP**: CP6 — P 재정의: 같은 공정·같은 범위로 에너지를 비교한다 (Timeloop/Accelergy로 고친 NPU형 구조 vs 설계안, J/게시물과 W 예산). 대상 기기 등급(노트북 / 폰 / 홈 노드)도 이때 정한다.

## CP6 — 노드 박스가 하는 일 전체와, 그중 기존 엣지 칩이 못 하는 것   (상태: 완료, 2026-10-31)
- **테마**: 대상 기기를 상시 켜진 홈 노드 박스로 정하고 암호도 범위에 넣은 뒤(NORTHSTAR 3·6번 갱신), 박스의 일을 처음으로 전부 숫자로 본다.
- **목적**: 목적형. 박스의 메인 워크로드를 측정으로 다시 정하고, 기존 엣지 칩(Hailo, Coral, Jetson, RK3588, Pi 5)이 못 하는 몫을 찾는다.
- **무엇을 하나**:
  - [측정] 게시물마다 하는 암호의 CPU 비용 (Rust): Ed25519, ChaCha20, BN254·BLS12-381 페어링·MSM, Groth16 증명·검증·배치 검증. P코어와 저전력 E코어, 시간과 패키지 에너지
  - [조사] 엣지 칩의 인코더 지원·입력 모양·암호 지원·전력, 가정용 상시 기기 전력 (출처만, 우리는 이 칩들이 없음)
  - [디자인] 박스 부하 모델: 평소 하루 (하루 10⁶건) vs 스팸 폭주 (모든 메시지의 증명을 검증해야 버릴 수 있음)
- **답할 질문**:
  - 익명 자격 증명 검증은 인코더에 비해 얼마나 비싼가?
  - 박스를 정의하는 부하는 평소인가 폭주인가? 그때 무엇이 W를 먹나?
  - 기존 엣지 칩이 이미 하는 것과 못 하는 것은?
- **계획과 이행**: [cp/CP6.md](cp/CP6.md), 조사 원문 [cp/cp6_survey.md](cp/cp6_survey.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). 조사는 에이전트에 맡기고 핵심 수치 1건(Hailo MiniLM)은 원문과 대조.
- **기대 → 실제 → 교훈**:
  - Groth16 검증 (BN254): P코어 **1.39 ms**, 저전력 E코어 **3.5 ms** (Ed25519의 약 45배). 배치 검증 64개로 **0.35 / 0.90 ms** (3.9배, 소프트웨어). 출처(gnark 1.7 ms, BBS 1.64 ms)와 같은 자릿수.
  - 기존 엣지 칩: Hailo-8L이 MiniLM을 이미 121 /s(배치 1), 1.4–1.9 W급으로 돌린다 (벤더). 단 128토큰 고정. **페어링·MSM은 어떤 엣지 NPU도 못 한다** (8/16비트 MAC 배열). Jetson GPU만 가능하지만 ZK 실측 없음.
  - 평소 하루: 어떤 선택지든 활성 1 W 아래, 박스 유휴(2.4–4.4 W, 출처)보다 작다. 인코더를 가속하면 검증이 활성 에너지의 33–48%.
  - **기대와 다름: 박스를 정의하는 부하는 평소가 아니라 스팸 폭주 때의 증명 검증이었다.** 100 Mbps를 1 KB 메시지로 채우면 초당 1.2만 건, CPU로는 24–181 W가 필요하다 (추정). 2 W 박스면 **검증당 ≤ 0.16 mJ**, CPU 배치보다 약 12배, P코어 단건보다 약 90배 효율적이어야 한다.
  - 교훈: 하드웨어의 몫(P) 후보가 바뀐다. **익명 스팸 방지 증명 검증의 W당 처리량**, 그리고 인코더와 같은 칩에서. 기존 엣지 칩에 없는 자리다.
- **계획에서 달라진 점**: before: 상시 전력 모델(Timeloop/Accelergy)을 CP7에. after: 상시 전력보다 폭주 시 검증이 먼저라, CP7을 검증 가속기 비용 모델로 바꾼다. Timeloop은 인코더 쪽과 합칠 때.
- **다음 CP**: CP7 — 증명 검증 가속기의 첫 비용 모델: BN254 페어링·MSM을 검증당 ≤ 0.16 mJ로 처리하는 데 필요한 모듈러 곱셈기 수·SRAM·W (Fp 곱셈 수 세기 + 곱셈기 단가, 기존 ZK·페어링 가속기 출처와 비교)

## CP7 — 증명 검증 가속기의 첫 비용 모델   (상태: 완료, 2026-10-31)
- **테마**: CP6에서 박스를 정의하는 부하가 스팸 폭주 때의 익명 증명 검증으로 바뀌었다. 전용 하드웨어라면 그게 얼마인지 처음으로 숫자로 본다.
- **목적**: 목적형. Groth16(BN254) 검증을 증명당 0.16 mJ(100 Mbps 폭주를 2 W에) 이하로 하려면 곱셈기 몇 개·몇 W인지, CPU 대비 몇 배인지.
- **무엇을 하나**:
  - [측정] 페어링 구성 연산의 CPU 시간 (Fq 곱, Miller loop, 최종 지수승, G1 스칼라 곱), 기본 빌드와 x86 asm 빌드, P코어·저전력 코어. 배치 검증의 패키지 에너지
  - [조사] 254비트 BN 페어링의 연산 수 (herumi/Aranha 외), G1 공식, 제작된 페어링 ASIC 지연
  - [디자인] 검증 유닛 비용 모델: 연산 수 × 254비트 몽고메리 곱 단가 (L7 Horowitz 45 nm, CP4와 같은 표) + SRAM 이동 → 증명당 mJ, 폭주 때 곱셈기 수·W
- **답할 질문**:
  - 전용 유닛의 검증당 에너지는? CPU 대비 몇 배?
  - 100 Mbps 폭주에 필요한 곱셈기 수와 W는?
  - CPU 측정이 연산 수 모델과 맞는가?
- **계획과 이행**: [cp/CP7.md](cp/CP7.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). CP5 교훈대로 CPU 기준선도 asm 빌드로 짜냈다 (검증 1.38 → 1.22 ms).
- **기대 → 실제 → 교훈**:
  - 유닛 (추정, 45 nm, 동적만): 검증 1건 **0.018 mJ**, 배치 64의 증명당 **0.0053 mJ**. 2 W 예산(0.16 mJ)에 9–31배 여유.
  - CPU (측정, 활성): 단건 14.9 mJ, 배치 2.1 mJ (저전력 코어). 유닛이 **약 400–800배** 작다. CPU 소프트웨어가 2배 빨라져도 자릿수는 그대로.
  - 100 Mbps 폭주: 500 MHz 파이프라인 Fp 곱셈기 **1개 이하**(단건 0.54개, 배치 0.16개), **0.07–0.22 W**. 제작된 페어링 ASIC 지연(0.185 ms, 출처)으로 환산해도 1–2개로 같은 자릿수.
  - CPU 대조: Miller loop에 Fq 곱 1.5만 번어치 (모델 0.5만–1만 번), 최종 지수승은 2.2만 번어치 (모델 0.3만–0.5만 번). arkworks 최종 지수승이 특히 덜 최적화됨.
  - 기대와 다름: 큰 유닛이 필요할 줄 알았는데 **곱셈기 하나도 다 안 쓴다**. P(명령 오버헤드, 엣지 NPU는 불가)는 크고, M은 작은 부속이다.
  - 교훈: 남은 설계 질문은 크기가 아니라 **어디에 두느냐**다. 전용 곱셈기로 둘지, 인코더의 INT8 배열로 큰 정수 곱을 할지 (254비트 = 8비트 조각 32개, 조각 곱 1,024개 = 16×16 배열 4번). 그리고 곱셈기의 실제 면적·에너지.
- **계획에서 달라진 점**: 없음. 단, G2 부분군 검사 등 증명 형식 확인 비용을 빠뜨림 → 다음 CP에서 연산 수에 넣는다.
- **다음 CP**: CP8 — RTL 블록 하나: 254비트 몽고메리 곱셈기를 RTL로 쓰고 45 nm(FreePDK45/Nangate)로 합성해 면적·에너지를 재고, CP7 단가를 검증한다. INT8 배열 재사용안과 비교 (WSL Ubuntu에 Yosys/OpenROAD)

## CP8 — 박스 아키텍처와 검증 유닛의 위치   (상태: 완료, 2026-10-31)
- **테마**: CP7에서 검증 유닛은 작아도 된다고 나왔다. 이제 크기가 아니라 위치와 형태를 정한다. 사용자 요청대로 RTL 전에 그림과 대안부터.
- **목적**: 목적형. 전용 유닛 / 인코더 INT8 배열 재사용 / 호스트 코어 명령 확장 / 소프트웨어 중 무엇이 100 Mbps 폭주를 2 W 박스에서 견디는지, 미리 적은 규칙으로 판정한다.
- **무엇을 하나**:
  - [측정] 증명 디코딩의 곡선·부분군 검사 비용 (CP7이 빠뜨림)
  - [디자인] 판정 규칙을 결과 전에 적음: R1 증명당 ≤ 0.08 mJ, R2 초당 ≥ 24,400 증명, R3 인코더·호스트 간섭 없음 → 곱셈기 면적 순
  - [디자인] 대안 A–D 모델 비교, 아키텍처 보드(L0 박스 전체 / L1 대안 / L2 유닛 내부 / 결정 기록) 새로 만듦
  - [조사] Apporto CAD 환경 확인 (VCS, Design Compiler, FreePDK45)
- **답할 질문**:
  - 검증 유닛은 어디에, 어떤 형태로 둬야 하나?
  - 인코더 하드웨어를 나눠 쓸 수 있나?
  - 증명 디코딩·검사는 얼마나 비싼가?

## CP10 — 파이프라인 곱셈기   (상태: 완료, 2026-10-31)
- **테마**: CP9에서 곱셈기 하나는 295 MHz에 그쳤다 (한 사이클에 곱셈기 3개가 직렬). 같은 면적으로 처리량을 올려 W=64 × 6(1.75 mm²)을 이길 수 있는지 본다.
- **목적**: 목적형. 독립 곱셈 S개를 번갈아 넣는 인터리브 + retiming이 제값을 하는지, 미리 적은 규칙으로 판정한다.
- **무엇을 하나**:
  - [디자인] 그림과 대안(S = 1–4), 판정 규칙(R1–R3, 총면적 20% 이상 절감, 클럭 1.5배 미만이면 인터리브 폐기)을 결과 전에 CP10.md에 적음
  - [구현] 인터리브 곱셈기 RTL (W, S 파라미터, valid/ready 스트림, 태그), 테스트벤치, retiming 합성 스크립트
  - [측정] VCS 1,000개 벡터, Design Compiler `compile_ultra -retime` + FreePDK45, 파형 기반 전력
- **답할 질문**:
  - 인터리브로 클럭이 S배 가까이 오르나?
  - R2를 채우는 총면적이 기준보다 얼마나 줄어드나?
- **계획과 이행**: [cp/CP10.md](cp/CP10.md), 그림: [아키텍처 보드](https://claude.ai/artifact/UMCvv2UR1zELj4B7AW3KTP), [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu). S = 1–4 네 가지를 Apporto에서 동시에 합성.
- **기대 → 실제 → 교훈**:
  - 기능: 모든 구성 오류 0. 곱셈 1번 = K = 4사이클 (CP9는 6).
  - 기대: 클럭 약 S배. **실제: S = 2–4 모두 1.20–1.22배 (약 360 MHz)**. 최장 경로가 retiming된 곱셈기 안에서 2.78 ns 아래로 안 내려감. 원인 미확인.
  - **판정: 인터리브 폐기** (규칙: 클럭 1.5배 미만). **S=1 채택**: 0.28 mm², 300 MHz, 곱셈 1번 1.76 nJ. R2에 4개 → **1.13 mm² (기준의 0.65배)**, 증명당 0.022 mJ, 폭주 중 0.27 W.
  - 규칙 때문에 버린 이득: S=2는 0.91 mm²로 20% 더 작다. 복잡도 대비 이득이 작다고 미리 정한 대로 따름.
  - CP9 W=256도 끝남: 1.05 mm², ≤ 125 MHz, 4.22 nJ → 넓은 폭은 손해라는 결론 그대로.
  - 교훈: 이득은 파이프라인이 아니라 제어(적재·마무리를 다음 곱셈과 겹치기)에서 나왔다. 합성 도구의 retiming을 믿고 RTL을 단순하게 두는 전략은 이 곱셈기에서는 통하지 않았다.
- **계획에서 달라진 점**: before: 파이프라인이 답일 것. after: 제어 개선이 답, 파이프라인은 손으로 나눌 때만 다시 고려 (새 뒤집을 조건: 손 파이프라인이 ≥ 443 MHz면 인터리브 재개).
