## CP0 — 영감을 줄 논문 찾기   (상태: 완료, 2026-10-30)
- **테마**: 우리 아이디어와 맞닿은 탑 컨퍼런스 논문을 모은다.
- **목적**: 정찰. **가늠하는 것**: server-blind 노드의 세 갈래(엣지 검색·인코더 / 프라이버시·암호 하드웨어 / 온디바이스 ML 시스템)에 이미 어떤 하드웨어·시스템 연구가 있고, 무엇을 빌려 올 수 있는지.
- **무엇을 하나**:
  - [조사] 1강의 탑 컨퍼런스(ISCA, MICRO, ASPLOS, HPCA, MLSys, DAC, ICCAD, DATE, ASP-DAC, ISSCC, VLSI, ESSCIRC, CICC, NeurIPS, ICCV, CVPR, ICML, AAAI)에서 후보 15편 안팎
  - [조사] 후보마다 목적 / 결과 / 전망 초간단 브리핑, PDF를 `refs/cp0/`에 저장
  - [조사] 가장 마음에 드는 한 편을 수업 리뷰 양식으로 리뷰
- **답할 질문**:
  - 팀원 셋에게 하나씩 던질 논문은?
  - 우리 제안의 Gap 문장("전력 제한 노드에서 검증·복호화·임베딩·삽입을 마감 안에")이 아직 유효한가?
- **계획과 이행**: 세 갈래로 나눠 병렬 조사 → 학회·연도·공개 PDF 검증 → 브리핑 → 리뷰 1편. 세부는 [cp/CP0.md](cp/CP0.md). 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu)
- **기대 → 실제 → 교훈**:
  - 기대: 후보 15편 안팎. 실제: 18편 (갈래당 6편), 18편 모두 PDF 1쪽 제목까지 일치 확인.
  - 리뷰: IKS (ASPLOS'25), 정확 검색 + 근접 메모리 top-K. `refs/cp0/IKS review yoonkyul.txt`
  - 팀원용: EdgeBERT(인코더), NDSearch(메모리 계층), PipeZK(익명 신원 암호). 영어 목록 `refs/cp0/HANDOUT.md`
  - 교훈 1: 엣지 검색 하드웨어(RoCR, ICCAD'24)는 이미 있다. 18편 중 아무도 안 다룬 것은 **마감 안의 수집 경로**와 **검색 중 삽입**. Gap 문장을 이쪽으로 좁힌다.
  - 교훈 2: IKS에서 정확 검색 시간의 약 99.9%는 메모리 스캔. 우리 인덱스는 최대 약 384 MB (추정)라 검색은 쌀 수 있다 → 병목은 인코더일 가능성. CP1에서 잰다.

## CP1 — 노드 작업 한 건의 단계별 비용 해부   (상태: 완료, 2026-10-30)
- **테마**: server-blind 노드가 게시물 하나를 받고, 검색 하나에 답하는 데 어디에 시간이 드는지 처음으로 숫자를 얻는다.
- **목적**: 목적형. 메인 워크로드(인코더 / 암호 / 검색)를 측정으로 고를 근거를 만든다. 제안서 2단계의 최소 버전.
- **무엇을 하나**:
  - [구현] 참조 파이프라인 `src/`: 수집 = Ed25519 서명 검증 → ChaCha20-Poly1305 복호화 → 토큰화 → MiniLM INT8 인코딩 → 색인 삽입. 쿼리 = 인코딩 → 정확 top-10
  - [측정] 실제 Reddit 게시물 길이 분포로 단계별 ms (중앙값, P99), 1스레드와 전체 스레드
  - [측정] 인덱스 10⁴·10⁵·10⁶에서 정확 검색 ms
  - [측정] INT8 인코더의 Recall@10 (FP32 정확 검색 기준, 목표 ≥ 0.95)
  - [디자인] 부하 산수: 커뮤니티 규모 → 노드의 초당 게시물 → 이 노트북이 포화되는 지점
- **답할 질문**:
  - 수집 한 건에서 지배적인 단계는? 암호는 정말 인코더보다 한두 자릿수 싼가?
  - 10⁶개 정확 검색은 몇 ms인가? (CP0 교훈: 쌀 것이다)
  - INT8 인코더는 Recall@10 ≥ 0.95를 지키나?
  - 이 노트북은 사용자 몇 명 규모까지 5초 신선도를 지키나?
- **계획과 이행**: [cp/CP1.md](cp/CP1.md), 그림: [체크포인트 보드](https://claude.ai/artifact/UA7msgwvuiBWANweu2kKuu)
- **기대 → 실제 → 교훈** (예비 측정: 전원 계획 균형, G-Helper 모드 미확인):
  - 수집 한 건: 1스레드 P50 21.5 ms / P99 53.9 ms, 전체 스레드 P50 7.0 ms. **인코딩이 약 98%, 암호(검증 + 복호화)는 약 0.5%.** 기대대로 인코더가 병목.
  - 쿼리: 10⁶개 정확 top-10 25 ms (1.5 GB, FP32), 쿼리 인코딩 3.4 ms. 기대대로 싸다.
  - **기대와 다름 1**: INT8 Recall@10 = **0.875** (목표 0.95 미달, 쿼리 31%가 0.9 미만).
  - **기대와 다름 2**: 배치 8/32가 배치 1보다 **약 2배 느림**. 길이가 들쭉날쭉해 패딩 낭비 (토큰 중앙값 128, 18%가 256에서 잘림).
  - 교훈: 평균 부하는 노트북에 문제가 아니다 (사용자 10⁵명 × 하루 10건이어도 1스레드 7.2 h/일). 진짜 압박은 **오프라인 후 밀린 수집**(전체 스레드로도 44분)과 **약한 기기**. 사용률은 가정이라 출처가 필요.
- **계획에서 달라진 점**: before: 단계별 ms + J. after: J는 못 잼 (Windows 전력 계측 도구 없음) → CP2로.
- **추가 (공식 조건 재측정)**: 예비 측정과 대부분 5% 안쪽 차이, 결론 그대로. 조건 정정: 예비 측정 때도 실제로는 Windows 최고 성능 모드였다 ("균형"은 전원 계획 이름일 뿐). 세부는 cp/CP1.md 끝.

## CP2 — 인코더 기준선 확정   (상태: 계획, 2026-10-30)
- **테마**: 가속기와 비교할 공정한 CPU 기준선을 정한다. 제안서 규칙: 모든 하드웨어는 같은 Recall에서 비교.
- **목적**: 목적형. Recall@10 ≥ 0.95를 지키는 가장 싼 인코더 설정과, 그 설정의 ms·J를 확정한다.
- **무엇을 하나**:
  - [측정] 양자화 방식별 품질과 속도: 동적 INT8(현재 0.875), 정적 per-channel INT8(우리 게시물로 보정), FP16, FP32
  - [측정] 길이 버킷 배치 (같은 길이끼리 묶기) vs 배치 1
  - [구현] 에너지 측정 방법 확보 (Windows 패키지 전력 도구 또는 ASU Sol의 Linux RAPL)
  - [측정] 약한 기기 대용: E코어만 / 전력 제한 상태에서 수집 비용과 밀린 수집 시간
  - [측정] Recall 평가 확대 (코퍼스 2만 이상, 쿼리 1,000개)
- **답할 질문**:
  - 0.95를 지키는 가장 싼 설정은? INT8을 포기해야 하나?
  - 길이 버킷이 배치 손해를 얼마나 되돌리나?
  - 게시물 한 건 수집에 몇 J인가? 약한 기기에서 8시간치 밀린 수집은 몇 분인가?
