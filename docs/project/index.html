1. The goal, and why

Replace the community operator with compute on users' own devices, so an online community can be as free, anonymous and forgetful as a real-life conversation and still be as easy to use as today's sites. Our part is the hardware that makes that compute cheap.

On today's forums the operator can read everything, can restore deleted posts, and comes under pressure that shakes the whole community. In a real-life conversation nobody is monitoring, only the speaker is responsible, and words are gone once spoken. We want those properties online:

  • Server-blind: servers and storage nodes never see plaintext. We don't allow any optimization that breaks this, such as letting the server build the search index.
  • No operator: nobody gets privileged access.
  • Forgetting: if the author deletes a post, the original is gone.
  • Creating identities is expensive: users are anonymous, but running many accounts is hard.
  • We don't give up usability: search, feeds, recommendations, votes, comments, chat and sub-communities stay. If peer-to-peer rules a feature out as it exists today, we replace it with something that meets the same need.

Earlier peer-to-peer communities gave up either autonomy and anonymity or usability. We get both by paying in compute, and that compute goes to two places:

  1. ML, to replace the operator's services: search (text embeddings + top-k), feed ranking, spam and bot detection.
  2. Crypto, to prove things without revealing them: signature checks, decryption, and anonymous credentials and zero-knowledge proofs.

The target device is an always-on home node box, something you leave running like a router or a NAS. Both ML and crypto are in scope for the course project. The project is not a generic "edge vector-search accelerator"; those already exist. What sets us apart is the conditions that server-blindness creates.

Scope. What the course grades is the hardware and systems work, but we don't limit what we implement. We build everything except physical devices and silicon: the protocol, the node software, the client, the community algorithms (spam, feeds, forgetting), and a simulation of many boxes and many users. A chip we can't fabricate is replaced by its cycle and energy model and attached to that software. Image posts are in scope too, so the box will also embed images.

2. The whole system: a community with everything but the hardware

We're building the community itself, not only the chip: M users and N home node boxes, running on one laptop. The design is done, the simulator's core (which messages reach which box) has results, and the box software on top of it (ingest, search, feeds, votes, forgetting, private rooms) now runs through a whole simulated day, both further down in this section. One question decides the approach: what runs for real, and what is a model?

  • Functions run for real (emulation). The box software is real code: real ciphertexts, real signatures, real embeddings, real search results. It runs on the laptop CPU instead of the box's hardware but computes the same thing.
  • Time and energy are simulated. We can't run hundreds of boxes in real time, so the simulator runs on a virtual clock (discrete events). Each task's time and energy come from our chip models (the verify-unit cycle model, the encoder's Timeloop + Accelergy model) and, for host work, from laptop timings scaled to a Pi 5-class CPU.
  • Each message is computed once. When many boxes receive the same post, the result (verification, embedding) is computed once and shared; each box is still charged the modeled time and energy.
  • Only the demo runs in real time: a few boxes as real processes, with a web UI to write posts.

Sensitivity. Limits. One user per box; a box shared by several people gets that many times the load. Who stores what: a smaller knob than we expected

Until now every chip number assumed that each box receives every public post. That was never written down as a choice. How posts are replicated across boxes decides how much one box has to ingest, so we compared three policies:

  • All: every box receives every public post (what the chip numbers assume today).
  • Subscribed: a box receives only the sub-communities its owner subscribes to.
  • Subscribed + k: subscriptions, plus the boxes share out any sub-community that has too few copies, so its posts stay available.

We decided in advance to take the policy that keeps availability (the chance that some other box holding a sub-community's posts is online while the author's box is off) at or above 99% in every sub-community, and of those, the one with the lowest load on the busiest 1% of boxes at the peak hour. Subscribed only won: every sub-community stays at or above 99% at every community size, and no sub-community had fewer than 3 subscribers, so "+ k" added nothing. But it barely helps the boxes that matter: the average box gets 0.78× the load of "All", the busiest 1% still get 0.94× simulation model. Activity is concentrated in popular sub-communities that nearly everyone subscribes to.

What the box software does in a day

On top of the simulator core, every box now does its real job on each message: check the signature and the proof, decrypt, embed, index, answer searches, rank a feed, count votes, forget deleted posts, and keep private rooms. Results (search hits, vote tallies, whether a deleted post is really gone) come from real code. Time comes from the chip models, and host work from laptop timings scaled to a Pi 5-class CPU. We ran a community of 10,000 boxes for one simulated day. Every box forwards gossip, but only 20 sample boxes keep full state (search index, tallies, the vote tags they have seen); the rest reuse the same result for the same message and only count work and time, because a separate index on every box would take several GB for 30 days of posts. The 30 days of older posts are loaded as already synced, and the day's new messages spread by gossip. Post text comes from our 2010 Reddit sample; images are synthetic (we haven't downloaded an image dataset).

How images travel

Pushing whole images clogs home uplinks (above). We compared three ways to move an image post, in the largest sub-community (9,420 boxes), 300 image posts 10 s apart simulation model:

  • Push: every hop sends the 177 KB image to its mesh neighbors.
  • Envelope + fetch: push only an envelope (header + thumbnail, 10 KB estimated); each box fetches the body once from the neighbor that sent it the envelope, then embeds it.
  • Envelope + author's embedding, spot-checked: the author's box puts its INT8 embedding (512 B) in the envelope, so boxes index the post on arrival. A few boxes per post (on average c = 14 of them) fetch the body, embed it again and flag a mismatch; a box that gets a flag hides the post and checks it itself.

We decided in advance: an image post must be searchable on subscribed boxes within 5 s (P99 at 20 Mbps). The embedding option also had to show that honest boxes almost never get flagged (false alarms ≤ 10-3), that a fake embedding is hidden on every box within 60 s, and that the chance no box checks a post is ≤ 10-6. Among the options that pass, the fewest image encodings on the busiest 1% of boxes wins, then the least uplink.

  • Envelope + fetch won. All three meet 5 s at 20 Mbps. The embedding option failed its first integrity condition (next bullet). Push and envelope + fetch tie on encodings (1 per post each), and envelope + fetch uses 0.21× the uplink. It isn't faster than pushing (2.01 vs 1.82 s at 20 Mbps), because every hop adds a request round trip; the gain is uplink (0.21×) and duplicates (0.06×). At 5 Mbps both miss 5 s (6.1 / 5.9 s). We had agreed beforehand that missing only at 5 Mbps keeps the choice, so boxes on slow uplinks are listed as a limit.
  • The fast option failed because boxes don't compute the same embedding. It held up against attack: in a test with 20 fake and 20 honest embeddings at 20 Mbps, all 20 fakes were caught and hidden on every box within 1.32 s (P99), and the chance that no box checks a post is 8.2×10-7 simulation model. But a box with a different precision gives a different embedding for the same image, and the gap is bigger than the gap between different images (table below). No threshold can tell an honest box apart from a fake embedding.

3. What the box must do, and why it needs hardware

Each box ingests encrypted posts. For every post it verifies the signature and the anonymous-credential proof, decrypts, runs a small text encoder (MiniLM) to embed the post, and inserts the vector into a local search index. It also answers search queries. Image posts add an image encoder (CLIP ViT-B/32 image tower) to that path. A first estimate scales the text encoder by MAC count: 4.41 GMAC (2.36× a text post), 19.0 ms and 18.7 mJ per image estimated; the next step models it properly.

The box and chip numbers in this section and the next two assume each box receives all 106 posts/day, messages are 1 KB, and a flood fills a 100 Mbps link assumption. The first simulator results (section 2) put the ordinary-day assumption at 26× what the busiest 1% of boxes ingest at the peak hour in a 1M-user community, so the ordinary-day numbers below are pessimistic. The simulated day (section 2) agrees: even the busiest boxes keep their encoders busy only 0.003% of the peak hour. The flood numbers don't depend on it.

Why the flood sets the size of the box: in an anonymous community you can't filter messages by sender. The only way to throw a message away is to verify its anonymous-credential proof first (Groth16 on the BN254 curve, the kind Semaphore/RLN use). If you can't verify fast enough, spam uses up all of the box's ingest capacity. Valid messages are capped by rate-limiting proofs, so the encoder's load stays modest. The simulator confirms this from the other side: on an ordinary day even the busiest boxes of a 1M-user community verify at most 4.2 proofs/s, 0.03% of the unit's capacity simulation model. Invalid proofs, on the other hand, cost an attacker nothing to make, so the hardest floods mix invalid proofs in to break batch verification (see Floods of invalid proofs).

The hardware gap: with a 2 W power budget assumption, the box must spend ≤ 0.16 mJ per verification. That is about 12× more efficient than batched verification on a CPU and about 90× more efficient than one-at-a-time verification on a P-core estimated. Our unit stays under that even in the worst case: 0.077 mJ per proof at the worst mix of invalid proofs estimated. Existing edge NPUs (Hailo, Coral, RK3588) are 8/16-bit MAC arrays and have no way to do pairings or MSMs source. A Jetson GPU could in principle, but nobody has published ZK numbers for it. The encoder, by contrast, is already handled: a Hailo-8L runs MiniLM at 121 posts/s in a 1.4–1.9 W-class module vendor.

So our hardware contribution is proof verifications per watt, on the same chip as the encoder. With a Hailo-8L as the encoder and verification left on a CPU core, verification would be 33% of the box's active energy on an ordinary day estimated.

Inside the verify unit

The unit handles the whole job of accepting a proof, not just the pairing: decoding and subgroup checks are 26% (measured) to 36% (model) of the work per proof. Left on the CPU, they would need 1.4 P-cores during a flood.

Scroll the diagram sideways →

Keeping the multipliers busy took three things: as many adders as multipliers (there are 2.5 additions per multiplication), running all proofs in a batch in lock-step, and a lookahead window a few hundred operations deep. Before we switched to lock-step order, the earlier 5-multiplier unit managed 14,110 proofs/s. Reordering by dependency depth also fills the multipliers, but then the buffer grows to 740 KB. So the throughput-versus-buffer tradeoff is set by how the microcode orders operations, more than by the hardware.

The unit's size has moved twice. It started at 5 multipliers + 4 adders, sized for a flood of valid proofs. Floods of invalid proofs, where many proofs must be checked alone, pushed it to 8 + 8 at first. Making a lone check cheaper brought it back to 6 + 6 (see Floods of invalid proofs). A lone check now has 4.2 additions per multiplication, so the adders matter as much as the multipliers. The operand register file's extra ports and the crossbar for 6 + 6 are not in the area model yet.

The box is a Pi 5-class host SoC (network, storage, queries, Ed25519, ChaCha20) with LPDDR4, plus our accelerator chip on PCIe. The chip has two power domains that are switched off whenever they have no work, and a small always-on part.

Floods of invalid proofs

Batch verification checks n proofs at once with one randomly weighted pairing product. If even one proof in the batch is invalid, the whole batch fails and the unit has to find out which proofs are bad. For an attacker, valid proofs are expensive: each needs an identity and a generated proof, and exceeding the rate limit reveals their secret key. Invalid proofs are free: any three points on the curve pass the format and subgroup checks. So the cheapest attack is to mix invalid proofs into the flood. We modeled every share of invalid proofs from 0 to 100%. Honest messages are never dropped: every valid proof in a failed batch is still found and accepted.

The key number is the fixed cost of one check: the final exponentiation, the Miller loops for the verifying key's three pairs, and the public-input multi-scalar multiplication. In our first count it was worth 4.3 proofs, and a check of a single proof is almost nothing but this fixed cost. Field operations per check, decoding excluded, as first counted counted:

How to find the bad proofs in a failed batch. All four strategies run on the same hardware:

  • A, one by one: if a batch fails, check each of its n proofs alone.
  • B, split in half: retest each half as a batch. If the left half passes, the right half must contain a bad proof, so it is split again without being tested.
  • C, split in half and keep Miller values: after a failure, compute each proof's Miller loop value once and store it (384 B per proof). Each subtest then only multiplies stored values and pays the fixed cost.
  • D, adaptive batch size: pick the next batch size n from the recent failure rate, down to n = 1 (every proof alone) when many proofs are bad.

That is why deferring the check raised the worst case only a little (13,306 → 13,429). Deferring is safe: a proof that fails the test is discarded anyway, and every accepted proof still passes the subgroup check, so the set of accepted proofs doesn't change. A proof built to pass the test but fail the subgroup check costs the same as a valid one, which the numbers above already cover.

  • Additions are now 4.2× multiplications, so the remaining lever is on the add side. Cutting additions by 7%, or a better adder (for example, multiplying by the constant 9 with one shift-and-add), looks like enough for 5 multipliers, saving 0.28 mm² (2.5% of the chip).

Can the network layer stop invalid proofs instead?

Peer-to-peer networks already penalize peers that send bad messages, so we checked whether that caps how many invalid proofs reach one node. We found no source that gives a numeric per-node cap source:

  • gossipsub v1.1 forwards only messages that passed validation, so invalid proofs come only from directly connected peers. Each invalid message adds a penalty that grows with the square of the count, with no cap. Once a peer's score falls below the graylist threshold, its RPCs are ignored.
  • nwaku, the Waku RLN-relay implementation (relay.nim): an invalid proof is rejected and penalized with weight −100, the graylist threshold is −10,000, and bad peers are disconnected. It verifies proofs one at a time, without batching. From that, a connection is cut after about 10 invalid proofs estimated, assuming a topic weight of 1.
  • New connections: go-libp2p's resource manager allows 0.2/s per IPv4 /32, 0.2/s per IPv6 /56 and 0.5/s per IPv6 /48, with no global cap. We didn't find the equivalent limit in nim-libp2p, which nwaku uses.

So for the earlier unit's 6% limit (about 730 invalid proofs/s), an attacker needs 73 new connections per second, which about 366 IPv4 addresses (or 146 IPv6 /48s) can supply estimated. Penalties limit what one connection can do, not an attacker with many addresses. Having the chip itself survive any share of invalid proofs is the most robust way to keep spam from exhausting ingest.

How the new encoder estimate compares with our earlier hand model

Earlier we estimated the encoder by hand from 45 nm energy-per-operation tables (dynamic energy only): 8.55 mJ per post. The new tool-based estimate is 7.90 mJ, 0.92× the old one model. We had agreed that a gap above 2× would force us to redo the ordinary-day numbers; it stayed well inside that.

The totals agree, but the parts don't. One INT8 MAC costs 1.27 pJ in the Aladdin tables, 4.2× the 0.3 pJ we used before (INT8 multiply 0.2 + INT32 add 0.1). Memory is cheaper than we assumed: the 2 MB global SRAM is 12.6 pJ/byte (we used 25 pJ/byte from a 1 MB table entry) and DRAM is 64 pJ/byte (we used 160). Our synthesized Montgomery multiplier also came out 4.2× its early estimate, so the logic estimates move in the same direction.

Idle power depends on the SRAM cell and on power gating

The default model uses low-standby-power SRAM cells (CACTI's itrs-lstp), which barely leak. With high-performance cells (itrs-hp), the 2 MB SRAM alone leaks 1.04 W instead of 0.05 mW, and the whole chip leaks 1.10 W estimated. With gating, that chip still does the ordinary day at 0.19 W, the flood at 0.59 W and the backlog at 1.96 W (just under 2 W). Without gating it burns 1.1 W doing nothing, 22× our 50 mW idle limit. The catch with low-standby cells: a random access to the 2 MB array takes 2.37 ns, longer than the 2 ns cycle at 500 MHz, so it would need banking or two-cycle access, which the model doesn't include.

6. Paths we tried and dropped

  • Sizing the box for "every box ingests all 106 posts a day." Nobody chose that number; it was a hidden assumption. With behavior from Reddit's statistics, the busiest 1% of boxes in a 1M-user community embed 0.45 text posts/s at the peak hour, 1/26 of the 11.6 posts/s we had assumed simulation model. We had decided in advance to re-decide the encoder toward smaller if real ingest fell under a tenth of the assumption. Instead: the encoder's size has to be justified by search latency, the backlog after a box has been offline, and images. In the simulated day the encoders were busy only 0.003% of the peak hour, even on the busiest boxes.
  • Bundling each user's votes into one proof every 50 s. Every vote carries its own proof, and votes are about 90% of proof-carrying messages. Bundling was meant to cut that, but each bundle held 1.00 vote on average and vote counts arrived 26 s later on average simulation model. It technically passed our advance rule (lower verification, counts within 60 s) by 0.1%, which is no real gain. Instead: one proof per vote, carrying both a rate-limiting tag and a per-post tag (+1.3% verification cost estimated).
  • Vote proofs with only a rate-limiting tag. They cap how often someone votes, but let one person vote several times on the same post within the limit. A per-post tag alone has the opposite gap (no limit across posts). Instead: both tags in one proof, the only design that keeps one vote per post, a rate limit and unlinkability.
  • Pushing whole images through the gossip network. Every hop sends 177 KB to each mesh neighbor in turn: 1,181 KB of uplink per box per image post on average simulation model. Instead: push a small envelope and fetch the body once, the same number of image encodings at 0.21× the uplink, though not faster (2.01 vs 1.82 s at 20 Mbps).
  • Shipping the author's image embedding and spot-checking it. It was by far the fastest (0.40 s at 20 Mbps, 0.01× the image encodings) and caught every fake embedding within 1.32 s simulation model. But the same image gives cosine similarity as low as 0.877 between FP32 and INT8, while two different images reach 0.981 measured, so no threshold separates an honest box from a fake. Could come back if every box ran a standard, deterministic INT8 encoder with bit-identical output, which the next step looks at as a chip requirement.
  • Plain INT8 encoder. No INT8 variant reached our quality bar (Recall@10 ≥ 0.95 against exact FP32 search); the best was 0.878. Mixed precision needed 83% of weight MACs left in FP32 and was only 1.1× faster. Instead: ingest in INT8 and re-rank the top 20 in FP32 at query time. That gives Recall@10 0.993 and ingest 1.9× faster with 2.2× less energy than FP32 (3.70 ms, 0.25 J/post) measured, at about 252 ms and 18.7 J per query estimated.
  • "The laptop NPU is too slow, so we need hardware." Out of the box it was about 3× over the backlog target. But 89% of its time (at 256 tokens) went to a softmax plus broadcast mask that the compiler sent down a slow path. Expanding the mask fixed it: 45 min, Recall@10 0.997 measured. It was a software problem, so we moved the target to the always-on box and argued from power instead of time.
  • Doing the crypto on the encoder's INT8 array. 615 proofs/s, 40× short estimated. A weight-stationary array pays off only when one operand stays put, but pairing math is mostly variable × variable, and the array has no integer carry handling.
  • A big-integer multiply instruction on the host core. The energy was fine (0.012 mJ/proof) but it ran at half the throughput and would tie up the host core for the whole flood estimated.
  • Software only. Batched verification on one low-power core: 989 proofs/s, 2.06 mJ/proof measured. It misses on both energy and throughput.
  • Wider multipliers (128/256-bit word). They were bigger, slower and used more energy per multiply (table above).
  • Interleaving independent multiplies through a pipelined multiplier and letting the tool retime it. We had decided up front that it needed a 1.5× clock gain to justify the complexity. The clock rose only 1.20–1.22× (about 360 MHz): the critical path stopped at 2.78 ns inside the retimed multiplier, and we haven't found out why. We gave up a real gain to stick to that call: the 2-way version would have been about 20% smaller (0.91 vs 1.13 mm² for a 4-multiplier unit).
  • A smaller encoder array (8×8 or 16×16). At 500 MHz, 16×16 clears the 8-hour backlog in 106 min and 8×8 in 401 min, both over the 60-minute target model. 16×16 would pass at 1 GHz (53 min), but we fixed the clock at 500 MHz beforehand and treated 1 GHz only as a sensitivity check.
  • Keeping the 5-multiplier verify unit and relying on smarter batch splitting. It was sized with 2× headroom over a flood of valid proofs, but no splitting strategy can go below the cost of checking every proof alone, and that drops it to 7,469 proofs/s, 61% of the flood, when every proof is invalid (with our first operation count) cycle model. 7 multipliers + 7 adders still came up 5% short, so at first we went to 8 + 8.
  • An 8 + 8 verify unit. Part of that size came from our own operation count being conservative (general instead of cyclotomic squarings, a plain binary exponent). With the library's real formulas, a precomputed verifying-key table and a deferred subgroup check, the cost to reject an invalid proof fell to 0.65×, and 6 multipliers + 6 adders keep up at any share of invalid proofs (2.12 mm² instead of 2.69 mm²) cycle model.
  • Sending proofs uncompressed. It skips three square roots per proof but doubles the proof to 256 B and changes the wire format, and the smallest unit that keeps up is still 6 + 6 (5 + 6 reaches 97% of the flood) cycle model. We decided in advance to change the format only if it saved a multiplier.
  • Caching each proof's Miller loop value to split failed batches faster. Every subtest still pays the fixed cost of a check, so it was no better than simply recomputing, and it needs extra storage (48 KB at n=128) cycle model.
  • Relying on network-layer peer penalties to stop invalid proofs. Peers that send invalid proofs get penalized and disconnected, but we found no source for a numeric per-node cap, and an attacker with a few hundred IP addresses gets around it estimated. So the chip itself has to survive a flood of nothing but invalid proofs.
  • A verify-only chip next to a Hailo-8L. The Hailo's share of ordinary-day power (0.134–0.182 W) is more than our whole chip (0.092 W) estimated, and it truncates posts to 128 tokens.

Good places to start (no hardware tools needed)

  • The client web UI. A browser client for the community: post text and images, read a feed, search, vote, delete, chat in a private room. It talks to the same client API that the simulated users use, so the same UI works against the simulation and against the demo boxes. No CAD tools or chip knowledge needed.
  • The behavior parameters we had to estimate. Most come from Reddit's public statistics now (table in section 2), but we found no source for the time-of-day curve, a direct measure of how popularity spreads across sub-communities, post body length, page views per daily user, or any non-Reddit community such as DCInside. Subscriptions per user and the share of boxes online are estimates too. A source for any of these would firm up the per-box load.
  • Real photos for the image tests. Our image tests use synthetic images, which look too alike to CLIP: the image-search check failed for that reason, and the embedding tolerance may differ on photos. Suggesting a small, openly licensed photo set (a few hundred images) would let us rerun both.
  • Image posts on slow uplinks. With envelope + fetch, an image post is searchable within 2.01 s at 20 Mbps but takes 5.86 s at 5 Mbps (P99), over the 5 s target simulation model. Prior art on moving large payloads through gossip networks, or a delivery trick for slow boxes, is welcome.

Open hardware questions you could take

  • A deterministic INT8 encoder. The fastest way to deliver image posts needs every box to compute bit-identical embeddings. Off-the-shelf dynamic INT8 doesn't: it even changes with the batch (cosine as low as 0.977, batch 1 vs 16) measured. What would a standard encoder with fixed integer arithmetic and static, batch-independent quantization take, and what would it cost in accuracy and area? This feeds directly into the next step.
  • ARM measurements. We have no verification costs on ARM, from measurement or from any source. A real box CPU is likely ARM. Running the Groth16 / Ed25519 / ChaCha20 benchmarks on a Raspberry Pi 5 would fill that gap.
  • Pi 5 + Hailo measurements. The Hailo numbers are vendor figures on an x86 host with PCIe Gen3 x4, and the Pi 5 has x1. MiniLM power isn't published (we borrowed a vision-model figure), and we don't know its idle power. The input is fixed at 128 tokens, while our median post is 128 tokens and 17% are cut even at 256. Measuring throughput, power, idle power, and the quality loss from truncation would firm up the comparison.
  • Encoder on the Pi 5 CPU. We haven't measured the encoder's energy on a Pi 5 CPU, so we couldn't evaluate the cheapest option (verify-only chip, encoder on the host). If the CPU handles an ordinary day within about 0.09 W, that option comes back.
  • Fewer additions in the verify unit. A lone check now does 4.2 additions per multiplication, and 5 multipliers + 6 adders already reach 97% of the flood. Cutting additions by 7%, or a smarter adder (for example, a three-input adder, or multiplying by the constant 9 with one shift-and-add), could drop a multiplier and save 0.28 mm² estimated.
  • RTL for the rest of the verify unit, and for the encoder MAC. Only the Montgomery multiplier exists in RTL. The 254-bit adders, the operand buffer, the microcoded sequencer and the encoder's INT8 MAC are still estimates. With 6 multipliers and 6 adders, the operand register file needs more ports and a crossbar, which the area model leaves out.
  • Hand-pipelining the multiplier. We'd like to know why retiming stops at 2.78 ns. A hand-split pipeline reaching ≥ 443 MHz (1.5×) would make interleaving worth reopening.
  • A better scheduler. Our scheduler is a simple greedy one in program order, and our throughput assumes the microcode runs independent checks side by side in lock-step. Run one at a time, a lone check on the 6 + 6 unit takes 26,542 cycles, which is 11,303 proofs/s, short of the 12,207/s flood. The utilization we assume also comes from batches, which have fewer additions per multiplication than lone checks. A scheduler that keeps the unit busy on lone checks would confirm 6 + 6; if it can't, 7 multipliers + 6 adders is the fallback.
  • Adapting the batch size against a changing attacker. Our results pick the batch size knowing the invalid share, which is an upper bound. A real unit has to estimate it from recent failures, and an attacker who switches the share suddenly costs it a few batches. Queueing delay during the flood also isn't modeled.
  • Is our quality bar right? The strict Recall@10 bar mostly penalizes swaps between near-tied results: the median score gap between the 10th and 11th results is just 0.0033. Changing the bar needs human relevance judgments.
  • How big is a real flood? The flood size is an assumption. Peer scoring in gossipsub and Waku penalizes and disconnects peers that send invalid messages, but we found no source that puts a number on how many invalid messages can still reach one node, and we couldn't find nim-libp2p's limit on new connections. A source for either would tell us how much of the worst case the network already absorbs.
