1. The goal, and why

Replace the community operator with compute on users' own devices, so an online community can be as free, anonymous and forgetful as a real-life conversation and still be as easy to use as today's sites. Our part is the hardware that makes that compute cheap.

On today's forums the operator can read everything, can restore deleted posts, and comes under pressure that shakes the whole community. In a real-life conversation nobody is monitoring, only the speaker is responsible, and words are gone once spoken. We want those properties online:

  • Server-blind: servers and storage nodes never see plaintext. We don't allow any optimization that breaks this, such as letting the server build the search index.
  • No operator: nobody gets privileged access.
  • Forgetting: if the author deletes a post, the original is gone.
  • Creating identities is expensive: users are anonymous, but running many accounts is hard.
  • We don't give up usability: search, feeds, recommendations, votes, comments, chat and sub-communities stay. If peer-to-peer rules a feature out as it exists today, we replace it with something that meets the same need.

Earlier peer-to-peer communities gave up either autonomy and anonymity or usability. We get both by paying in compute, and that compute goes to two places:

  1. ML, to replace the operator's services: search (text embeddings + top-k), feed ranking, spam and bot detection.
  2. Crypto, to prove things without revealing them: signature checks, decryption, and anonymous credentials and zero-knowledge proofs.

The target device is an always-on home node box, something you leave running like a router or a NAS. Both ML and crypto are in scope for the course project. The project is not a generic "edge vector-search accelerator"; those already exist. What sets us apart is the conditions that server-blindness creates.

Scope. What the course grades is the hardware and systems work, but we don't limit what we implement. We build everything except physical devices and silicon: the protocol, the node software, the client, the community algorithms (spam, feeds, forgetting), and a simulation of many boxes and many users. A chip we can't fabricate is replaced by its cycle and energy model and attached to that software. Image posts are in scope too, so the box will also embed images.

2. The whole system: a community with everything but the hardware

We're building the community itself, not only the chip: M users and N home node boxes, running on one laptop. The design is done, the simulator's core (which messages reach which box) has results, and the box software on top of it (ingest, search, feeds, votes, forgetting, private rooms) now runs through a whole simulated day, both further down in this section. One box has also been run through backlog and attack scenarios, compared with existing box hardware on the same scenarios, and run against spam with valid proofs under three protocol defenses, which text-only spam turned out to break (section 5). And five boxes now run as real processes with a web page each, doing the same work the simulator counts (the demo). One question decides the approach: what runs for real, and what is a model?

  • Functions run for real (emulation). The box software is real code: real ciphertexts, real signatures, real embeddings, real search results. It runs on the laptop CPU instead of the box's hardware but computes the same thing.
  • Time and energy are simulated. We can't run hundreds of boxes in real time, so the simulator runs on a virtual clock (discrete events). Each task's time and energy come from our chip models (the verify-unit cycle model, the encoder's Timeloop + Accelergy model) and, for host work, from laptop timings scaled to a Pi 5-class CPU.
  • Each message is computed once. When many boxes receive the same post, the result (verification, embedding) is computed once and shared; each box is still charged the modeled time and energy.
  • Only the demo runs in real time: five boxes as real processes on the laptop, each with a web page to post, search, vote and chat. It doubles as a check that the simulator counts each box's work correctly (the demo).

Sensitivity. Limits. One user per box; a box shared by several people gets that many times the load. Gossip is immediate forwarding only (no IHAVE/IWANT gossip, no mesh-maintenance heartbeat, no penalties), and a box that is off stays off for the whole hour, with the mesh already repaired around it. The trace. The run writes a Perfetto trace of the peak hour for the median box and the busiest box (message counters plus verification spans). Download the JSON and open it at ui.perfetto.dev to zoom in like a waveform.

Who stores what: a smaller knob than we expected

Until now every chip number assumed that each box receives every public post. That was never written down as a choice. How posts are replicated across boxes decides how much one box has to ingest, so we compared three policies:

  • All: every box receives every public post (what the chip numbers assume today).
  • Subscribed: a box receives only the sub-communities its owner subscribes to.
  • Subscribed + k: subscriptions, plus the boxes share out any sub-community that has too few copies, so its posts stay available.

We decided in advance to take the policy that keeps availability (the chance that some other box holding a sub-community's posts is online while the author's box is off) at or above 99% in every sub-community, and of those, the one with the lowest load on the busiest 1% of boxes at the peak hour. Subscribed only won: every sub-community stays at or above 99% at every community size, and no sub-community had fewer than 3 subscribers, so "+ k" added nothing. But it barely helps the boxes that matter: the average box gets 0.78× the load of "All", the busiest 1% still get 0.94× simulation model. Activity is concentrated in popular sub-communities that nearly everyone subscribes to.

What the box software does in a day

On top of the simulator core, every box now does its real job on each message: check the signature and the proof, decrypt, embed, index, answer searches, rank a feed, count votes, forget deleted posts, and keep private rooms. Results (search hits, vote tallies, whether a deleted post is really gone) come from real code. Time comes from the chip models, and host work from laptop timings scaled to a Pi 5-class CPU. We ran a community of 10,000 boxes for one simulated day. Every box forwards gossip, but only 20 sample boxes keep full state (search index, tallies, the vote tags they have seen); the rest reuse the same result for the same message and only count work and time, because a separate index on every box would take several GB for 30 days of posts. The 30 days of older posts are loaded as already synced, and the day's new messages spread by gossip. Post text comes from our 2010 Reddit sample; images are synthetic (we haven't downloaded an image dataset).

How images travel

Pushing whole images clogs home uplinks (above). We compared three ways to move an image post, in the largest sub-community (9,420 boxes), 300 image posts 10 s apart simulation model:

  • Push: every hop sends the 177 KB image to its mesh neighbors.
  • Envelope + fetch: push only an envelope (header + thumbnail, 10 KB estimated); each box fetches the body once from the neighbor that sent it the envelope, then embeds it.
  • Envelope + author's embedding, spot-checked: the author's box puts its INT8 embedding (512 B) in the envelope, so boxes index the post on arrival. A few boxes per post (on average c = 14 of them) fetch the body, embed it again and flag a mismatch; a box that gets a flag hides the post and checks it itself.

We decided in advance: an image post must be searchable on subscribed boxes within 5 s (P99 at 20 Mbps). The embedding option also had to show that honest boxes almost never get flagged (false alarms ≤ 10-3), that a fake embedding is hidden on every box within 60 s, and that the chance no box checks a post is ≤ 10-6. Among the options that pass, the fewest image encodings on the busiest 1% of boxes wins, then the least uplink.

Limits of the simulated day, and the trace
  • Images are synthetic (no dataset downloaded yet). The embedding tolerance and image-search results may differ on photos.
  • Searching images with text works only through post titles and bodies: CLIP's text tower wasn't in the simulated day. We have since decided to keep MiniLM for text and use CLIP's text tower only to find images by words (The encoder). Measured since: the right photo is in the top 10 for 0.671 of captions over 4,700 COCO photos (FP32, photo results) and for all of them over the demo's 104 photos (the demo) measured.
  • Proof pairings aren't executed (valid/invalid flag + modeled cost). Tags and RLN secret sharing are real.

3. What the box must do, and why it needs hardware

Each box ingests encrypted posts. For every post it verifies the signature and the anonymous-credential proof, decrypts, runs a small text encoder (MiniLM) to embed the post, and inserts the vector into a local search index. It also answers search queries. Image posts add an image encoder (CLIP ViT-B/32 image tower, 4.41 GMAC, 2.36× a text post) to that path. On photos the image tower has to run in FP16 to keep search quality, and on our chosen encoder one image then takes 0.55 s and 64 mJ estimated (photo results).

The ordinary-day and flood numbers in this section and in the earlier box comparison (end of section 5) assume each box receives all 106 posts/day, messages are 1 KB, and a flood fills a 100 Mbps link assumption. The first simulator results (section 2) put the ordinary-day assumption at 26× what the busiest 1% of boxes ingest at the peak hour in a 1M-user community, so the ordinary-day numbers below are pessimistic. The simulated day (section 2) agrees: even the busiest boxes keep their encoders busy only 0.003% of the peak hour. The encoder is now sized from the simulated load (The encoder). The flood numbers don't depend on it.

An ordinary day: easy

< 1 W

active power for 106 posts/day estimated, whichever encoder option we pick. That is less than the box's own idle power, 2.4–4.4 W for comparable devices source.

A spam flood: hard

24–181 W

on CPUs, to verify every proof in a 100 Mbps flood of 1 KB messages (12,207 msg/s) estimated from measured costs. Our re-sized chip: 0.88 W when every proof is invalid, with the box checking proofs before signatures estimated.

Why the flood sets the size of the box: in an anonymous community you can't filter messages by sender. The only way to throw a message away is to verify its anonymous-credential proof first (Groth16 on the BN254 curve, the kind Semaphore/RLN use). If you can't verify fast enough, spam uses up all of the box's ingest capacity. Valid messages are capped by rate-limiting proofs, so the encoder's load stays modest. The simulator confirms this from the other side: on an ordinary day even the busiest boxes of a 1M-user community verify at most 4.2 proofs/s, 0.03% of the unit's capacity simulation model. Invalid proofs, on the other hand, cost an attacker nothing to make, so the hardest floods mix invalid proofs in to break batch verification (see Floods of invalid proofs). Two limits to this argument came out of the scenario runs (Where a box breaks first): the host CPU in front of the chip gives out first unless the box checks proofs before signatures, and spam that carries valid proofs (real identities posting up to their rate limit) gets past the verify unit and has to be stopped by the protocol, not by the chip. That part isn't solved yet (Stopping spam with valid proofs).

The hardware gap: with a 2 W power budget assumption, the box must spend ≤ 0.16 mJ per verification. That is about 12× more efficient than batched verification on a CPU and about 90× more efficient than one-at-a-time verification on a P-core estimated. Our unit stays under that even in the worst case: 0.077 mJ per proof at the worst mix of invalid proofs estimated. Existing edge NPUs (Hailo, Coral, RK3588) are 8/16-bit MAC arrays and have no way to do pairings or MSMs source. A Jetson GPU could in principle, but nobody has published ZK numbers for it. The encoder, by contrast, is already handled: a Hailo-8L runs MiniLM at 121 posts/s in a 1.4–1.9 W-class module vendor.

So our hardware contribution is proof verifications per watt. The comparison on equal scenarios (section 5) bears this out: the verify unit is what separates a box that survives the flood from one that doesn't. Putting the encoder on the same chip is a smaller gain: 3.9 mW on an ordinary day against 4.5–6.0 mW for a verify-only chip next to a Hailo-8L, and the Hailo pair is better on spam and on catching up estimated. A second candidate: an encoder whose output is bit-identical on every box, which software runtimes don't give (The encoder) and which would make image posts searchable faster.

4. Current chip design

The box: the path of one message

The verify unit sits in front of everything else, so invalid messages are dropped before the host checks a signature or the encoder sees them. The only thing the host does first is one table lookup that drops exact repeats; in a flood, checking signatures first would use up the host before the chip is even busy (Where a box breaks first).

Scroll the diagram sideways →

The host-CPU costs are small. On our laptop, an Ed25519 check is 29–31 µs on a P-core and 103–105 µs on a low-power E-core, and decrypting 1 KB is 1.7 / 3.1 µs measured. The encoder numbers come from Timeloop (how each matrix multiply maps onto the array) and Accelergy (45 nm energy and area: CACTI for SRAM, Aladdin tables for logic). We haven't written RTL for the encoder.

Inside the verify unit

The unit handles the whole job of accepting a proof, not just the pairing: decoding and subgroup checks are 26% (measured) to 36% (model) of the work per proof. Left on the CPU, they would need 1.4 P-cores during a flood.

Scroll the diagram sideways →

Keeping the multipliers busy took three things: as many adders as multipliers (there are 2.5 additions per multiplication), running all proofs in a batch in lock-step, and a lookahead window a few hundred operations deep. Before we switched to lock-step order, the earlier 5-multiplier unit managed 14,110 proofs/s. Reordering by dependency depth also fills the multipliers, but then the buffer grows to 740 KB. So the throughput-versus-buffer tradeoff is set by how the microcode orders operations, more than by the hardware.

The unit's size has moved twice. It started at 5 multipliers + 4 adders, sized for a flood of valid proofs. Floods of invalid proofs, where many proofs must be checked alone, pushed it to 8 + 8 at first. Making a lone check cheaper brought it back to 6 + 6 (see Floods of invalid proofs). A lone check now has 4.2 additions per multiplication, so the adders matter as much as the multipliers. Once the box checked proofs first, replays no longer reached the unit and the worst flood was all-invalid proofs again, so we asked whether it could shrink. It can't: 5 multipliers + 6 adders would be 95.6% busy in that flood, just short of the 5% headroom we require, and would have saved 0.28 mm² estimated. The operand register file's extra ports and the crossbar for 6 + 6 are not in the area model yet.

The chip: two gated domains behind PCIe

The box is a Pi 5-class host SoC (network, storage, queries, Ed25519, ChaCha20) with LPDDR4, plus our accelerator chip on PCIe. The chip has two power domains that are switched off whenever they have no work, and a small always-on part.

The encoder: sized for latency, backlog and identical embeddings

The encoder was first sized for "every box ingests all 106 posts a day". The simulator showed that the heaviest boxes get 1/26 of that and the encoder is almost always idle, and image posts joined the workload. 5. Key results

Where a box breaks first: five scenarios on the re-sized chip

We put the re-sized chip (8×8 encoder with 1 MB SRAM, verify unit with 6 multipliers + 6 adders) into one box and ran it event by event: a Pi 5-class host with 4 cores, a 100 Mbps downlink, and the load of the busiest box in a 1M-user community (upper end: every box storing every sub-community). The question was what breaks first (the chip, the host in front of it, or the protocol) and what the cheapest fix is. Before running, we wrote down the targets:

  • an honest new post is searchable within 5 s (P99); the box gets 4.64 s of that, after 0.36 s of network spreading
  • encoding a search query, waiting included, takes ≤ 50 ms (P99), the encoder's share of a 100 ms search answer
  • an 8-hour backlog is cleared within 60 min
  • during a flood, ingest uses at most 2 of the host's 4 cores; the other 2 are for the owner's own searches and feeds our new target
  • the chip stays ≤ 2 W in a flood and ≤ 50 mW idle

And the scenarios: an ordinary 24-hour day (239,304 proofs, 25,889 text posts and 1,143 images); the evening peak hour with the owner searching every 5 s; catching up after being off for 1, 8 or 24 hours while peak traffic continues; a flood that fills the 100 Mbps downlink with 1 KB invalid proofs (12,207/s) for 60 s, 3 random seeds; and spam with valid proofs, where K identities each post up to their rate limit with the most expensive content (a 256-token body plus an image) for an hour. All results here are model outputs estimated; only the cost of a connection handshake was timed on the laptop.

These runs used the image tower in INT8. Photos later showed it needs FP16 (photo results), and the comparison further down reran the scenarios that way. What changes for the current design: an 8-hour catch-up takes 17.8 min instead of 14.3; spam with valid proofs breaks freshness at 100 identities instead of 310; yielding at layer boundaries is no longer enough for queries (55 ms), so the encoder yields between matrix multiplies (31 ms); in the flood the chip draws 0.88 W and new posts are searchable in 0.34 s estimated.

Stopping spam with valid proofs, without an operator

Not solved yet. The three defenses below hold when spammers send photo posts, which is what we first assumed. Text-only spam breaks them: new users' posts never finish during an hour of spam from 10,000 new identities, and 541 aged identities are enough to break the old group. No way of putting the work budget into the proof fixes this; the best survives 7,044 new identities (0.70% of members). Details in Putting the work budget into the proof estimated.

The scenario runs left one attack the chip can't absorb. K identities, each with valid proofs, post the most expensive content (a 256-token body plus a photo) up to their rate limit. On the current chip (8×8 encoder, FP16 image tower, yielding between matrix multiplies), about 100 such identities, 0.01% of a 1M-user community, push honest new posts past 5 s. A tighter rate limit alone can't fix it. If 10,000 identities (1% of members) post at the honest limit of 6 posts per 10 minutes, that is 100 posts/s, and the text alone is 12 s of encoder work every second estimated. The box has to process the posts that are probably not spam first. But it can't tell who sent what: every post uses a one-time key and a fresh rate-limit tag each epoch, so there is no per-identity reputation to use. So we compared protocol defenses that keep messages unlinkable and need no operator:

  • Limit on encoder work: each post has a weight in units of encoder time. One unit is encoding a 256-token text post (0.124 s); a photo adds 4.43 units (0.552 s in FP16), so the most expensive post is 5.43 units. Each identity gets a budget of W units per window instead of a message count. This first run counted weight as a real number; how a real proof enforces it, and what that costs, is in the next part.
  • Photos last: the box embeds photos only after all live text. A photo post's caption and body are still searchable within 5 s. This changes box software only.
  • Age groups: identities that joined more than 30 days ago go into a separate membership group (a separate Merkle tree) from newer ones. The box sees which group's root a proof uses, which is one bit, and processes the old group first. The new group gets its own tighter limit. The cost: a message's anonymity set shrinks to its group.
  • Hardware identity (not simulated): one identity per box, proven anonymously with the chip's device key. We use it only to put a price on the attack that remains.

Putting the work budget into the proof, and the attack we had missed

The run above counted each post's weight as a real number. A real rate-limit proof (RLN) spends one message number per message, and using the same number twice in a window reveals the identity's secret, which is the penalty. So "a photo post costs 5.43 units" needs a proof design. The designs differ in where they cost: public inputs (verify time on the box, and the precomputed tables the verify unit keeps), circuit size (proof generation on the user's device), rounding (honest messages blocked, and how much an attacker gets), and whether the penalty still works. Before running, we wrote down what a design had to do: the penalty must always work; the same targets as above, under the attacker's worst strategy; and the verify unit must still keep up with a 100 Mbps flood of invalid proofs built on the most expensive circuit. Among designs that pass, the one that changes the fewest places wins.

  • Several message numbers per post: a post of weight w uses w rounded up to whole units, halves or quarters, as consecutive message numbers. The proof reveals a share and a tag for each number, so it has 3 + 2n public inputs for n numbers, and the box needs one verifying key per n. Two variants behave the same: one fixed-size circuit with unused slots switched off, and splitting a post into n messages with n proofs.
  • Size classes: 2 classes (text post, photo post) or 3 (short text up to 64 tokens, long text, photo post), each with its own count limit. The circuit doesn't change, but the attacker fills every class to its limit.
  • Separate budgets for text and photos: text counted in quarter units, photos as a separate count. We added this after the first full run showed why the others failed (see below).
  • Power-of-two blocks were dropped on paper: catching overlapping blocks needs tags at the ancestor levels, and if those carry rate-limit shares, two honest, non-overlapping sibling blocks expose their owner's secret. Without the shares, overlap is only refused and there is no penalty.
  • Two extra fixes, applied to every design. 128-token live text (box only): the live encoder embeds only the first 128 tokens of a post, and weight counts only what is encoded; an earlier test found the 128-token cut no worse for title search (Hit@10 0.968 vs 0.943 at 256 tokens) measured. Early message numbers first: the proof reveals one more bit, whether the message is within the first m units of its window, and the box processes those first.

Floods of invalid proofs

Batch verification checks n proofs at once with one randomly weighted pairing product. If even one proof in the batch is invalid, the whole batch fails and the unit has to find out which proofs are bad. For an attacker, valid proofs are expensive: each needs an identity and a generated proof, and exceeding the rate limit reveals their secret key. Invalid proofs are free: any three points on the curve pass the format and subgroup checks. So the cheapest attack is to mix invalid proofs into the flood. We modeled every share of invalid proofs from 0 to 100%. Honest messages are never dropped: every valid proof in a failed batch is still found and accepted.

The key number is the fixed cost of one check: the final exponentiation, the Miller loops for the verifying key's three pairs, and the public-input multi-scalar multiplication. In our first count it was worth 4.3 proofs, and a check of a single proof is almost nothing but this fixed cost. Field operations per check, decoding excluded, as first counted counted:

How to find the bad proofs in a failed batch. All four strategies run on the same hardware:

  • A, one by one: if a batch fails, check each of its n proofs alone.
  • B, split in half: retest each half as a batch. If the left half passes, the right half must contain a bad proof, so it is split again without being tested.
  • C, split in half and keep Miller values: after a failure, compute each proof's Miller loop value once and store it (384 B per proof). Each subtest then only multiplies stored values and pays the fixed cost.
  • D, adaptive batch size: pick the next batch size n from the recent failure rate, down to n = 1 (every proof alone) when many proofs are bad.

That is why deferring the check raised the worst case only a little (13,306 → 13,429). Deferring is safe: a proof that fails the test is discarded anyway, and every accepted proof still passes the subgroup check, so the set of accepted proofs doesn't change. A proof built to pass the test but fail the subgroup check costs the same as a valid one, which the numbers above already cover. The scenario runs later removed this worst case at the box level: the valid proofs in such a flood are replays, and a box that drops repeats before the proof check never sends them to the verify unit, which is then only 13% busy (Where a box breaks first).

Can the network layer stop invalid proofs instead?

Peer-to-peer networks already penalize peers that send bad messages, so we checked whether that caps how many invalid proofs reach one node. We found no source that gives a numeric per-node cap source:

  • gossipsub v1.1 forwards only messages that passed validation, so invalid proofs come only from directly connected peers. Each invalid message adds a penalty that grows with the square of the count, with no cap. Once a peer's score falls below the graylist threshold, its RPCs are ignored.
  • nwaku, the Waku RLN-relay implementation (relay.nim): an invalid proof is rejected and penalized with weight −100, the graylist threshold is −10,000, and bad peers are disconnected. It verifies proofs one at a time, without batching. From that, a connection is cut after about 10 invalid proofs estimated, assuming a topic weight of 1.
  • New connections: go-libp2p's resource manager allows 0.2/s per IPv4 /32, 0.2/s per IPv6 /56 and 0.5/s per IPv6 /48, with no global cap. We didn't find the equivalent limit in nim-libp2p, which nwaku uses.

So for the earlier unit's 6% limit (about 730 invalid proofs/s), an attacker needs 73 new connections per second, which about 366 IPv4 addresses (or 146 IPv6 /48s) can supply estimated. Penalties limit what one connection can do, not an attacker with many addresses. Having the chip itself survive any share of invalid proofs is the most robust way to keep spam from exhausting ingest.

For the full 100 Mbps flood on the current unit, the same penalty and per-address limits mean an attacker needs 6,104 IPv4 addresses to reach one box at link speed estimated. Each reconnect also costs the host a handshake (0.57 ms on a Pi 5-class core). A box-wide cap on new connections would stop such a flood, but it would also keep new honest boxes from joining during an attack, so we treat it as an extra defense and don't size the verify unit on it.

How the tool-based encoder estimate compares with our earlier hand model

Earlier we estimated the encoder by hand from 45 nm energy-per-operation tables (dynamic energy only): 8.55 mJ per post. The new tool-based estimate is 7.90 mJ, 0.92× the old one model. We had agreed that a gap above 2× would force us to redo the ordinary-day numbers; it stayed well inside that.

The totals agree, but the parts don't. One INT8 MAC costs 1.27 pJ in the Aladdin tables, 4.2× the 0.3 pJ we used before (INT8 multiply 0.2 + INT32 add 0.1). Memory is cheaper than we assumed: the 2 MB global SRAM is 12.6 pJ/byte (we used 25 pJ/byte from a 1 MB table entry) and DRAM is 64 pJ/byte (we used 160). Our synthesized Montgomery multiplier also came out 4.2× its early estimate, so the logic estimates move in the same direction.

Idle power depends on the SRAM cell and on power gating

Computed for the earlier chip with the 2 MB SRAM. The default model uses low-standby-power SRAM cells (CACTI's itrs-lstp), which barely leak. With high-performance cells (itrs-hp), the 2 MB SRAM alone leaks 1.04 W instead of 0.05 mW, and the whole chip leaks 1.10 W estimated. With gating, that chip still does the ordinary day at 0.19 W, the flood at 0.59 W and the backlog at 1.96 W (just under 2 W). Without gating it burns 1.1 W doing nothing, 22× our 50 mW idle limit. The catch with low-standby cells: a random access to the 2 MB array takes 2.37 ns, longer than the 2 ns cycle at 500 MHz, so it would need banking or two-cycle access, which the model doesn't include.

6. Paths we tried and dropped

  • Any one or two of the three spam defenses. Against an hour of spam from 10,000 new identities, age groups alone protect the old group, but new users' posts never finish. Photos last and a work limit, alone or together, have no way to tell new identities from old ones, so nobody's posts finish. Age groups with either of the other two still bury new users' posts estimated. Instead: all three together (new posts 0.16 s and 0.41 s, queries 31 ms), which holds against photo spam but not against text-only spam.
  • Assuming spammers send the most expensive post. Once photos go last, text-only posts put more than 5× as much work in front of honest posts with the same budget: new users' posts never finish under 10,000 new identities, and 541 aged identities break the box instead of 2,823 estimated. Instead: every run tries photo posts, text-only posts and the largest post in each size class, and keeps the worst.
  • One work budget for text and photos. It has to be bigger than one photo post (5.4 units), and text-only spam spends all of it in the live queue. Instead (best so far, not enough): separate budgets, text in quarter units plus a photo count, with live text encoded up to 128 tokens: 2,842 aged and 7,044 new identities, against a target of 10,000 new estimated.
  • Power-of-two blocks to charge a post's weight. Catching overlapping blocks needs tags at the ancestor levels; with rate-limit shares on them, two honest, non-overlapping sibling blocks reveal their owner's secret, and without the shares there's no penalty. Dropped before any run. Instead: several message numbers per post, size classes, or separate budgets, all of which keep the penalty.
  • Processing early message numbers first. The proof would reveal whether a message is within the first m units of its window. To push back at most 0.5% of honest messages, m has to be at least the limit itself (new group: 6.5 units against a limit of 5), so it separates nobody estimated. Instead: nothing; 128-token live text helped every design.
  • Age groups alone, as a cheap fix. Besides failing new users, they make the box weaker against aged identities: 55 instead of 103 today, because new users' lower-priority posts are the first to fall estimated.
  • Reputation per identity. Not possible without breaking unlinkability: every post uses a one-time key and a fresh rate-limit tag each epoch. Instead: the proof reveals one bit, whether its identity joined more than 30 days ago.
  • A 10-minute window for the new group's limit. A limit is a whole number per window, so it can't go below 1 per 10 minutes, and in a short test run new users' posts never finished under a 10,000-identity attack. Instead: whichever of a 10-minute and a one-hour window lets less spam through per identity; the one-hour window won (5 units per hour).
  • Letting only the first box that catches a rate-limit cheater announce the penalty. The simulator did this, but it needs knowledge of the whole network that no real box has; the real boxes showed it when two of them caught the same cheater measured. Instead: every box that catches it sends the notice, and the notice is one message tied to the revealed secret, so copies collapse into one and a box that already has it stays quiet.
  • Fetching each photo from a fixed neighbor (for example the lowest-numbered one). It would make each box's photo sends the same in real time and in the simulator, but it adds delay. Instead: a box fetches from whichever neighbor sent it the envelope; only the per-box split of photo uploads depends on timing, and the totals match (412 photo sends, 524 duplicates) measured.
  • An INT8 image tower. On 4,700 COCO photos, no INT8 version of CLIP's image tower keeps 0.95 of the exact search's top 10: 0.631 with INT8 in the linear layers only, 0.814 with the patch embedding and the first and last blocks left in float, even though caption recall drops by only 0.7–1.1 points measured. Instead: the image tower runs in FP16 on the chip's existing FP16 unit, 0.55 s and 64 mJ per image instead of 143 ms and 27.3 mJ estimated.
  • Letting search queries in only at layer boundaries. With the image tower in FP16, one image layer takes 46 ms, and a query waiting behind it takes 55 ms, over the 50 ms target estimated. Instead: the encoder switches tasks between matrix multiplies (31 ms).
  • Shrinking the verify unit to 5 multipliers + 6 adders. With proofs checked first, the worst flood is all-invalid proofs again, and 5 + 6 would be 95.6% busy, just short of the 5% headroom we require. It would have saved 0.28 mm² estimated. Instead: 6 + 6 stays.
  • Checking each message's signature before its proof. In a 100 Mbps flood of invalid proofs, the host's Ed25519 checks take 3.90 of its 4 cores, and 4.59 once penalties make attackers reconnect (new posts then wait 23 s), while the chip is only 85% busy estimated. Instead: drop repeats with one lookup, check the proof on the chip, then the signature: 0.85 host cores.
  • Catching up in plain arrival order. After 8 hours offline, new posts waited 18.9 s behind 95,000 missed messages on the host and the verify unit, whatever the encoder did estimated. Instead: backlog work gets at most 2 of the 4 host cores, and verification batches are filled with live proofs first (new posts 0.16 s).
  • One queue, or priority per whole task, for the shared encoder. With one queue, new posts (750 s) and queries (749 s) waited behind the whole backlog during an 8-hour catch-up; with priority per task, a query still waited behind a backlog batch or an image (359 ms at batch 8) estimated. Instead: the encoder lets queries in at layer boundaries (39 ms), and between matrix multiplies since the image tower moved to FP16.
  • A bigger encoder against spam with valid proofs. Growing from 8×8 to 32×32 raises the number of spamming identities a box survives only from 310 to 2,682 (with the image tower in INT8; 100 on 8×8 with FP16), against a benchmark of 10,000 (1% of members) estimated. Instead: keep 8×8 and defend in the protocol: age groups, a budget of encoder work, and photos last. They hold against photo spam from 10,000 new identities but not yet against text-only spam (Stopping spam with valid proofs).
  • One rate limit of 20 messages of any kind per 10 minutes. It blocks only 1.4×10-12 of honest messages, so it is just as generous to spammers simulation model. Instead: 6 posts and comments and 4 votes per 10 minutes, which raises the spam the box survives 3.3× for +1.3% verify cost.
  • A box-wide cap on new connections as the basis for sizing the verify unit. It would stop a many-address flood, but it would also keep new honest boxes from joining during an attack. Instead: the verify unit is sized for a link-speed flood (6,104 IPv4 addresses with penalties and per-address limits), and the cap is only an extra defense.
  • Sizing the box for "every box ingests all 106 posts a day." Nobody chose that number; it was a hidden assumption. With behavior from Reddit's statistics, the busiest 1% of boxes in a 1M-user community embed 0.45 text posts/s at the peak hour, 1/26 of the 11.6 posts/s we had assumed simulation model. We had decided in advance to re-decide the encoder toward smaller if real ingest fell under a tenth of the assumption. In the simulated day the encoders were busy only 0.003% of the peak hour, even on the busiest boxes. Instead: the encoder is sized by search latency, the backlog after a box has been offline, and images, which brought it from 32×32 with 2 MB of SRAM (9.22 mm²) down to 8×8 with 1 MB (3.53 mm²) estimated.
  • One CLIP model for both text and images. Fewer models would make a simpler chip, but CLIP's text tower finds a post by its title in the top 10 only 0.776 of the time, against 0.943 for MiniLM measured; we had allowed a gap of 0.005. It's lower on short posts too, so it isn't only CLIP's 77-token cut. Instead: MiniLM for text, CLIP's image tower for images, and CLIP's text tower only to find images by words. Three models cost DRAM capacity, not chip area.
  • Static INT8 as a way to make every box compute the same embedding. It is bit-identical across batch sizes and thread counts, but the same model file gives different values in two runtimes (cosine 0.872), and its quality is low (0.798 against FP32 on synthetic images; on photos, too low for search, see the INT8 image tower above) measured. Instead: image posts keep envelope + fetch, and an integer-only encoder with a fixed operation order and rounding is a candidate chip requirement.
  • A 512 KB encoder SRAM. The activations of one 256-token post (786 KB) don't fit estimated. Instead: 1 MB. Spilling activations to DRAM might make 512 KB work; we haven't weighed the extra DRAM traffic.
  • Bundling each user's votes into one proof every 50 s. Every vote carries its own proof, and votes are about 90% of proof-carrying messages. Bundling was meant to cut that, but each bundle held 1.00 vote on average and vote counts arrived 26 s later on average simulation model. It technically passed our advance rule (lower verification, counts within 60 s) by 0.1%, which is no real gain. Instead: one proof per vote, carrying both a rate-limiting tag and a per-post tag (+1.3% verification cost estimated).
  • Vote proofs with only a rate-limiting tag. They cap how often someone votes, but let one person vote several times on the same post within the limit. A per-post tag alone has the opposite gap (no limit across posts). Instead: both tags in one proof, the only design that keeps one vote per post, a rate limit and unlinkability.
  • Pushing whole images through the gossip network. Every hop sends 177 KB to each mesh neighbor in turn: 1,181 KB of uplink per box per image post on average simulation model. Instead: push a small envelope and fetch the body once, the same number of image encodings at 0.21× the uplink, though not faster (2.01 vs 1.82 s at 20 Mbps).
  • Shipping the author's image embedding and spot-checking it. It was by far the fastest (0.40 s at 20 Mbps, 0.01× the image encodings) and caught every fake embedding within 1.32 s simulation model. But the same image gives cosine similarity as low as 0.877 between FP32 and INT8, while two different images reach 0.981 measured, so no threshold separates an honest box from a fake. Could come back if every box ran an integer-only encoder with bit-identical output. Static INT8 in software doesn't get there (different runtimes disagree), so that would take a fixed spec that a chip implements.
  • Plain INT8 encoder. No INT8 variant reached our quality bar (Recall@10 ≥ 0.95 against exact FP32 search); the best was 0.878. Mixed precision needed 83% of weight MACs left in FP32 and was only 1.1× faster. Instead: ingest in INT8 and re-rank the top 20 in FP32 at query time. That gives Recall@10 0.993 and ingest 1.9× faster with 2.2× less energy than FP32 (3.70 ms, 0.25 J/post) measured, at about 252 ms and 18.7 J per query estimated.
  • "The laptop NPU is too slow, so we need hardware." Out of the box it was about 3× over the backlog target. But 89% of its time (at 256 tokens) went to a softmax plus broadcast mask that the compiler sent down a slow path. Expanding the mask fixed it: 45 min, Recall@10 0.997 measured. It was a software problem, so we moved the target to the always-on box and argued from power instead of time.
  • Doing the crypto on the encoder's INT8 array. 615 proofs/s, 40× short estimated. A weight-stationary array pays off only when one operand stays put, but pairing math is mostly variable × variable, and the array has no integer carry handling.
  • A big-integer multiply instruction on the host core. The energy was fine (0.012 mJ/proof) but it ran at half the throughput and would tie up the host core for the whole flood estimated.
  • Software only. Batched verification on one low-power core: 989 proofs/s, 2.06 mJ/proof measured. It misses on both energy and throughput.
  • Wider multipliers (128/256-bit word). They were bigger, slower and used more energy per multiply (table above).
  • Interleaving independent multiplies through a pipelined multiplier and letting the tool retime it. We had decided up front that it needed a 1.5× clock gain to justify the complexity. The clock rose only 1.20–1.22× (about 360 MHz): the critical path stopped at 2.78 ns inside the retimed multiplier, and we haven't found out why. We gave up a real gain to stick to that call: the 2-way version would have been about 20% smaller (0.91 vs 1.13 mm² for a 4-multiplier unit).
  • A 32×32 encoder array with 2 MB of SRAM. We chose it when every box was assumed to ingest all 106 posts a day: then 16×16 needed 106 min and 8×8 401 min for an 8-hour backlog, over the 60-minute target model. Under the simulated load, 8×8 clears the backlog in 11.3 min (14.3 min when peak traffic continues during the catch-up, 17.8 min with the image tower in FP16). Instead: 8×8 with 1 MB, 3.53 mm² instead of 9.22 mm² estimated.
  • Keeping the 5-multiplier verify unit and relying on smarter batch splitting. It was sized with 2× headroom over a flood of valid proofs, but no splitting strategy can go below the cost of checking every proof alone, and that drops it to 7,469 proofs/s, 61% of the flood, when every proof is invalid (with our first operation count) cycle model. 7 multipliers + 7 adders still came up 5% short, so at first we went to 8 + 8.
  • An 8 + 8 verify unit. Part of that size came from our own operation count being conservative (general instead of cyclotomic squarings, a plain binary exponent). With the library's real formulas, a precomputed verifying-key table and a deferred subgroup check, the cost to reject an invalid proof fell to 0.65×, and 6 multipliers + 6 adders keep up at any share of invalid proofs (2.12 mm² instead of 2.69 mm²) cycle model.
  • Sending proofs uncompressed. It skips three square roots per proof but doubles the proof to 256 B and changes the wire format, and the smallest unit that keeps up is still 6 + 6 (5 + 6 reaches 97% of the flood) cycle model. We decided in advance to change the format only if it saved a multiplier.
  • Caching each proof's Miller loop value to split failed batches faster. Every subtest still pays the fixed cost of a check, so it was no better than simply recomputing, and it needs extra storage (48 KB at n=128) cycle model.
  • Relying on network-layer peer penalties to stop invalid proofs. Peers that send invalid proofs get penalized and disconnected, but we found no source for a numeric per-node cap, and an attacker with a few hundred IP addresses gets around it estimated. So the chip itself has to survive a flood of nothing but invalid proofs.
  • A verify-only chip next to a Hailo-8L (the runner-up). On the same scenarios it meets every target and beats our one-chip design on spam with valid proofs (2,327 vs 100 identities, under the old per-identity limit) and catching up (1.0 vs 17.8 min); its 128-token cut didn't cost quality on our test. We keep one chip because its ordinary-day accelerator power is lower: 3.9 mW against 4.5–6.0 mW with the Hailo's idle power counted as zero estimated. Could come back if a source puts the Hailo-8L's idle power at a few mW or less and spam tolerance matters more.

Good places to start (no hardware tools needed)

  • The client web UI. A first version exists: each demo box serves one page to post text or a COCO photo, read the feed, vote, delete your own post, search, find photos by words, use a private room, and see the box's work counts (The demo). It's plain, and nobody outside the project has tried it. Making it feel like a real community site, or running a small usability test with a few classmates, would help. No CAD tools or chip knowledge needed.
  • The behavior parameters we had to estimate. Most come from Reddit's public statistics now (table in section 2), but we found no source for the time-of-day curve, a direct measure of how popularity spreads across sub-communities, post body length, page views per daily user, or any non-Reddit community such as DCInside. Subscriptions per user and the share of boxes online are estimates too. A source for any of these would firm up the per-box load.
  • The Hailo-8L's idle power. It now decides one chip versus two: a verify-only chip next to a Hailo-8L meets every target and handles spam (under the old per-identity limit) and catching up better, and our one-chip design wins only by 0.6–2.1 mW on an ordinary day plus whatever the Hailo draws when idle estimated. A datasheet, forum measurement or paper that gives the Hailo-8L's idle power on a Pi 5 would settle it. No hardware tools needed.
  • What should an identity cost? This is now the open center of the spam problem. Age groups, a work budget and photos last don't survive text-only spam from 10,000 new identities (1% of members); the best version survives 7,044 new identities and 2,842 identities older than 30 days. An anonymous rate limit can't tell an honest new user from a new spam identity, so either new users must be few (see the next item) or creating an identity must cost something: time, money, or a box if identities were tied to hardware estimated. We don't model what it takes to keep thousands of identities dormant and unnoticed for 30 days. Prior work on the cost of aging anonymous identities, on hardware-attested identities, or on spotting dormant accounts without linking posts would go straight into the design. Protocol thinking, no hardware tools.
  • How many new users, and how do they post? The spam defenses assume new accounts (joined within 30 days) are 5% of honest users and post like everyone else; we found no source for either. Against text-only spam this share now decides the verdict: a tight new-user limit holds against 10,000 new identities while blocking at most 1 in 1,000 honest messages only if new users are at most 2.8% of honest users; it passes at 1% and fails at 20% estimated. Any public statistic on new-account share or new-account activity (Reddit, forums, papers) would settle this.
  • Image posts on slow uplinks. With envelope + fetch, an image post is searchable within 2.01 s at 20 Mbps but takes 5.86 s at 5 Mbps (P99), over the 5 s target simulation model. Prior art on moving large payloads through gossip networks, or a delivery trick for slow boxes, is welcome.

Open hardware questions you could take

  • The rate-limit proof on a phone, with real constants. Our circuit for charging a post's weight uses placeholder Poseidon constants (right constraint count, not secure), and proof generation was measured only on one laptop CPU thread: 363 ms for one message number, 1,161 ms for 24 measured (preliminary). Users make these proofs on their own devices, so a real circuit with production constants, timed on a phone, would show whether the heavier designs are usable. Crypto, no chip tools.
  • An encoder controller that switches tasks between matrix multiplies. One encoder serves search queries, new posts and the backlog. With the image tower in FP16, one image layer takes 46 ms, so stopping only at layer boundaries leaves a query at 55 ms. Stopping between matrix multiplies (an image becomes 49 pieces) brings it to 31 ms estimated. The activations already sit in the 1 MB global SRAM; what's missing is the controller: what state it saves at each switch, how big the switch overhead is, its area (not counted yet), and whether a query's activations fit alongside a paused 256-token post or image. A small, self-contained design question.
  • An integer-only encoder with bit-identical output. The fastest way to deliver image posts needs every box to compute bit-identical embeddings. Dynamic INT8 changes with the batch; static INT8 doesn't, but two runtimes running the same file still disagree (cosine 0.872) measured. An encoder that defines every operation in integers, including GELU, softmax and LayerNorm, with a fixed order and rounding (as in I-BERT, arXiv 2101.01321), would be a spec a chip can guarantee. The catch: on photos, none of our INT8 versions of CLIP's image tower keeps 0.95 of the exact search's top 10 (the best, mixed precision, gets 0.814) measured. Can an integer-only design do better, and at what area? A good self-contained project.
  • ARM measurements. We have no verification costs on ARM, from measurement or from any source. A real box CPU is likely ARM. Running the Groth16 / Ed25519 / ChaCha20 benchmarks on a Raspberry Pi 5 would fill that gap.
  • Pi 5 + Hailo measurements. The Hailo numbers are vendor figures on an x86 host with PCIe Gen3 x4, and the Pi 5 has x1. MiniLM power isn't published (we borrowed a vision-model figure), and we don't know its idle power. The 128-token input turned out not to hurt on our title-search test (Hit@10 0.968 vs 0.943 at 256) measured, but its CLIP image tower quality is only known from the vendor's CIFAR-100 figure. Measuring throughput, power and especially idle power on a real Pi 5 would firm up the comparison.
  • Encoder on the Pi 5 CPU. We haven't measured the encoder's energy on a Pi 5 CPU, so we couldn't evaluate the cheapest option (verify-only chip, encoder on the host). If the CPU handles an ordinary day within about 0.09 W, that option comes back. One warning from the equal-scenario comparison: a single Pi 5 core encoding queries misses the 50 ms target at the evening peak (124 ms) estimated.
  • Fewer additions in the verify unit. A lone check now does 4.2 additions per multiplication. With proofs checked first, 5 multipliers + 6 adders would be 95.6% busy in the worst flood, just short of our 5% headroom. Cutting additions a little, or a smarter adder (for example, a three-input adder, or multiplying by the constant 9 with one shift-and-add), could drop a multiplier and save 0.28 mm² estimated.
  • RTL for the rest of the verify unit, and for the encoder MAC. Only the Montgomery multiplier exists in RTL. The 254-bit adders, the operand buffer, the microcoded sequencer and the encoder's INT8 MAC are still estimates. With 6 multipliers and 6 adders, the operand register file needs more ports and a crossbar, which the area model leaves out.
  • Hand-pipelining the multiplier. We'd like to know why retiming stops at 2.78 ns. A hand-split pipeline reaching ≥ 443 MHz (1.5×) would make interleaving worth reopening.
  • A better scheduler. Our scheduler is a simple greedy one in program order, and our throughput assumes the microcode runs independent checks side by side in lock-step. Run one at a time, a lone check on the 6 + 6 unit takes 26,542 cycles, which is 11,303 proofs/s, short of the 12,207/s flood. The utilization we assume also comes from batches, which have fewer additions per multiplication than lone checks. A scheduler that keeps the unit busy on lone checks would confirm 6 + 6; if it can't, 7 multipliers + 6 adders is the fallback.
  • Adapting the batch size against a changing attacker. Our results pick the batch size knowing the invalid share, which is an upper bound. A real unit has to estimate it from recent failures, and an attacker who switches the share suddenly costs it a few batches. Queueing delay during the flood also isn't modeled.
  • Is our quality bar right? The strict Recall@10 bar mostly penalizes swaps between near-tied results: the median score gap between the 10th and 11th results is just 0.0033. The same bar is what pushed the image tower to FP16: on photos, INT8 keeps caption recall within about 1 point but only 0.63–0.81 of the exact top 10 measured. Changing the bar needs human relevance judgments.
  • How big is a real flood? The flood size is an assumption. Peer scoring in gossipsub and Waku penalizes and disconnects peers that send invalid messages, but we found no source that puts a number on how many invalid messages can still reach one node, and we couldn't find nim-libp2p's limit on new connections. With go-libp2p's per-address limit and nwaku's penalties, our estimate is that 6,104 IPv4 addresses are enough to flood one box at 100 Mbps. A source for either would tell us how much of the worst case the network already absorbs.
